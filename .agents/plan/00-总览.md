## 顺序保障

母任务之间在母任务粒度不存在全序（如 数据与同步 ⇄ 账号与登录 互为前置），顺序在**子任务粒度**成立，三层机制保证：

1. **波次闸门（母任务级）**：按 W1–W8 分批过确认门——只把当前波次的母任务置「进行」，其余停在「拆解」；状态 ≠「进行」的母任务不派发任何子任务。复用既有状态机，是最硬的闸门。
2. **依赖核查（子任务级）**：各 `_母任务.md` 的「外部前置」与拆解清单依赖列细化到具体子任务（如「外部：账号与登录/02」）；派发任何子任务前，编排者核查被依赖子任务文件的状态行全部=「完成」，不满足不派发。子任务文件已全量预生成（2026-07-23），文件存在与初始状态不代表已启动——**子任务「已启动」的判定 = 其母任务状态=「进行」且编排者已派发**；母任务=「拆解」下的子任务文件一律视为未启动。
3. **状态遍历审计**：任意时刻状态遍历命令可核对在办任务与波次一致性，发现越波派发即停并纠正。

## 统一约定

- 一个方案生成一个母任务：`.agents/tasks/<方案名去编号>/`，以 `tasks/_template-epic.md` 为底；方案的「方案级验收标准」即母任务「整体验收标准」的直接来源，「拆分建议」表是「拆解清单」的参考底稿（拆解时可增删，以母任务文件为准）。
- 功能点明细与实现状态以 TODO.md 为唯一事实源，方案内只列功能节点与边界，不复制逐点状态；状态流转由开发角色按 AGENTS.md 同步 TODO.md。
- 验证命令一律用 AGENTS.md「应用命令」节：`pnpm run check`、`pnpm run dev`/`tauri:dev` 手动走查、`cargo test --workspace`、`cargo check --workspace`；契约变更必跑 `pnpm run types:generate` 并同步调用方。
- 已锁定技术决策（不在方案内重议）：端侧 SQLite 走 Rust rusqlite + command 封装、经 repository 接口进视图端；登录为邮箱 + 密码自建 token；服务端持久化用 SQLite。
- 视觉与交互规格以 DESIGN.md 为准，由各母任务的 UI/UX 阶段产出，方案不含视觉规格。
