# 落地方案 06：数据与同步

- 来源：TODO.md 模块 6（6.1 本地持久化 / 6.2 自动同步 / 6.3 日历集成）
- 前置方案：前段无（全项目首个启动的方案）；后段子任务分别依赖方案 05（登录绑定）与 09（移动接入）
- 端序阶段：前段 = W1 底座；后段随 W6/W8；日历集成随 W7
- 母任务：未生成（建议名 `数据与同步`）

## 范围

- 6.1 SQLite 落地（端侧统一本地库）、Store → SQLite 一次性迁移。
- 6.2 契约扩展（周期规则、标签、象限、清单、子任务、备注、开始日期、时间段、估时、附件链接、依赖、手动排序等新字段）、服务端 SQLite 持久化、备份容灾、监控告警、登录绑定（依赖 05）、移动端同步接入（依赖 09）。
- 6.3 ICS 导出、ICS 订阅。
- 边界：各业务字段的语义与界面归各业务方案，本方案只负责底座与通道；订阅功能分层（同步收费开关）归方案 12。

## 技术要点

- 已锁定决策：端侧 SQLite 走 Rust rusqlite + `#[tauri::command]` 封装，视图端经 repository 接口注入 Pinia（现有 store 持久化调用点收敛到 repository，组件不感知实现）；服务端持久化同用 SQLite（替换现状 `Arc<Mutex>` 内存态操作日志）。
- 迁移：启动时检测 Store 旧数据 → 事务式导入 SQLite → 成功后标记迁移完成；失败则保持 Store 读取路径可用（不丢数据是硬标准），浏览器开发模式仍回退 localStorage。
- 契约扩展是全项目扇出最大的一步：contracts 派生规范照 AGENTS.md（`camelCase`、`deny_unknown_fields`、可选字段规约），每批字段变更即跑 `pnpm run types:generate` 并同步全部调用方；op-based 同步的操作类型随字段扩展，冲突仍为服务端优先、字段级合并。
- 备份容灾：服务端 SQLite 定时快照 + 恢复演练脚本；监控告警最小集 = 健康检查端点 + 错误率/可用性告警（具体通道随部署环境定，方案 12 双市场部署时复用）。
- ICS：导出为文件生成（客户端本地即可）；订阅为服务端只读 ICS feed 端点（需 05 的 token 或签名 URL）。
