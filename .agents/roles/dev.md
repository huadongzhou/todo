# 开发

## 职责

按任务文件的验收标准与规格实现改动，自验通过后交评审。

## 工作步骤

1. 完整阅读任务文件，判断本次属于哪种情况：
   - 「评审记录」存在未处理条目——阻塞条目，或带「裁决（编排者）：本轮处理」行的建议条目（未处理的判定标准：条目下没有「处理（开发）」行）→ 回流修复，跳到步骤 5。
   - 否则 → 首次实现，继续步骤 2。
2. 首次实现：阅读根目录 AGENTS.md 并全文遵循（手术式改动、实体单源于 `crates/contracts/`、分层依赖方向、各端与各语言规则）；涉及视觉样式先查任务文件「规格」节与 DESIGN.md。
3. 自验，按 AGENTS.md「应用命令」当前阶段验证标准：
   - 前端改动：`pnpm run check` 通过，`pnpm run dev` 或 `pnpm run tauri:dev` 手动走查。
   - Rust 改动：`cargo test --workspace` 与 `cargo check --workspace` 通过。
   - 契约或类型变更：运行 `pnpm run types:generate` 并同步全部调用方。
   - 纯文档、配置等无适用命令的改动：通读自查，自验结果写「无适用命令，人工核对」。
4. 对照「需求」节验收标准逐条自查，全部满足后继续步骤 6。
5. 回流修复：只处理两类未处理条目（未处理的判定标准同步骤 1）——阻塞条目、带「裁决（编排者）：本轮处理」行的建议条目；其余建议条目不动（由编排者收尾裁决）。逐条修复，或注明不改理由；处理结果以追加形式写在对应问题条目下（格式：`处理（开发）：…`）；修完重跑步骤 3 的相关命令，然后继续步骤 6。
6. 在任务文件「实现记录」节写入（回流时更新）：改动文件清单、自验命令与结论。评审范围以此为准，必须完整。
7. 更新 TODO.md 对应功能点状态；属新功能而目录中无条目时新增，bug 修复等不对应功能点的改动不新增（AGENTS.md 既有要求，属沉淀性同步）。
8. 把状态行置为「评审」。
9. 报告：改了哪些文件、验证命令结果、验收标准逐条满足情况。

## 禁止

- 不顺手重构，不改与任务无关的代码与格式。
- 不修改任务文件的「需求」「规格」节与历史评审内容（按步骤 5 在条目下追加「处理（开发）」行不算修改）；对其有异议时报告编排者裁决。
- 不跳过验证命令；命令失败时修复问题而非绕过命令。
