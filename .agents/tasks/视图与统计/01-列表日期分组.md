# 列表日期分组

- 级别：简化
- 状态：设计

## 需求（产品）

- 目标与场景：进行中列表按 今天/明天/本周/以后/逾期 分组展示。
- 范围（做 / 不做）：做 分组逻辑与展示；不做 排序（02）。
- 验收标准（逐条可检查）：
  - [ ] 五组划分正确，跨天（日切）自动刷新归组。

### 编排者并入项（来自 任务管理/03 评审第 1 轮，已裁决「转任务处理」）

**「将来」分组的口径冲突需在本子任务收口**：`任务管理/03` 已交付「开始日期」字段、`isNotStarted` 判定依据（复用 `src/lib/dueDate.ts` 的日历日算法）与列表行的「{明天/N天后/M月D日}开始」徽标，但**分组、移出、计数、日切**明确归本子任务。

冲突点：本子任务的五组是按**截止日**划分的，而「将来」是按**开始日期**判定的——两者正交。一个有截止日、但开始日期尚未到的任务，同时满足两套口径。请在本子任务里把两套口径收口成一套明确规则（谁优先、是否互斥、计数怎么算），不要让两处各自实现。

补充验收标准：

- [ ] 「有截止日 + 开始日期未到」的任务归属唯一且可解释，不同时出现在两组里。
- [ ] 跨过零点（日切）后分组与计数自动更新，无需重启应用。

### 编排者补充（来自 任务管理/04 评审第 1 轮）

**撤销的可见性取决于列表行显示多少字段**：04 交付撤销/重做后，只改动**备注 / 时间段 / 估时**的编辑被撤销时，列表行 `innerText` 逐字节不变、也无任何提示——用户按下 Ctrl+Z 后看不到任何变化。

编排者当时写给 04 的验收标准「按 Ctrl+Z 必有可见效果」后半条越界了：一次撤销是否可见，取决于列表行显示多少字段，而列表行的内容归本母任务，04 无从决定。因此该缺口转记于此。修法二选一（或都做）：① 列表行显示更多字段；② 为撤销新增一类页面提示来源——注意后者要重跑 `任务管理/03` 规格第 5 节的提示优先级与遮蔽约束，且 03 已确立「不新增第二个 live region」。

补充验收标准：

- [ ] 用户可感知一次撤销确实发生了（无论经列表行变化还是经提示），不存在「按了没反应」的编辑类型。
