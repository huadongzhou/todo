# 拖延洞察

- 级别：简化
- 状态：设计

## 需求（产品）

- 目标与场景：统计任务被顺延/改期次数，识别卡壳任务并提示拆解（可接 AI 拆解）。
- 范围（做 / 不做）：做 计数埋点消费与洞察展示；埋点字段已在契约。
- 验收标准（逐条可检查）：
  - [ ] 顺延/改期计数准确；卡壳阈值提示正确且可关闭。

### 编排者并入项（来自 任务管理/05 的 UI/UX 阶段，已裁决「转任务处理」）

**顺延无留痕**：`任务管理/05` 交付「逾期任务自动顺延到今天」，但契约里没有「原始截止日 / 顺延次数」这类字段，因此顺延不留任何痕迹——一条被顺延过 10 次的任务与今天刚建的任务在数据上无从区分。

这正是本子任务要消费的数据：拖延洞察若要回答「哪些任务在被反复推迟」，就必须有留痕。请由本子任务决定字段形状（放 `Todo` 上还是独立事件流）并落进契约，而不是由 05 凭空先加一个没有读者的字段。

**追加【前置必办】：给复制口径装上编译期护栏**（来自 `任务管理/05` 评审第 1 轮）。`任务管理/05` 的 `src/stores/todos.ts` 里 `duplicate` 的字段表只有一句注释声称「漏掉某字段会是编译错误」，实际不会——`Todo` 的可空字段按契约惯例都是可选属性，对象字面量漏掉可选字段 TS 不报错。于是 05 规格第 3 节那条维护规则（「新字段进契约不进复制表即视为复制漏了它」）在代码里**没有任何强制力**：将来往 `Todo` 加字段而忘了加进复制表，用户复制任务时会静默丢掉那个字段的值。

本子任务正是第一个要给 `Todo` 新增字段的地方，护栏装在这里立刻能被新字段验证。仓库已有正解：`src/lib/todo-repository.ts:272` 的 `satisfies Record<keyof Todo, TodoFieldRule>`（05 新增的 `archivedAt` 正是被它拦下的），照搬即可。

补充验收标准：

- [ ] 被自动顺延或手动改期的任务留有可查的痕迹，拖延洞察能据此识别反复推迟的任务。
- [ ] `duplicate` 的复制字段表由类型系统保证完整：故意往 `Todo` 加一个字段而不改复制表，`pnpm run check` 必须报错（须实测）。
