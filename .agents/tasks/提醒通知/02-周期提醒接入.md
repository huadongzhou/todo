# 周期提醒接入

- 级别：直达
- 状态：完成

## 需求（产品）

- 目标与场景：周期任务每次实例到点均提醒。（外部前置：任务管理/06、/08 完成）
- 范围（做 / 不做）：做 实例生成与调度器联动；不做 规则本体。
- 验收标准（逐条可检查）：
  - [ ] 周期任务连续两次实例均按时提醒（含跨日用例）。

### 编排者并入项（来自 任务管理/12 评审第 1 轮，已裁决「转任务处理」）

**入站同步不重排本端提醒**（`src/stores/todos.ts` 的 `applyRemoteUpsert`）：该函数对任何字段都不触碰提醒排程。`任务管理/12` 接了「锁定任务不排提醒、本地完成/删除/还原前置即重排」，但**远端**完成某前置时，本端依赖任务的提醒不会被重排（本地看仍锁定）。这不是 12 的缺口（既有边界，12 未新增偏差），而是「提醒排程随入站同步刷新」这一面尚未建立。

本子任务把提醒排程接周期实例，请把「入站同步导致的状态变化应触发受影响任务的提醒重排」一并纳入——不只是周期，还包括依赖解锁、远端改提醒时间等。若排程届时已下沉 Rust，则在 Rust 侧的入站合并后重排。

补充验收标准：

- [ ] 远端变更（含完成某前置、改提醒时间、周期推进）经入站同步后，本端受影响任务的提醒被正确重排，不需要重启或本地再操作一次。

## 实现记录（开发）

### 结论：由 01 的轮询架构满足，本任务只验证 + 补域测，不新增运行时代码

先通读 01（`提醒通知/01-Rust调度底座`）后判定：本任务两条验收（周期实例每次到点均提醒、入站同步重排提醒）**已由 01 的「Rust 后台线程每 30s 轮询 SQLite、从当前数据现算 `due_reminders`、`reminder_deliveries` 按 `(todo_id, reminder_at)` 防重发」架构天然覆盖**。核实的链路如下，均可 cargo 测：

- **周期实例每次到点均提醒（核心验收，含跨日）**：周期实例由 store 生成，有两条路径，两条都把 `reminder_at` 位移到下一次发生：
  - 新 id 路径（`src/stores/todos.ts::buildNextInstance`，非打卡型 completeRecurring/顺延）——完成源行后另插一行新 id，`reminderAt: shiftInstant(source.reminderAt, shift)`。源行完成即被 gating 排除（非 Open），后继新 id + 新 `reminder_at` 是全新投递键，下一轮轮询发它。
  - 同 id 原地推进路径（`checkInHabit`／`advanceOverdueRecurring`，打卡型日/周与逾期顺延）——保留 id，`reminder_at` 经 `shiftInstant` 移到下一次发生。同 id + 新 `reminder_at` 仍是新键（键含 `reminder_at`），旧键已投递不重发，新键照发。
  - `shiftInstant` 产出 `Date.toISOString()`（形如 `2026-07-25T09:00:00.000Z`），01 判定用的 `crates/domain/src/ics.rs::instant_unix_seconds`（`parse_instant`）可读该带 `.000Z` 分数秒的格式——已核 `parse_instant` 分数秒分支，且新测直接用该字符串跑通即为跨层证据。
  - **本次新增 2 项 domain 单测**锁定该链（`crates/domain/src/reminder.rs`）：`consecutive_recurring_instances_each_raise_their_own_reminder`（新 id 路径：实例一到点发→完成+后继新 id 次日到点只发后继、已投递的前驱不重发＝连续两实例各发一次·跨日）、`a_recurring_row_advanced_in_place_re_arms_its_reminder_for_the_next_occurrence`（同 id 原地推进：首发→次日推进后新键再发→记后二次不重发＝每实例恰发一次·跨日）。两测均用 `.000Z` 格式，兼作 `instant_unix_seconds` 跨层读法校验。

- **入站同步重排提醒（编排者并入项）**：01 是轮询现算架构，schedule＝SQLite 数据本身。`applyRemoteUpsert`（改字段后 `persist(existing)`）与 `applyRemoteDelete`（`forget`）都写同一 SQLite（`repository.save`→`nativeCommands.saveTodo`→被 `TodoDb` 管理的连接），而调度线程经 `app.state::<TodoDb>()` 读同一连接。故远端变更落库后，下一轮（≤30s）轮询重导 gating（依赖解锁、改提醒时间、周期推进），**不需重启或本地再操作**。并入项写在旧前端 setTimeout 架构下（`applyRemoteUpsert` 不触碰排程＝真缺口）；01 把排程下沉 Rust 轮询后，「排程随入站同步刷新」这一面已结构性建立，缺口消解，**无需在 `applyRemoteUpsert` 重排提醒（AGENTS 简约至上，不重复实现已满足项）**。三种远端变更的判定分别由域测覆盖：完成前置→解锁重排＝既有 `a_locked_task_holds_its_reminder_until_the_prerequisite_is_done`；改提醒时间→再发＝既有 `a_reminder_edited_to_a_new_time_is_raised_again`；周期推进＝本次两项新测。`due_reminders` 是数据驱动、对「数据从何而来」无感，故「经入站同步后」在域层与任何数据变化同构，无需另写入站专属域测。已复核无「改数据却不落库」的入站路径（两条入站方法均 persist/forget）。

- **轮询延迟（30s）判断：可接受，不改**。提醒设在 T 最坏 T+30s 发。任务级提醒非秒级临界，30s 内到点在人可容忍范围；01 的 60s 逾期宽限（宽于一个轮询间隔）已把「窗口内到点」归为准点而非逾期，架构已吸收这段延迟。若做自适应缩短轮询（临近提醒时缩间隔）：要么必须仍以 30s 封顶（否则较长睡眠会漏掉入站新到的更近提醒＝比现状更差），封顶后收益仅「未来 30s 内的提醒早几秒发」，对待办提醒无实感价值，却引入「下一个边界」计算与新到提醒的正确性隐患。按 AGENTS「简约至上／不过度设计」，维持固定 30s。

独立核查结论（逐条落代码）：

- **周期实例每次到点均提醒（含跨日）＝由 01 覆盖，认可**。新 id 路径：`completeRecurring`→`applyChange`（完成源行落库、状态门排除）＋`insertTodo(buildNextInstance)`（后继新 id、`reminderAt=shiftInstant`，落库），后继是全新 `(id,reminder_at)` 投递键。同 id 路径：`checkInHabit`／`advanceOverdueRecurring` 保留 id、`reminder_at` 经 `shiftInstant` 位移。同 id 边界安全——`reminder_deliveries` 虽留旧键 `(id,first_at)`，但域层查的是**精确**新键 `(id,next_at)`（`reminder.rs:84`），旧键匹配不上故照发；且 `shift≥1 天` 保证两串永不相撞。跨日在域层是纯数值比较非问题，`parse_instant`（`ics.rs:410`）能读 `.000Z`。
- **入站同步重排＝被轮询架构结构性化解，认可**。入站仅经 `applyRemoteChange`→`applyRemoteUpsert`/`applyRemoteDelete` 两条路（`sync-engine.ts:151`），两者均落 SQLite（`persist`→`repository.save`→`nativeCommands.saveTodo`→`TodoDb.save`；`forget`→`TodoDb.delete`），无「只改内存 store 不落库」的入站路径。调度线程经 `app.state::<TodoDb>()` 读同一连接（Mutex 串行），远端变更落库后下一轮现算 gating，无需重启或本地再操作。
