# 晨间摘要

- 级别：简化
- 状态：完成

## 需求（产品）

- 目标与场景：每日早晨一条汇总通知：今日到期 / 逾期 / 我的一天概览。
- 范围（做 / 不做）：做 定时聚合通知（读统计数据源）；不做 内容个性化。
- 验收标准（逐条可检查）：
  - [ ] 每日定时一条，三段内容与应用内数据一致；无任务时按空态文案处理。

### 编排者并入项（来自 提醒通知/05 UI/UX 阶段，待本任务评估）

**05/06 边界与早晨双通知**：勿扰时段（05）结束时会补推一条「N 条提醒待查看」摘要，而晨间摘要（本任务）也在早晨定时发一条——两者时刻可能相近（如勿扰 8:00 结束、摘要 8:00）。05 已把两者定为正交（事件驱动的被压提醒 vs 定时驱动的统计概览），不合并、不互相替代。

本子任务落地时请评估并定案：① 晨间摘要本身是否受勿扰门控（勿扰期内摘要静默暂存还是照发）；② 05 的补推是否可并入晨间摘要以减少早晨通知数。05 已保证补推走 01 的同一发送判定、可被本任务协调。

补充验收标准：

- [ ] 早晨勿扰结束补推与晨间摘要的关系有明确结论（受门控/合并/分离各择其一并说明），不产生用户困惑的重复早晨通知。

## 规格（UI/UX）

先通读了 01/03/04/05 的实现记录，本规格接其架构：桌面提醒由 Rust 后台线程每 30s 轮询 SQLite、按纯规则现算「该发什么」、`reminder_deliveries` 按键（真实 `reminderAt` ISO 串或合成键如 04 的 `renag:<unix>`）每键只发一次（01/04）；03 在设置面板建了「提醒」`fieldset`（重催开关 + 勿扰 + 四档 snooze 时长）＋应用内快捷条；04 建了 `reminder_prefs.rs`（Rust 从 `settings.json` 读提醒偏好，模块文档已为 06「晨间时刻」预留接入位）；05 在 `poll_once`/`show()` 发送判定前落了一道勿扰门（同时门控首次提醒与重催），并把「05/06 边界」的定案留给本任务（05 编排者裁决 2026-07-24 已倾向「分离」、明确交 06 定案）。

**本任务与 04/05 同型——「引擎为主、界面只露一角」的简化任务。** 晨间摘要是一种**定时聚合的通知行为**：界面上只露出两处——① 设置面板「提醒」fieldset 里的一个**摘要开关 + 一个 `type="time"` 推送时刻输入 + 一句人话说明（含勿扰交互提示）**；② 每日定时发出的**摘要通知文案**（纯文本计数概览）。列表侧零改动、无新增组件；其余全是 Rust 侧的「每日定时算计数、发一条、每天只发一次」调度（数据模型归开发，第 5 节点明其语义与接缝）。

### 0. 四个关键判断（正面表态）

| 议题 | 判断 |
|------|------|
| **a) 摘要开关 + 时刻** | **摘要整体开关（默认关）＋ 一个 `type="time"` 推送时刻（默认 `09:00`），开关开启后才展开时刻输入。** 放进 03 已建的「提醒」`fieldset`，与 renag/quiet 同属「通知何时发」的顶层组、置于勿扰块之后、snooze 说明句之前。默认**关**：与 `renagOverdue`/`quietHoursEnabled`/`rolloverOverdue`「擅自做有后果的事＝一种改动，默认关」同 philosophy——晨间摘要是一条**每天新增**的系统通知，出厂即每早弹一条属未经用户请求的打扰，保守默认关、用户显式开启。默认开/关是产品裁决点，本规格取关并交编排者知悉（第 6 节点 1）。理由见第 1 节。 |
| **b) 摘要时刻＝「早晨」锚点，本任务不跨接** | **是**——`reminder.summary.time`（默认 `09:00`）就是全应用唯一的「早晨」锚点偏好；03 的「明天」snooze 常量（`TOMORROW_HOUR=9`）注释已注明「待 默认提醒时间（外观与设置/02）与 晨间摘要时间（本任务）落地后，『明天』应复用晨间时刻以免双份漂移」。**但本任务不跨接**：03 的接线条件是**两者都落地**，而 外观与设置/02 尚未落地；故本任务只**建立**该锚点偏好、默认取 `09:00`（与现有 `TOMORROW_HOUR=9` 重合、当下零漂移），**不改** `ReminderSnoozeBar.vue` 的常量、不重连「明天」——跨接留作已被 03/settings.ts 记录在案的接线点，待 外观与设置/02 落地时统一收敛。理由见第 3 节。 |

| **d)「我的一天」段本任务降级** | **本任务只**引用**计数、不建「我的一天」视图本身；而其数据源（视图与统计/06）尚未落地（状态＝需求），故本任务的「我的一天」段先降级为「缺省不显」。** 摘要机制留出该段的槽位与读取接缝；视图与统计/06 的验收标准已自带「今日清单数据可被晨间摘要读取（联动接口就位）」，届时由其把计数填进同一 body（接缝＝一次计数读取、无界面改动）。当下 body 只呈现有数据源的两段（今日到期 / 逾期）。理由见第 2 节。 |

### 1. 摘要开关 + 时刻（设置面板，五项齐全）

**位置**：`src/App.vue` 设置面板「提醒」`fieldset` 内、05 的勿扰窗口块（`<template v-if="settingsStore.quietHoursEnabled">…</template>`，现于 line 618–659）**之后**、03 的 `以下时长会作为"稍后提醒"的快捷选项。` 说明句（现 line 660）**之前**。理由：renag（多发）、quiet（压住）、summary（每日定时汇总）都是「**通知何时发**」的投递行为，三者相邻成一组更好读；其下的四档 snooze 是「快捷条的快捷选项」子组，保持完整。摘要作为该顶层组的第三行（renag → quiet → **summary**）。**不另开 fieldset、不加 `isDesktop` 门**——与该组其余项同理（提醒行为偏好、非桌面能力，移动端本地通知落地后复用；同 renag/quiet 的既有注释）。

**结构与布局**（`fieldset「提醒」` 内新增两块，逐字复用既有设置行 / 05 时刻输入形状）：

1. **摘要开关行**（单个复选框行，与 `renagOverdue`/`quietHoursEnabled` 行同型、逐字复用类串）：
   - 外层 `<label class="mb-2 flex min-h-10 cursor-pointer items-center gap-3 rounded-lg px-3 py-2 hover:bg-slate-50 dark:hover:bg-slate-900">`。
   - `<input type="checkbox" :checked="settingsStore.morningSummaryEnabled" @change="settingsStore.setMorningSummaryEnabled(($event.target as HTMLInputElement).checked)">`。
   - 双行 `span`（`min-w-0`）：
     - 标题（`block text-sm font-medium text-slate-800 dark:text-slate-100`）：`晨间摘要`。
     - 说明（`block text-xs text-slate-500 dark:text-slate-400`）：`开启后，每天早晨推送一条今日概览通知：今日到期与逾期的任务数量。`——默认关，说明句是用户发现并理解此行为的入口。（「我的一天」段待 视图与统计/06 落地后并入，见第 2/6 节；说明句此刻只述已有的两段，避免描述churn。）

2. **推送时刻输入块**（`v-if="settingsStore.morningSummaryEnabled"`，渐进展开——关时不占视觉重量，与 05 勿扰窗口块同型）：
   - 容器：`<div class="mb-2 px-3">`（`px-3` 与设置行左内边距对齐；单个输入无需 flex 列布局）。
   - 标签：`<label for="morning-summary-time" class="mb-1 block text-xs font-medium text-slate-500 dark:text-slate-400">推送时间</label>`（＝ 05 时刻列标签 / `TodoFields.vue` `LABEL_CLASS` 同款）。
   - 输入：`<input id="morning-summary-time" type="time" :value="settingsStore.morningSummaryTime" aria-describedby="morning-summary-desc" class="min-h-11 w-full rounded-lg border-0 bg-slate-100 px-3 py-2 text-base focus:ring-2 focus:ring-sky-500 sm:text-sm dark:bg-slate-900" @change="settingsStore.setMorningSummaryTime(($event.target as HTMLInputElement).value)">`（**类串＝ 05 勿扰起止输入所用 `CONTROL_CLASS`（全应用输入基线），内联在 `.vue` 模板，不引 `.ts` 常量**，避 UnoCSS 不扫 `.ts` 陷阱；`w-full` 与既有 sync 服务端地址 / 勿扰时刻输入同，不新造 max-width 令牌）。
   - **人话说明句**（`id="morning-summary-desc"`，`<p class="mb-0 px-3 text-xs text-slate-500 dark:text-slate-400">`，文案由 App.vue `<script setup>` 内 computed `morningSummaryDescription` 现算，非 `.ts`）：
     - 基础：`每天 <时刻> 推送今日概览。`（`<时刻>` ＝ `morningSummaryTime`）。
     - **勿扰交互提示（答第 0 节 c 的 05/06 边界，让门控对用户可见）**：当 `quietHoursEnabled` ∧ 勿扰窗口有效（起止均非空且不相等）∧ **该推送时刻落在勿扰窗口内**时，追加 ` 该时间在勿扰时段内，摘要将在勿扰结束（<结束时刻>）后推送。`（`<结束时刻>` ＝ `quietHoursEnd`）。这把「摘要受勿扰门控、会顺延到勿扰结束」直接讲给用户，正面预防「早晨双通知的困惑」（补充验收）。
     - 「是否落在勿扰窗内」的判定**复用** App.vue 既有 `quietMinutes(value)` 解析与跨午夜窗口判定式（现于 `quietSilentNow`：`start > end ? (m >= start || m < end) : (m >= start && m < end)`），只把 `now` 换成**摘要时刻的分钟数**——这是配置时刻 vs 配置窗口的纯派生、与「当前时刻」无关，**不需 tick**（不同于 05 的 `quietSilentNow` 需 60s tick）。

**存储**：摘要开关走既有 `saveBooleanPreference`/`loadBooleanPreference`（键 `reminder.summary.enabled`，默认 `false`）；推送时刻走既有 `saveStringPreference`/`loadStringPreference`（`src/lib/settings-storage.ts`，含浏览器回退，键 `reminder.summary.time`，默认 `"09:00"`——即使开关关也存默认值，开启时输入即显 `09:00`）。在 `useSettingsStore`（`src/stores/settings.ts`）按 `quietHoursEnabled`（bool）＋ `quietHoursStart`（字符串，共用私有 `persistQuietPreference` 先例）同一模式加 2 个 ref（`morningSummaryEnabled` 默认 `false`、`morningSummaryTime` 默认 `"09:00"`）＋ 2 个具名 setter（`setMorningSummaryEnabled` 走 `saveBooleanPreference`；`setMorningSummaryTime` 走 `saveStringPreference`，失败均沿用既有 `persistenceError` 通道）＋ bootstrap 读取 ＋ catch 兜底默认 ＋ 导出 ＋ 诊断快照。

**状态**：
- 默认：摘要关 → 只见开关行（复选框未勾选），时刻输入块 `v-if` 不渲染。
- 悬停：开关行 `hover:bg-slate-50 dark:hover:bg-slate-900`（沿用既有设置行）；时刻输入无独立 hover 态。
- 聚焦：复选框走浏览器默认焦点框（同组其余项）；`type="time"` 输入走 `focus:ring-2 focus:ring-sky-500`（＝ `CONTROL_CLASS` 既有输入聚焦式，与全应用输入及 05 勿扰输入一致；注：DESIGN `focus-ring` shortcut 现有失效缺陷已转 `外观与设置/04`，既有输入本就用 raw `focus:ring-2`，本规格随之、不旁路，修复后统一收敛）。
- 加载：无异步加载态——开关/时刻即时落库（同 `setQuietHoursEnabled`/`setQuietHoursStart`），说明句为本地纯派生、同步可得。
- 空数据：不适用于本设置块（单开关 + 单时刻）。「无任何任务时是否发/发什么」是**通知侧**的空态，见第 2 节（定案：三段计数全为 0 时当日不发）。
- 错误：持久化失败沿用既有 `persistenceError` 通道（面板顶部主题行 `aria-live="polite"` 处），不新增错误 UI、不新增 live region。

**暗色适配**（与浅色成对，全部既有类）：开关行 `dark:hover:bg-slate-900`、`dark:text-slate-100`、`dark:text-slate-400`；时刻输入 `dark:bg-slate-900`（＝ `CONTROL_CLASS` 暗色对）；标签/说明 `dark:text-slate-400`。无新增色值。

**移动端适配**：时刻输入 `w-full`、`min-h-11`（≥44px 触控），无固定宽高、绝不横向滚动（DESIGN 硬性）；`type="time"` 在移动端唤起原生时间选择器（DESIGN「语义化 type 唤起正确键盘」）；开关行 `min-h-10` 沿用既有设置项基线；文案自然换行不截断；320px 下不越界。

**可访问性**：
- 分组归属既有 `fieldset`+`legend「提醒」`（`aria-labelledby="reminder-settings-heading"`），读屏进组报出组名。
- 摘要开关关联可见 `label`（双行文字＝可访问名＋说明），键盘可达、空格切换。
- `type="time"` 关联可见 `<label for="morning-summary-time">推送时间`（＝可访问名），并 `aria-describedby="morning-summary-desc"` 指向人话说明——读屏聚焦输入即读出「每天 09:00 推送今日概览。（+ 勿扰提示）」，勿扰顺延含义对读屏可达、不单靠视觉。
- 勿扰交互提示不靠颜色/图形单传，全由文字说明。
- **不新增第二个 live region**：说明句为静态文本（经 `aria-describedby` 关联，非 `aria-live`）；持久化错误复用既有主题行 polite 区。页面级 `pickPageAlert` 的唯一 `role="status"` 区不碰（03 建立，本任务不涉及应用内即时反馈）。

### 2. 摘要通知的呈现（计数概览，唯一的「输出」表面）

摘要的用户可见输出**只有系统通知**（文案由 Rust 侧生成，属 01 已确立的「文案标注、非数据标注」路径，不动契约、无样式令牌，OS 渲染）。

**三段内容 → 计数式 body（不列标题）**：

| 段 | 语义 | 数据源（第 5 节详列） | 本任务状态 |
|----|------|----------------------|-----------|
| 今日到期 | 截止日＝今日、未完成、未归档 的任务数 | SQLite 现算（Rust 侧，同 04 的 `dueDate` 本地日读法） | ✅ 有源，本任务呈现 |
| 逾期 | 截止日＜今日、未完成、未归档 的任务数 | SQLite 现算（＝ 04 renag 的逾期锚点集口径） | ✅ 有源，本任务呈现 |
| 我的一天 | 今日清单（挑选出的今日执行项）计数 | 视图与统计/06 的今日清单数据源 | ⏳ 源未落地，本任务降级缺省不显 |

**文案定案**（纯文本，dev 可微调措辞，OS 渲染）：
- 标题：`今日待办概览`。
- 正文：把**计数非零**的段以 ` · ` 连接，每段 `<标签> <N> 条`，末尾句号。示例：
  - 今日到期 3、逾期 2 → `今日到期 3 条 · 逾期 2 条。`
  - 今日到期 3、逾期 0 → `今日到期 3 条。`（零段略去，报忧不报「无忧」，body 更紧）
  - 今日到期 0、逾期 2 → `逾期 2 条。`
  - 视图与统计/06 落地后 → `今日到期 3 条 · 逾期 2 条 · 我的一天 5 条。`（第三段接缝就位即自动并入，无界面改动）。

**空态定案（补充需求点名「无任务时按空态文案处理」）**：
- **三段计数全为 0（今日无到期、无逾期，且我的一天段无源或为 0）→ 当日不发通知（静默）。** 理由：一条「今天没有到期或逾期」的空摘要每早重复弹＝纯噪音，违 DESIGN 原则 1「低摩擦/克制」与本仓一贯的噪音规避；摘要的价值是**浮现需关注项**，无可关注项时沉默即正确信息。
- 这**refine 而非违背** 05 的边界表述「06 每天定时发（即便无提醒被压）」：05 那句的对比对象是「05 补推＝事件驱动、仅有被压提醒才发」vs「06＝定时驱动、不以『是否有被压提醒』为门」——讲的是**触发机制**是定时而非事件，并未承诺「用户零任务时也必发一条空摘要」。故「计数全 0 当日不发」与 05 表格无冲突：06 仍是定时触发（不 gate 在「是否有被压提醒」上），只是定时触发那一刻若确无可报内容则不弹。
- 非全零时按上面文案发（略去零段）。

**列标题属可选增强、非默认**（交开发裁量，非验收项）：如产品要在计数后附 1–2 个任务标题（`…：<标题1>、<标题2> 等`），需权衡 OS 通知正文长度与锁屏隐私（内容泄露）；本规格默认**只计数**（范围「不做内容个性化」＝不列具体任务内容），列标题超范围，不做。

**列表侧零改动**：摘要只读统计、不改任何任务视觉状态；逾期任务的红色到期徽标（`dueDateTone`，`src/lib/dueDate.ts`）是「逾期」的既有视觉承载，与摘要计数**正交**、天然一致，不新增徽标、不扩展 `ReminderSnoozeBar`。

### 3. 摘要时刻＝「早晨」锚点（与别处统一的定案）

- **`reminder.summary.time`（默认 `09:00`）是全应用唯一的「早晨」锚点偏好。** 03 的「明天」snooze 走 `TOMORROW_HOUR=9` 常量，其注释（`ReminderSnoozeBar.vue` 与 `settings.ts` 均记）明言「待 默认提醒时间（外观与设置/02）与 晨间摘要时间（本任务）落地后，『明天』复用晨间时刻以免双份漂移」。本任务**落地了晨间时刻**这一半。
- **本任务不跨接「明天」**：03 记录的接线条件是**两项都落地**，而 外观与设置/02（默认提醒时间）**尚未落地**；此刻把「明天」改去读 `reminder.summary.time` 会：① 触碰 03 的 `ReminderSnoozeBar.vue` 常量（超本任务「晨间摘要」范围、手术式改动原则）；② 只接了一半（默认提醒时间那半没有源）。故本任务**只建立锚点偏好**，默认 `09:00` 与现有 `TOMORROW_HOUR=9` 重合、当下零可见漂移；真正的跨接（令「明天」及默认提醒时间读同一锚点）留作**已被 03/settings.ts 记录在案的接线点**，待 外观与设置/02 落地时一并收敛。第 6 节点 2 登记此接缝，交编排者知悉。
- 结论：晨间摘要时刻**就是**那个「早晨」锚点、应与别处统一，但**统一动作**（改「明天」）不在本任务、留接线点；本任务不预埋跨读、不改既有常量，避免半接的双份真相。

### 4. 05/06 边界定案（【并入项】，本任务正面定清）

05 已把「晨间摘要是否受勿扰门控 / 补推是否并入晨间摘要」交本任务定案（05 编排者裁决 2026-07-24 点 3 已倾向分离、明确「属 06 范围」）。逐条定案如下：

#### ① 晨间摘要**受勿扰门控**（定案：受门控）

- **结论**：晨间摘要与首次提醒、重催一样**受 05 的勿扰门门控**——若配置的推送时刻落在启用中的勿扰窗口内，摘要**静默暂存、顺延到勿扰结束后补推**，走 05 在 `poll_once`/`show()` 前的**同一道发送判定**。
- **理由（必须受门控，否则 05 破功）**：05 的验收标准是「窗口内零通知」。若晨间摘要**不**受门控，用户把摘要设在 `07:00`、勿扰 `22:00–08:00`，则 `07:00` 会弹一条摘要——**直接违反 05「窗口内零通知」**。故门控是正确性要求，非取舍。摘要就是一条系统通知，勿扰的语义是窗口内不发任何通知，理应一并压住。
- **顺延后计数按补发时刻现算**：摘要在其定时时刻落入窗口→暂存；勿扰结束后的下一轮轮询（`now` 已出窗、门放行）才真正发出，此时**重新现算**今日到期/逾期计数，故补发的摘要反映**补发时刻**的最新状态（更准）。开发在实发那一轮取计数即可。
- 设置面板的说明句（第 1 节）在「摘要时刻落在勿扰窗内」时已提示「摘要将在勿扰结束（<结束>）后推送」，让门控对用户可见、不困惑。

#### ② 05 补推与 06 晨间摘要**保持分离、不合并**（定案：分离）

- **结论**：05 的勿扰补推（`勿扰时段已结束 · N 条提醒`）与 06 的晨间摘要（`今日待办概览 · 计数`）**各发一条独立通知，不合并、不互相替代**。确认 05 裁决的倾向为最终定案。
- **理由**：
  - **信息不同、心智模型不同**：05 补推＝「你静默期间**被压住的那几条具体提醒**」（事件驱动、逐条可在应用内快捷条处理）；06 摘要＝「今日**统计概览**」（定时驱动、计数）。合并会把两种心智糅进一条，措辞尴尬（`N 条提醒待查看 + 今日到期 M 条 · 逾期 K 条`），且降低各自可读性。
  - **只是**有时**时刻接近，不是恒等**：勿扰 `08:00` 结束、摘要设 `09:00` 时二者差一小时，合并要么把 `08:00` 补推按住一小时（延误「你错过了这些」的及时性）、要么把摘要提早发（违背用户设的时刻）——都需要**脆弱的近同时性特判逻辑**。保持分离最简单、各司一职、最稳。
  - **不构成「重复」**：二者**内容不重叠**——补推报「N 条**提醒**待查看」（提醒告警的计数），摘要报「今日到期/逾期**任务**数」（任务的统计口径）。即便同一任务同时出现在两者（一条今日到期、其提醒被压），补推说的是「有一条提醒等你看」、摘要说的是「今天有 3 条到期」，**粒度与目的不同**，非重复。
- **反双通知困惑的保障（答补充验收「不产生用户困惑的重复早晨通知」）**：
  - 二者永不承载**相同文案**（一为提醒告警计数、一为任务统计计数），故不是「重复」。
  - 因 ① 摘要也受勿扰门控：当摘要时刻落在勿扰窗内，摘要与 05 补推**同在勿扰结束那一轮**释放——此时用户早晨收到最多两条（补推「你静默期间错过的这些提醒」＋摘要「今日概览」），信息互补而非重复。开发**可选**让二者在同一轮有序发出（补推在前、摘要在后）以免同刻双震，但**仍是两条**、不合并。
  - 当摘要时刻在勿扰窗外（如勿扰 `22:00–08:00`、摘要 `09:00`）：补推 `08:00` 单独发、摘要 `09:00` 单独发，相隔一小时、信息不同，天然不撞。

（对应补充验收标准：早晨勿扰结束补推与晨间摘要的关系＝**摘要受门控 + 二者分离**，理由如上，不产生重复早晨通知。）

## 实现记录（开发）

### 架构决策一：摘要触发＝domain 纯规则（`crates/domain/src/summary.rs`，新增）

- **与 01/04 并列的第三条判定分支**：新增 `due_morning_summary(todos, delivered, prefs, now_unix, zone_offset_seconds) -> Option<MorningSummary>`——**定时聚合**，不像 `due_reminders`/`due_renags` 锚在某任务的时刻，而是每天到点算一次计数。返回 `None` 的四条闸（按裁决点 1/4/5 逐条）：① 开关关；② 未到时刻（`now` 的本地 time-of-day < 摘要时刻）；③ 当天已发（合成键在 `delivered` 内）；④ 空态（三段计数全 0）。四条任一成立即当轮不发。
- **每日一次去重＝合成键 `summary:<本地YYYY-MM-DD>`**（`SUMMARY_KEY_PREFIX="summary:"`，todo_id 定值 `SUMMARY_TODO_ID="morning-summary"`）：与 01 真实 `reminderAt`（ISO，年份数字起头）、04 `renag:<unix>` 前缀命名空间**均不碰撞**，三分支**共读同一 `reminder_deliveries` 表、各看各键**，沿用 01「每键一次」故无新表、无契约。键是**本地日期**，故跨日自动换新键（裁决点：跨日重置）；停机跨多日重启只补**当日**一条（当日键未记、昨日键的日期已过不再算），不 burst——同 04 `latest_renag_offset` 精神。
- **计数口径＝列表徽标（`src/lib/dueDate.ts`）**：`summary_counts(todos, now, offset)`——open ∧ 未归档 ∧ `dueDate` 本地日＝今日→`due_today`、＜今日→`overdue`（本地日号 `days_from_civil(parse_date(dueDate))` vs `(now+offset).div_euclid(86400)`，精确等价前端 `dayDifference<0`/`==0`）。**不排除依赖锁定**（有意区别于 renag 发通知时的更严 gating）——摘要答「今天盘子里有什么」＝用户在列表看到的红/琥珀徽标计数，`dueDateTone`/`isOverdue` 本就不看锁。completed/archived/无坏 `dueDate` 不计。
- **body 文案**（`format_summary_body`，纯文本 OS 渲染，无令牌）：非零段以 ` · ` 连接、每段 `<标签> <N> 条`、末尾句号；零段略去（`今日到期 3、逾期 0 → 今日到期 3 条。`）。标题 `今日待办概览`。仅在 counts 非空时调用，body 恒非空。
- **「我的一天」接缝（裁决点 3，降级缺省不显）**：`SummaryCounts.my_day: Option<i64>` 由私有 `my_day_count() -> None` 供给（视图与统计/06 未落地）。当下第三段不显；**视图与统计/06 落地怎么填**：把该函数改为返回今日清单计数 `Some(n)`（其验收已含「今日清单数据可被晨间摘要读取」），`format_summary_body` 的 `if let Some(n) if n>0` 分支即自动把 `· 我的一天 N 条` 并入同一 body——接缝＝一次计数读取、无界面改动、无契约新字段。单测 `the_my_day_segment_joins_the_body_once_its_source_lands` 已锁定填入后的 body 形状，不预埋假计数。
- **`"HH:mm"` 解析单源**：摘要时刻复用 `crate::quiet::parse_hm`（本次提为 `pub(crate)`），与勿扰窗同一严格解析，不新写第二份 `"HH:mm"` 解析漂移（同 05 复用 `ics::instant_unix_seconds` 的理由）。不可解析的时刻（手改 settings）→ 摘要不可调度→静默，不猜时刻发。

### 架构决策二：勿扰门控 + 分离不合并（裁决点 5，`reminder_scheduler.rs`）

- **受勿扰门控（①，正确性硬要求）**：`poll_once` 在 due reminders/renags 批之后**单独**处理摘要——`due_morning_summary` 每轮从 `db.list()` 现算计数，经**独立单项** `plan_quiet_delivery([summary.scheduled_unix], window, now, offset)` 骑 05 **同一勿扰门与同一 `show()` 路径**：窗内→plan 空→不发不记投递（暂存），窗外→发一条独立 toast + 记 `summary:<date>` 键。`window` 复用批处理已读的同一个（开关开才读）。若摘要不受门控，用户把摘要设在勿扰窗内会违反 05「窗口内零通知」——故门控是正确性而非取舍。
- **补发按补发时刻现算（①）**：暂存的摘要不记键，故勿扰结束后的轮次 `due_morning_summary` 再算——计数取**该轮** `db.list()`（补发时刻的最新状态），非原时刻。单测 `a_summary_scheduled_inside_the_quiet_window_is_held_until_it_ends` 组合 `due_morning_summary`+`plan_quiet_delivery` 锁定：07:00（窗内）held、08:00（窗末）以「窗内暂存 + 新逾期任务」的最新 counts 发出。
- **分离不合并（②）**：摘要走**独立单项** plan，`held.len()` 永为 0/1、**永不进 `summarize`**（05 折叠摘要要 `held.len()>=2`），故 06 摘要绝不被折进 05 补推——二者各发一条独立通知。排在 reminder/renag 批之后＝补推在前、摘要在后（05 建议的有序发出），仍是两条。
- 关开关则该轮 `due_morning_summary` 返回 `None`、不进摘要计算，下一轮即停。
