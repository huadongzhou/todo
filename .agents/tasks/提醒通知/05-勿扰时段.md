# 勿扰时段

- 级别：简化
- 状态：完成

## 需求（产品）

- 目标与场景：设定静默窗口（如 22:00–8:00），期间提醒暂存不打扰，结束后补推。
- 范围（做 / 不做）：做 窗口设置、暂存队列、补推；重催在勿扰期同样静默暂存。
- 验收标准（逐条可检查）：
  - [ ] 窗口内零通知，结束后暂存提醒统一补推且不重复。

## 规格（UI/UX）

先通读了 01/03/04 的实现记录，本规格接其架构：桌面提醒由 Rust 后台线程每 30s 轮询 SQLite、按纯规则现算「该发什么」、`reminder_deliveries` 按 `(todo_id, reminder_at)` 每键只发一次（01）；03 在设置面板加了「提醒」`fieldset`（重催开关 + 四档 snooze 时长开关）＋应用内快捷条；04 建了 `reminder_prefs.rs`（Rust 从 `settings.json` 读提醒偏好）并**在 01 的 `poll_once`/`show()` 发送判定前留好了「发送前加勿扰门」的接缝**——重催与首次提醒都骑同一发送路径。

**本任务的 UI 表面同样很小——「引擎为主、界面只露一角」的简化任务。** 勿扰时段是一种**通知门控行为**：界面上只露出三处——① 设置面板「提醒」fieldset 里的一个**勿扰开关 + 一对起止时刻输入 + 一句人话窗口说明**；② 静默中的一行**面板内状态提示**（可选，本规格判定要做，见第 4 节）；③ 窗口结束后的**补推通知文案**（合并摘要）。其余全是 Rust 侧的「发送前判勿扰、窗口后补发」调度（数据模型归开发，第 5 节点明其接缝语义）。列表侧零改动、无新增组件。

### 0. 三个关键判断（正面表态）

| 议题 | 判断 |
|------|------|
| **a) 窗口设置形态** | **勿扰整体开关（默认关）＋ 一对 `type="time"` 起止输入（默认 22:00–08:00），窗口开启后才展开输入。** 跨午夜是常态，靠**一句现算的人话说明**消歧——「每天 22:00 到**次日** 08:00 静默」，`次日` 二字点破「晚上到早上」而非「早上到晚上的 22 小时」。默认**关**：勿扰会压住系统通知＝有后果的改动，与 `rolloverOverdue`/`renagOverdue`「擅自做有后果的事＝改动」同philosophy，保守默认关；用户开启时窗口默认 22:00–08:00。理由见第 1 节。 |
| **b) 补推的呈现** | **合并成一条摘要，不逐条刷屏。** 窗口结束后，暂存 ≥2 条时**只弹一条**摘要通知「勿扰时段已结束 · N 条提醒」；恰好 1 条时按其原文案单发（一条不必摘要）。这既满足验收「统一补推」，又避免 8:00 一次弹 5 条。「**不重复**」＝每条暂存提醒在整个「窗口内静默 → 窗口后补发」过程中**恰好投递一次**：勿扰期到点不发也**不记投递**，窗口后补发（单发或计入摘要）时**才记**——靠 01 `reminder_deliveries` 的「有记录=已发」天然表达，无需新表。合并 vs 逐条属产品裁决点，本规格取合并、并把取舍交编排者知悉（第 7 节）。理由见第 2 节。 |
| **c) 勿扰状态反馈** | **做，但只在设置面板内、纯文本一行。** 勿扰的本质是「悄悄压住通知」，无任何反馈时用户会疑惑「怎么没提醒」；故在窗口说明句旁给一行「当前正处于静默中，提醒将在 08:00 后补推」。只在面板内、纯文本、非 live region、无新令牌，成本极低却正面回答「用户怎么知道在勿扰期」。**不做**应用内常驻徽标/图标（那是背景行为，常驻＝噪音）。见第 4 节。 |

### 1. 窗口设置形态（设置面板，五项齐全）

**位置**：`src/App.vue` 设置面板「提醒」`fieldset` 内、04 的重催开关行**之后**、03 的 `以下时长会作为"稍后提醒"的快捷选项。` 说明句**之前**。理由：重催（多发通知）与勿扰（压住通知）都是「**通知何时发**」的投递门控行为，二者相邻成一组更好读；其下的四档 snooze 是「快捷条的快捷选项」子组，保持完整。**不另开 fieldset、不加 `isDesktop` 门**——与该组其余项同理（提醒行为偏好，非桌面能力，移动端本地通知落地后复用）。

**结构与布局**（`fieldset「提醒」` 内新增两块，逐字复用既有设置行形状）：

1. **勿扰开关行**（单个复选框行，与 `renagOverdue`/`rolloverOverdue` 行同型、逐字复用类串）：
   - 外层 `<label class="mb-2 flex min-h-10 cursor-pointer items-center gap-3 rounded-lg px-3 py-2 hover:bg-slate-50 dark:hover:bg-slate-900">`。
   - `<input type="checkbox" :checked="settingsStore.quietHoursEnabled" @change="settingsStore.setQuietHoursEnabled(($event.target as HTMLInputElement).checked)">`。
   - 双行 `span`（`min-w-0`）：
     - 标题（`block text-sm font-medium text-slate-800 dark:text-slate-100`）：`勿扰时段`。
     - 说明（`block text-xs text-slate-500 dark:text-slate-400`）：`开启后，静默时段内的提醒暂存不打扰，时段结束后一并补推，不会丢失。`——默认关，说明句是用户发现并理解「暂存不丢失」的入口。

2. **窗口输入块**（`v-if="settingsStore.quietHoursEnabled"`，渐进展开——关时不占视觉重量）：
   - 容器：`<div class="mb-2 flex flex-col gap-3 px-3 sm:flex-row sm:gap-4">`（窄屏纵向堆叠、`sm:` 起横排；`px-3` 与设置行左内边距对齐）。

     - 列 1：`<label for="quiet-hours-start" class="mb-1 block text-xs font-medium text-slate-500 dark:text-slate-400">开始</label>` ＋ `<input id="quiet-hours-start" type="time" :value="settingsStore.quietHoursStart" @change="…setQuietHoursStart(…value)" aria-describedby="quiet-hours-window-desc" class="min-h-11 w-full rounded-lg border-0 bg-slate-100 px-3 py-2 text-base focus:ring-2 focus:ring-sky-500 sm:text-sm dark:bg-slate-900">`（**类串＝ `TodoFields.vue` 的 `CONTROL_CLASS`，即全应用输入基线**，此处内联在 `.vue` 模板，不引 `.ts` 常量，避 UnoCSS 不扫 `.ts` 陷阱）。
     - 列 2：同上，`开始`→`结束`、`start`→`end`、`quietHoursStart`→`quietHoursEnd`、id `quiet-hours-end`。
   - **人话窗口说明句**（消歧核心，`id="quiet-hours-window-desc"`，`<p class="mb-0 px-3 text-xs text-slate-500 dark:text-slate-400">`，文案由 App.vue `<script setup>` 内 computed 现算，非 `.ts`）：
     - 跨午夜（`start > end`，如 22:00 / 08:00）：`每天 22:00 到次日 08:00 静默。`——`次日` 点破跨午夜。
     - 同日窗口（`start < end`，如 13:00 / 14:00）：`每天 13:00 到 14:00 静默。`（无「次日」）。
     - `start == end` 或任一为空：`开始与结束时间相同，当前不会静默。`（空窗口，见第 5 节「空/失效窗口＝不静默」的 fail-open 语义）。
   - 说明句后可续接第 4 节的静默中状态短语（同一 `<p>` 内条件追加，见第 4 节）。

**存储**：勿扰开关走既有 `saveBooleanPreference`/`loadBooleanPreference`（键 `reminder.quiet.enabled`，默认 `false`）；起止时刻走既有 `saveStringPreference`/`loadStringPreference`（`src/lib/settings-storage.ts` 已提供，含浏览器回退，键 `reminder.quiet.start` / `reminder.quiet.end`，默认 `"22:00"` / `"08:00"`——即使开关关也存默认值，开启时输入即显 22:00–08:00）。在 `useSettingsStore`（`src/stores/settings.ts`）按 `renagOverdue`（bool）与既有字符串偏好同一模式加 3 个 ref + 3 个具名 setter（可共用一个私有 `persistQuietPreference` 免三份 try/catch 漂移，同 `persistSnoozePreference` 先例）+ bootstrap 读取 + catch 兜底默认 + 导出 + 诊断快照。

**状态**：
- 默认：勿扰关 → 只见开关行（复选框未勾选），窗口输入块 `v-if` 不渲染。
- 悬停：开关行 `hover:bg-slate-50 dark:hover:bg-slate-900`（沿用既有设置行）；时刻输入无独立 hover 态。
- 聚焦：复选框走浏览器默认焦点框（同「任务」「提醒」组其余项）；`type="time"` 输入走 `focus:ring-2 focus:ring-sky-500`（＝ `CONTROL_CLASS` 既有输入聚焦式，与全应用输入一致；注：DESIGN `focus-ring` shortcut 现有失效缺陷已转 `外观与设置/04`，既有输入本就用 raw `focus:ring-2`，本规格随之、不旁路，修复后统一收敛）。

### 2. 补推的呈现（合并摘要，唯一的「输出」表面）

窗口结束后暂存提醒的用户可见输出**只有系统通知**（文案由 Rust 侧生成，属 01 已确立的「文案标注、非数据标注」路径，不动契约）。

**合并规则（防刷屏）**：以「窗口结束后第一轮轮询」一次性收拢该批暂存提醒（30s 轮询下，窗口结束瞬间所有被压住的提醒同刻变为「可发」，故单轮即抓齐整批，见第 5 节）：

| 该批暂存条数 | 行为 | 通知文案 |
|------|------|---------|
| 0 | 无（窗口内无提醒到点） | —— |
| 恰 1 | 单发该提醒的**原文案** | 该提醒本来的首次提醒 / 重催文案 |
| ≥2 | **只发一条摘要** | 标题 `勿扰时段已结束`；正文 `勿扰期间有 N 条提醒待查看。` |

- **摘要正文取计数式**（`N 条提醒待查看`）为简化底线，稳健、无越界风险；如需列前几个标题（`…：<标题1>、<标题2> 等`）属可选增强，交开发按 OS 通知正文长度裁量，非必需。
- **暂存的既有承接**：补推的这批提醒 `reminderAt` 仍在过去，用户点通知（或以任何方式）打开应用后，03 的 `ReminderSnoozeBar` 快捷条本就对「刚到点、仍待处理」逐条给出稍后/完成/跳过——于是「一条摘要通知 + 应用内逐条处理」天然衔接：不刷屏，又可逐条操作。摘要通知与 04 一样无点击回收能力（01/04 已核实桌面 `show()` 弃句柄），仅告知；动线由打开应用后的快捷条承担。
- **重催同样静默暂存**（需求点名）：04 的重催合成键 `renag:<unix>` 同走 01 发送路径，勿扰期内一并被压、不记投递，窗口后计入本批（04 的 `latest_renag_offset` 只返回「当前一次」，故每任务至多一条重催进批，不 burst）。摘要计数 N ＝首次提醒 + 重催的暂存并集。
- **不重复的准确含义**：见第 0 节 b 与第 5 节——每条暂存提醒的 `reminder_deliveries` 记录只在补发时写一次；单发计入 1、进摘要计入 N，均只写一次记录，此后不再复发。摘要路径把该批各键各记一次投递（虽只弹一条摘要），确保验收「不重复」。
- **补推不带 01 的「【逾期】」前缀**（建议，交开发）：01 的 `【逾期】` 含义＝「这条提醒发晚了（关机错过）」；勿扰暂存的「晚发」是**有意为之**，标 `【逾期】` 会误导。故补推（摘要与单发）建议**不加**该前缀，用普通/摘要文案。此为文案细节、非验收项，交开发裁量。
- **列表侧不加新徽标、不扩展 `ReminderSnoozeBar`**：勿扰只改「提醒何时发」，不改任务视觉状态；逾期任务的红色到期徽标（`dueDateTone`）与勿扰正交，不动。

### 3. 与 06 晨间摘要的边界（划清，避免重叠/相互吞并）

二者都可能在早晨发一条「汇总」通知，但语义正交、各自独立门控，**不合并、不相互替代**：

| | 05 补推摘要（本任务） | 06 晨间摘要 |
|---|---|---|
| 触发 | **事件驱动**：勿扰窗口结束那一刻 | **定时驱动**：每日固定晨间时刻 |
| 内容 | 勿扰期间**被压住的那些具体提醒**（首次提醒 + 重催） | 今日到期 / 逾期 / 我的一天**统计概览** |
| 是否恒发 | 仅当窗口内确有提醒到点才发 | 每天定时发（即便无提醒被压） |
| 数据源 | `reminder_deliveries` 暂存差集 | 统计数据源（06 定义） |

- 二者可能在时刻上接近（勿扰 08:00 结束、晨间摘要也设 ~08:00）→ 用户当天早晨可能收到两条：一条「你在静默期间错过的这些提醒」＋一条「今日概览」。这是**不同信息**（具体提醒 vs 统计），不算重复，本任务保持二者分离。
- **交编排者/06 知悉的协调点**（第 7 节记录，本任务不预埋）：06 落地后可评估——(i) 06 的晨间摘要是否也应受勿扰门控（若晨间时刻落在勿扰窗口内）；(ii) 是否把 05 的补推并入 06 的晨间摘要以进一步减少早晨通知条数。这两点属 06 的范围与产品取舍，05 只保证补推走同一发送判定路径、可被 06 无冲突协调，本任务不实现二者合并。

### 4. 勿扰状态反馈（第 0 节 c，判定要做）

在第 1 节窗口说明句所在 `<p id="quiet-hours-window-desc">` 内，条件追加一行静默中短语：
- 当 `quietHoursEnabled` ∧ 窗口有效（`start != end` 且均非空）∧ 当前本地时刻落在窗口内：在窗口说明句后追加 ` 当前正处于静默中，提醒将在 <结束时刻> 后补推。`（`<结束时刻>` ＝ `quietHoursEnd`，`tabular-nums` 不必——纯 HH:mm 短串）。
- 否则不追加（面板只显示窗口说明句本身）。
- 计算：App.vue `<script setup>` 内 computed，由窗口偏好 + 当前本地时刻现算「是否在窗内」（跨午夜判定 `start > end ? (now >= start || now < end) : (now >= start && now < end)`，与第 5 节 Rust 判定同式）。为让边界翻转能刷新，可挂一个 60s tick 的 `now` ref（仅设置面板打开时运行、关闭/卸载清理）；**60s 刷新为 nice-to-have**，面板短时打开、render-time 现算已足，tick 由开发裁量（可复用既有分钟级 tick）。
- 纯文本、非 live region、无新令牌——只补「用户怎么知道在勿扰期」这一确认，答第 0 节 c。

### 5. 数据模型点明（交开发，只点语义不写实现）

以下均**不阻塞本规格 UI 表面的定稿**（零新令牌、零列表 UI、零契约），但勿扰要真正生效依赖引擎侧落地，需编排者知悉并派开发：

1. **勿扰窗口＝三个偏好，Rust 侧发送判定要读（复用 04 的 `reminder_prefs`）**：开关 `reminder.quiet.enabled`（bool）＋起止 `reminder.quiet.start` / `reminder.quiet.end`（`"HH:mm"` 字符串）。前端经 `saveBooleanPreference`/`saveStringPreference` 落 `settings.json`；Rust 侧在 `src-tauri/src/reminder_prefs.rs`（04 已建、文档已为 05/06/07 预留接入位）新增 accessor——如 `quiet_hours_enabled(app) -> bool`、`quiet_hours_window(app) -> Option<(start_min, end_min)>`（读两个字符串、解析为「当日分钟数」，任一缺失/不可解析则返 `None`）。**不新建 SQLite 偏好表**（与 04 同理，避免第二份偏好真相与前端 `settings.json` 分叉）。
2. **勿扰门骑在 04 留好的接缝上**：在 `reminder_scheduler.rs::poll_once` 里、01 的 `due_reminders` 与 04 的重催各自 `show()` **之前**加同一道勿扰门——若开关开 ∧ 窗口有效 ∧ 当前本地时刻在窗内，则**不 `show()`、也不 `record_reminder_delivery()`**（留作暂存），提醒/重催统一被门。跨午夜判定 `start > end ? (now ∈ [start,24) ∪ [0,end)) : (now ∈ [start,end))`；`start == end` 或窗口 `None` ＝**空/失效窗口 → 不静默（fail-open）**，照常发——母任务「提醒零丢失」下，配置失效时宁可多发也不静默吞掉。
3. **暂存队列＝`reminder_deliveries` 里「到点未发即未记投递」的天然差集，无需新表**：勿扰期内某提醒到点但被门 → **不写投递记录** → 它在后续每轮仍是「到点且未投递」的候选；窗口结束后的下一轮 `now` 已出窗、门放行 → 该提醒（连同整批）变为可发 → 补发时**才写投递记录**。于是「暂存队列」＝「到点、未投递、且此刻不在勿扰窗内」的现算集合，「窗口后补发才记」正是任务点名的语义——每条恰记一次 → 验收「不重复」成立。
4. **补推的合并需单轮抓整批**：窗口结束后第一轮轮询里，该批暂存提醒同刻全部满足「可发」；开发需在该轮 `poll_once` 内先**收拢这批**（首次提醒 + 重催并集）再决定单发（=1）或摘要（≥2），而非逐条各自 `show()`。摘要弹一条、批内各键各记一次投递。
5. **勿扰门对重催与首次提醒一视同仁**：04 已让重催走同一 `show()` 路径，故一道门同时门控二者，无需两处判定（承 04 前置 4 的接缝设计）。
6. **时区**：窗内判定用「当日分钟数 + 设备本地时刻」。04 的重催锚点已知 offset=0 早催边界归 07；勿扰窗判定同样需设备真实本地时刻，07 落地时经 `reminder_prefs` 供 offset / 用本地时钟统一收敛。本任务按设备本地时刻实现即可（与 04 同采信边界）。

### 8. 对需求的说明

需求验收「窗口内零通知，结束后暂存提醒统一补推且不重复」逐条对应：**窗口内零通知**＝第 5 节勿扰门在 `show()` 前拦截首次提醒与重催、窗内不发（fail-open 仅在窗口失效时，属「无有效窗口」非「窗口内」）；**统一补推**＝第 2 节窗口结束后第一轮单轮抓整批、≥2 条合并一条摘要、恰 1 条单发；**不重复**＝第 5 节「到点未发不记投递、补发才记」使每条恰记一次、此后不复发。范围内「重催在勿扰期同样静默暂存」＝第 2/5 节：重催走 01 同一 `show()` 路径，被同一道勿扰门压住、计入补推整批。

### 编排者裁决（2026-07-24）

规格第 7 节三个产品裁决点，逐条采纳 UI/UX 的取向：

1. **补推合并摘要，不逐条**。需求原文即「统一补推」，合并符合措辞且防刷屏（勿扰一夜攒 5 条不该 8:00 弹 5 条）；代价「每条即时可辨识」由 03 的应用内快捷条承接（打开应用逐条处理）。采纳。

3. **05/06 边界保持分离**。勿扰 8:00 补推与晨间摘要各发一条不算重复（信息不同）；「晨间摘要是否受勿扰门控 / 补推是否并入晨间摘要」属 06 范围，本任务只保证补推走同一发送判定、可被 06 协调。采纳，已在 06 任务文件登记。

数据模型按规格：三个偏好落 settings.json、Rust 经 04 的 `reminder_prefs.rs` 新增 quiet accessor 读取；勿扰门骑 04 留好的 `poll_once`/`show()` 接缝（同时门控首次提醒与重催）；暂存队列＝`reminder_deliveries`「到点未发即未记投递」的天然差集，无新表；空/失效窗口 fail-open（不静默，守母任务「零丢失」）。
