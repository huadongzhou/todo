## 规格（UI/UX）

先通读了 01/04/05/06 的实现记录，本规格接其架构：桌面提醒由 Rust 后台线程每 30s 轮询 SQLite、按纯规则现算「该发什么」、`reminder_deliveries` 按键每键只发一次（01）；03 在设置面板建了「提醒」`fieldset`（重催开关 + 勿扰块 + 晨间摘要块 + 四档 snooze），04 建了 `reminder_prefs.rs`（Rust 从 `settings.json` 读提醒偏好，文档已为 05/06/07 预留接入位），05/06 都把「设备真实时区」的收敛明确交给本任务。**四处调度判定当前都用 `ZONE_OFFSET_SECONDS=0`（`reminder_scheduler.rs`，UTC 读时刻）**：04 逾期锚点、05 勿扰窗判定、06 晨间时刻与今日/逾期计数、01 逾期补发都受它影响，东八区等主市场因此偏晚/偏移。本任务让调度器读设备真实偏移收敛它们，并落定「本地时刻 / 固定时刻」的提醒语义。

**本任务的 UI 表面极小——「引擎为主、界面只露一角」的简化任务，且比 04/05/06 更小。** 时区收敛（真实 offset 喂进域函数已备的 `zone_offset_seconds` 参数）与 05 转来的「【逾期】」文案口径都在 Rust 侧、零界面；界面上只露出**一处**——设置面板「提醒」fieldset 里的一个**全局「本地时刻 / 固定时刻」单选（单个复选框行）**。列表侧零改动、无新增组件、无新增 live region。下面先给三个正面判断，再给这唯一控件的五项规格，最后点明数据流与出处核对。

### 0. 三个关键判断（正面表态）

| 议题 | 判断 |
|------|------|
| **a) 策略怎么让用户选：全局还是每任务？放哪？默认？** | **全局设置（不做每任务），放「提醒」`fieldset`，单个复选框行，默认＝本地时刻（floating）。** 每任务＝新增 todo 字段＝契约变更＋逐项 UI，超简化级（同 04 拒绝每任务重催开关的理由）；且「按当地时间还是绝对时刻理解我的提醒」是一种**跨全部提醒的心智模型**、不是逐条属性，全局一次定清最省心。**默认本地时刻**：个人待办提醒绝大多数锚在「我人在哪、当地几点」——「9:00 吃药」「20:00 给妈打电话」「9:30 站会」都指当地墙钟；换时区后用户仍要它们在当地那个点响，这正是 floating。绝对时刻只对「与他人共享的某一全球瞬间」（如跨时区会议的固定 UTC 时刻）才对，对个人待办是少数。主流日历/提醒（iOS 提醒、日历默认事件）也按当地墙钟，故默认 floating。理由见第 1 节。 |
| **b) 真实偏移怎么拿 / 要不要在界面显示时区** | **偏移是设备环境状态、不是用户偏好，必须能被 Rust 调度器读到（应用关到托盘、webview 不在时也要正确）；界面不显示当前时区/偏移。** 前端 `new Date().getTimezoneOffset()` / `Intl.DateTimeFormat().resolvedOptions().timeZone` 可得，但**关键是「保持新鲜」**——offset 随旅行/夏令时会变，若前端写进 `settings.json` 缓存、而应用正关在托盘（webview 不跑）时用户跨了时区，缓存就过期、Rust 会用错 offset。故推荐 **Rust 侧取实时系统偏移**（哪怕 webview 不在也正确），具体通道（原生读 / 前端写 settings.json 经 04 `reminder_prefs` 读 / command）归开发，本规格只点明「offset＝会变的实时设备状态、要被 Rust 读到且不能读到陈值」。**不在界面显示时区/偏移**：OS 已显示时区，重复即噪音；「UTC+8」是术语、多数用户不解；offset 是应用自动跟随的环境量、用户无可操作对象，显示只会招困惑（DESIGN 内容优先/低摩擦——不加用户无法操作的只读状态）。理由见第 2 节。 |
| **c) 切换策略对既有提醒的界面提示** | **控件下的一句静态说明句足矣，不做确认弹窗、不做切换时的告警/播报。** 关键事实：floating↔absolute 的差异**只在设备换过时区后才显现**——用户仍在设定提醒时的那个时区里时，两种语义算出的触发时刻**完全相同**（当地 9:00＝那一刻）。故在同一时区切换策略**对既有提醒无任何可见变化**，重弹告警反而令人费解（「明明什么都没变，警告我什么」）。用一句平实说明句讲清两种语义即可（与 quiet/summary 的静态说明句同权重、非 live region）。理由见第 3 节。 |

### 1. 「本地时刻 / 固定时刻」单选（设置面板，五项齐全）

**位置**：`src/App.vue` 设置面板「提醒」`fieldset` **末尾**——四档 snooze 的最后一行（`明天`，现于 line 778–792）**之后**、`fieldset` 结束标签（现 line 793）**之前**。理由：renag/quiet/summary 是「通知何时发」的日常投递行为、snooze 四档是其快捷子组，都是高频设置；时区策略是**只在跨时区旅行时才起作用的进阶/边缘语义**，按 DESIGN「内容优先」把日常设置排在前、边缘设置压到末尾，且置于完整 snooze 子组之后不劈开它。**不另开 fieldset**（一个开关不值得单起一组，「提醒」组是它的自然归属）、**不加 `isDesktop` 门**——与该组其余项同理（提醒行为偏好、非桌面能力，移动端本地通知落地后复用；同 renag/quiet/summary 的既有判断）。

**结构与布局**（单个复选框行，与 `renagOverdue`/`quietHoursEnabled`/`morningSummaryEnabled` 行**同型、逐字复用类串**——不是渐进展开块，无 `type="time"`、无 `<p>`、无 `aria-describedby`，是本 fieldset 里最简单的一种行）：

- 外层 `<label class="mb-2 flex min-h-10 cursor-pointer items-center gap-3 rounded-lg px-3 py-2 hover:bg-slate-50 dark:hover:bg-slate-900">`。
- `<input type="checkbox" :checked="settingsStore.reminderAbsoluteInstant" @change="settingsStore.setReminderAbsoluteInstant(($event.target as HTMLInputElement).checked)">`。
- 双行 `span`（`min-w-0`）：
  - 标题（`block text-sm font-medium text-slate-800 dark:text-slate-100`）：`按固定时刻触发提醒`。
  - 说明（`block text-xs text-slate-500 dark:text-slate-400`，**静态文本、非 computed**）：`默认按当地时间触发：换时区后，设「9:00」的提醒仍在当地 9:00 响。勾选后按设定时的绝对时刻触发，换时区后响铃的当地时间随之改变。`——默认关（＝本地时刻），说明句是用户发现并理解两种语义的入口，含义全由文字讲清、不靠颜色。

**为何用「复选框（默认关＝本地时刻）」而非两选一 radiogroup**：① 本 fieldset 全部是复选框行，复选框零新控件模式、零新令牌；radios 会引入本组尚无的控件类型，为一个边缘设置新增模式属过度设计。② 与本组「有后果/更专门的行为默认关，关＝更常见更安全的那个」哲学一致（renag/quiet/summary 皆默认关）——floating 是更常见、更安全的默认，故让它落在「未勾选」态，勾选＝显式选进专门的绝对时刻语义。③ 复选框「未勾选＝本地时刻」的含义已由说明句正面点破（说明句同时讲清勾选与不勾选两态），不靠用户臆测。两选一 radiogroup 为可选替代（更显式地并列命名两态），若编排者更倾向显式 radios，属可吸收的小改，本规格取复选框（第 6 节登记为已考虑并选择的取舍）。

**存储**：走既有 `saveBooleanPreference`/`loadBooleanPreference`（`src/lib/settings-storage.ts`，含浏览器回退），键名建议 `reminder.tz.absolute`，**默认 `false`（＝本地时刻）**；在 `useSettingsStore`（`src/stores/settings.ts`）按 `renagOverdue` 同一模式加 1 个 ref（`reminderAbsoluteInstant` 默认 `false`）＋ 1 个具名 setter（`setReminderAbsoluteInstant` 走 `saveBooleanPreference`，失败沿用既有 `persistenceError` 通道）＋ bootstrap 读取 ＋ catch 兜底默认 ＋ 导出 ＋ 诊断快照。命名归开发裁量（如偏好 `reminderTimezoneMode` 之类亦可），本规格给形状与键。

**状态**：
- 默认：复选框未勾选（＝本地时刻，floating）。
- 悬停：`hover:bg-slate-50 dark:hover:bg-slate-900`（沿用既有设置行）。
- 聚焦：原生 checkbox 浏览器默认焦点框，与本组其余项一致（注：DESIGN `focus-ring` shortcut 现有失效缺陷已转 `外观与设置/04`，原生 checkbox 本就走浏览器默认焦点框、不涉该 shortcut，本规格随之不旁路）。
- 加载：无异步加载态——开关即时落库（同 `setRenagOverdue`）。
- 空数据：不适用（单一开关）。
- 错误：持久化失败沿用既有 `persistenceError` 通道（面板顶部主题行 `aria-live="polite"` 处），不新增错误 UI、不新增 live region。

**暗色适配**（与浅色成对，全部既有类）：行 `dark:hover:bg-slate-900`、标题 `dark:text-slate-100`、说明 `dark:text-slate-400`。无新增色值。

**移动端适配**：行 `min-h-10` 沿用既有设置项基线（触控命中达标）；双行文案自然换行不截断；无固定宽高，320px 下不越界、不横向滚动（DESIGN 硬性）。

**可访问性**：
- 分组归属既有 `fieldset`+`legend「提醒」`（`aria-labelledby="reminder-settings-heading"`），读屏进组报出组名。
- 复选框关联可见 `label`（双行文字＝可访问名＋说明），键盘可达、空格切换，与本组其余项一致。
- 两种语义不靠颜色/图形单传，全由说明句文字讲清（含具体「9:00」例）。
- **不新增第二个 live region**：说明句为 `label` 内静态文本、非 `aria-live`；持久化错误复用既有主题行 polite 区；页面级唯一 `role="status"` 区（03 建立）不碰。

### 2. 真实偏移的数据流（点明语义，具体归开发）

以下不阻塞本规格 UI 表面的定稿（零新令牌、零列表 UI），但真实时区要生效依赖引擎侧落地，需编排者知悉并派开发：

1. **offset＝会变的实时设备状态，必须被 Rust 读到且不读陈值**：调度器四处判定（04 逾期锚点、05 勿扰窗、06 晨间时刻与计数、01 逾期补发）现用 `ZONE_OFFSET_SECONDS=0`；本任务把设备真实偏移喂进域函数**已备好的 `zone_offset_seconds` 参数**（04/05/06 实现记录均注明规则零改、只接线）。**关键约束＝新鲜度**：应用可能关在托盘、webview 不跑，此时用户跨时区或夏令时切换，任何「前端一次性写进 settings.json 的缓存 offset」都会过期、令 Rust 用错值。故**推荐 Rust 侧取实时系统偏移**（每轮轮询现取，webview 不在也正确）；若走「前端写 settings.json、Rust 经 04 `reminder_prefs` 读」通道（与 renag/quiet/summary 偏好同路），必须保证写入随时区变化刷新、不留陈值。**具体通道（原生读 / settings.json / command）归开发**，本规格只钉死「offset 是实时设备状态、要被 Rust 读到、不能是陈值」。
2. **界面不显示当前时区/偏移**（判断＝不显示，理由见第 0 节 b）：OS 已显示时区、重复即噪音；offset 是应用自动跟随的环境量、无用户可操作对象；旅行用户「为什么提醒时刻变了」的疑惑更该由 floating 默认（提醒本就按当地墙钟、自然对）来消解，而非把裸 offset 摆给用户。故本任务界面**不加**任何时区/偏移显示。

### 3. 切换策略对既有提醒的影响与提示（第 0 节 c 展开）

- **事实**：floating 与 absolute 的触发时刻**只在设备换过时区后才分叉**。用户仍在「设定提醒时那个时区」里时，两者算出的触发时刻恒等（当地 9:00＝那一绝对时刻）。故**在同一时区切换本控件，对全部既有提醒无任何可见变化**。
- **因此不做重提示**：不弹确认框、不发切换告警、不进 live region 播报、不触发列表重渲染或徽标变化（切换只改「触发时刻怎么解释」，不改任何任务的存储数据与到期徽标——到期徽标由 `dueDate` 驱动、与本策略正交）。一句控件下的**静态说明句**（第 1 节的双行说明，已同时讲清勾选/不勾选两态）就是全部提示，与 quiet/summary 的静态说明句同权重。
- 这答「切换会不会让用户困惑」：因效果只在跨时区后显现，此刻加重提示反而制造「什么都没变却被警告」的困惑；平实说明 + floating 默认（多数人永不需要切）是最不困惑的组合。

### 4. 范围澄清：本策略只管「提醒点」，日期/时刻类判定恒按当地（点明，避免开发误接）

「本地/固定」这个**选择**只对 `reminderAt`（完整日期时间的提醒瞬间）有意义，其余受 offset 影响的判定**没有 absolute 语义、恒按当地**，本控件不门控它们：

- **`reminderAt` 提醒点**：既是完整瞬间，才有「按当地墙钟重新解释（floating）」还是「钉死那一绝对瞬间（absolute）」的二义。本控件正是选这一件事。
- **04 逾期 / 06 今日到期计数**：锚在 `dueDate`（纯日期、无时刻）——一个裸日期只能在当地时区里解释「今天 > 截止日？」，**无 absolute 可言**，恒按当地；本任务对它只做「用真实 offset 定当地日界」（收敛 offset=0），不受本控件影响。
- **05 勿扰窗 / 06 晨间时刻**：是纯时刻（无日期）——「22:00」「9:00」本就是当地墙钟，恒 floating；本任务对它只做「用真实 offset 把当前瞬间读成当地时刻」，不受本控件影响。

即：**真实 offset 收敛**（第 2 节）作用于全部四处、无用户选择；**本地/固定选择**（第 1 节）只作用于 `reminderAt` 提醒点。这也是为什么一个全局单选就够——它只需门控 `reminderAt` 一处的解释，其余恒当地、无需选择。

### 停下报告（全局规则 5 · floating 与选择开关）

裁决第 4 点问的关键——「正确实现 floating 是否必须改 `reminderAt` 存储形态」——**答案是必须**，论证如下：

- floating 要求设备换时区后，「9:00」的提醒仍在**新时区的当地 9:00** 触发。这需要调度器在触发时按**当前**时区把提醒的**原始墙钟时刻**重新解释为绝对瞬间。
- 但 `reminderAt` 现存为**绝对 UTC 瞬间**，已**不可逆地丢失原始时区**。设 UTC+8 时设「9:00」→ 存 `01:00Z`；换到 UTC+0，floating 期望 09:00Z 触发，这需先还原原始墙钟「09:00」——而从 `01:00Z` 还原墙钟必须知道原偏移 +8，绝对 UTC 里没有。若改用**当前**偏移去解释，等价于假设「原偏移＝现偏移」，此时 floating 与 absolute **恒等**（偏移相同则两者算出同一瞬间）——恰在两偏移不同（floating 唯一有意义的场景）时失效。故绝对 UTC 里的信息**不足以**支撑正确 floating。
- 结论：正确 floating **必须**改 `reminderAt` 存储形态（如另存 zone-naive 墙钟 + 原始偏移），这是数据模型/契约改动，与 **08**（`reminder_at` 单值→多提醒点契约迁移，同样重塑 `reminderAt` 形态）**强耦合**，无法在本任务内干净完成。按裁决第 4 点与全局规则 5 停下，不硬塞半吊子 floating、不擅自改契约。

**连带：「本地/固定」全局单选（UI 开关）一并延后。** 规格与裁决第 1 点把默认钉为**本地时刻（floating）**。若此刻加开关，其默认（floating）会承诺一个未实现的行为——正是裁决禁止的「半吊子 floating」。开关与 floating 不可分（开关的作用就是在 floating/absolute 间选择，而 absolute≡floating 时选择无意义），故与 floating 一并延后。本任务因此**无前端改动**（settings.ts / App.vue 未动）。
