# 备份容灾

- 级别：直达
- 状态：开发

## 需求（产品）

- 目标与场景：服务端数据库定时备份，可从快照恢复，用户数据丢不起。
- 范围（做 / 不做）：做 定时快照、恢复流程与演练脚本；不做 多区域部署（发布工程/14）。
- 验收标准（逐条可检查）：
  - [ ] 快照按计划自动生成并可清理过期。
  - [ ] 恢复演练：从快照拉起服务成功且数据一致，演练记录在案。

### 编排者并入项（来自 04-服务端SQLite持久化 评审第 1 轮，已裁决「转任务处理」）

1. **【必办】`patch` 列 JSON 载荷的前后兼容**（`crates/server/src/sync_store.rs:151`）：落盘后新引入的风险面——`TodoPatch` 派生 `deny_unknown_fields`，一旦服务端二进制**回滚**到旧版本，库里由新版本写入的、带新字段的 patch 行会**整行读不回并被静默跳过**。`SCHEMA_VERSION` 只声明列布局，不覆盖列内 JSON 形状。回滚安全属容灾范畴，本子任务必须给出策略（例如存储读取路径上放宽 `deny_unknown_fields`、或为 patch JSON 引入形状版本），而不只是做快照。
2. **`with_log` 的并发归因注释是错的**（`crates/server/src/sync_store.rs:228-240`）：注释把「revision 不撞号」归因于事务，实际靠的是「全进程只有一条 `Connection` 且被 `Mutex` 包住」。`BEGIN DEFERRED` 下多连接会得到不走 busy handler 的 `SQLITE_BUSY_SNAPSHOT`。**本子任务若引入第二个连接（快照、在线备份、只读副本都会），这条竞态立刻从不可达变为可达**——请在设计备份方案时正面处理，并把注释改对。
3. **补一条「重启后新操作编号接续」的自动化断言**（`crates/server/src/lib.rs:269-302`）：该性质目前只有人工走查覆盖。恢复演练正是它的真实场景——从快照拉起服务后，新操作必须接在原 revision 之后而非从 1 重编。

补充验收标准：

- [ ] 服务端二进制回滚到不认识某新字段的旧版本后，既有 patch 行仍能被读回，不被静默跳过（须实测）。
- [ ] 备份/恢复方案若引入第二个数据库连接，revision 分配在并发下仍无重号无跳号（须有并发用例）。
- [ ] 存在自动化断言覆盖「从快照拉起后新操作编号接续」。
