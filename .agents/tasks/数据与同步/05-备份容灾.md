### 编排者并入项（来自 04-服务端SQLite持久化 评审第 1 轮，已裁决「转任务处理」）

1. **【必办】`patch` 列 JSON 载荷的前后兼容**（`crates/server/src/sync_store.rs:151`）：落盘后新引入的风险面——`TodoPatch` 派生 `deny_unknown_fields`，一旦服务端二进制**回滚**到旧版本，库里由新版本写入的、带新字段的 patch 行会**整行读不回并被静默跳过**。`SCHEMA_VERSION` 只声明列布局，不覆盖列内 JSON 形状。回滚安全属容灾范畴，本子任务必须给出策略（例如存储读取路径上放宽 `deny_unknown_fields`、或为 patch JSON 引入形状版本），而不只是做快照。
2. **`with_log` 的并发归因注释是错的**（`crates/server/src/sync_store.rs:228-240`）：注释把「revision 不撞号」归因于事务，实际靠的是「全进程只有一条 `Connection` 且被 `Mutex` 包住」。`BEGIN DEFERRED` 下多连接会得到不走 busy handler 的 `SQLITE_BUSY_SNAPSHOT`。**本子任务若引入第二个连接（快照、在线备份、只读副本都会），这条竞态立刻从不可达变为可达**——请在设计备份方案时正面处理，并把注释改对。
3. **补一条「重启后新操作编号接续」的自动化断言**（`crates/server/src/lib.rs:269-302`）：该性质目前只有人工走查覆盖。恢复演练正是它的真实场景——从快照拉起服务后，新操作必须接在原 revision 之后而非从 1 重编。

补充验收标准：

- [ ] 服务端二进制回滚到不认识某新字段的旧版本后，既有 patch 行仍能被读回，不被静默跳过（须实测）。
- [ ] 备份/恢复方案若引入第二个数据库连接，revision 分配在并发下仍无重号无跳号（须有并发用例）。
- [ ] 存在自动化断言覆盖「从快照拉起后新操作编号接续」。

## 实现记录（开发）

### 落点：快照走同一条连接，恢复走停机的子命令

三件事各自落一处：

| 交付物 | 落点 | 形状 |
|-------|------|------|
| 定时快照 + 过期清理 | `crates/server/src/backup.rs`（新增） | 独立线程，启动即拍一张，之后按间隔；按数量保留 |
| 快照怎么拍 | `SyncStore::snapshot_into` | `VACUUM INTO`，**跑在 store 自己的那条连接上**，与同步请求共用同一把 `Mutex` |
| 恢复 | `todo-server restore <snapshot>` 子命令 | 一次性、跑完即退，操作者在服务停机时执行 |

快照不是新开一条连接去读库，而是排进同步请求的那把锁里——这是本子任务最要紧的一条设计约束，理由见下一节。

### 并入项 2：为什么不引入第二个连接，以及注释改成了什么

04 的 revision 不撞号，靠的不是事务，而是「全进程只有一条 `Connection` 且被 `Mutex` 包住」。SQLite Online Backup API、`VACUUM INTO` 开在另一条连接上、只读副本，三种拍快照的常规做法**都会引入第二个连接**，那时 `BEGIN DEFERRED` 下「先读 `MAX(revision)` 再 INSERT」的竞态立刻可达（后升级为写事务的一方拿到 `SQLITE_BUSY_SNAPSHOT`，该错误不走 busy handler，`busy_timeout` 等不出来）。

本方案正面选择保住那条不变式：`snapshot_into` 先 `self.connection.lock()`，再在这条连接上执行 `VACUUM INTO`。代价是拍照期间同步请求要等——付这份代价换来的是「revision 分配不依赖进程拓扑之外的任何假设」，而日志是每条操作一行的小文件（演练里从日志时间戳看，一轮「拍照 + 清理」约 8 ms）。`transaction_with_behavior(Immediate)` 没有加：单连接下它一行行为都不改，属为不存在的拓扑写代码。

`with_log` 的文档注释按事实重写：**互斥来自这里取的锁**（进程只有一条连接），事务提供的是原子性（半途失败不留行）；并写明 `BEGIN DEFERRED` 在多连接下会发生什么，以及「快照不开第二条连接、恢复在停机时跑」这两条今天成立的前提。`snapshot_into` 的注释从另一头指回来。

并发用例 `revisions_stay_unique_and_gapless_while_snapshots_are_taken_alongside_syncs`：8 个线程各推 4 条操作，同时另一个线程连拍 8 张快照，断言两件事——最终 revision 序列恰为 1..=32（无重号、无跳号）；**每一张快照本身也是一条完整日志**（revision 连续到它自己的末尾），即拍照拍不出半条操作。

### 并入项 1（必办）：patch JSON 的回滚兼容

`deny_unknown_fields` 在**线上**是对的（服务端认不得的字段应整个拒收，而不是半吞），在**出库路径**上是错的：日志由当时在跑的那个二进制写下，回滚到不认识某新字段的旧版本后，带该字段的行整行 `from_str` 失败 → 被跳过 → 而 `next_cursor` 照样把它算进去，**设备的游标越过了它从未收到的变更，此后再也不会来要**。这比「延迟送达」严重，是本项必办的原因。

做法（`sync_store.rs::patch_from_json`）：先严格解；解不动时才把「本 build 叫不出名字的键」摘掉重解，并 `warn!` 把摘掉的字段名报出来。

- **怎么判定一个键是否已知**（第 2 轮改写，见评审阻塞 1）：让 serde 自己指出来。新增的 `Watched` 适配器把 `serde_json::Value` 按 serde 原样读一遍，唯一动作是在 `MapAccess::next_key_seed` 里记下「被 seed 拒掉的那个键」和它的路径；`deny_unknown_fields` 的派生代码正是在这一步、在看值之前拒绝未知名字的，所以这条信号在**任意深度**都成立（`subtasks.0.note`、`recurrence.weekOfMonth`、`attachments.0.caption`），也不必在 server 侧抄一份会漂移的字段清单。`patch_from_json` 由此变成「严格解 → 失败就跑一遍 `Watched` 取名字 → 从它所在的那个对象里摘掉 → 再严格解」的循环，**交出去的 patch 始终由普通 serde 从摘干净的 Value 解出**，适配器只负责指位置。
- **只放宽「不认识的名字」，不放宽「认识但值坏了」**：`{"title":42}` 仍然整行跳过，嵌套层同理（`{"subtasks":[{…,"done":"maybe"}]}`）。坏值的失败发生在读值那一步，不会留下任何名字记录，于是直接返回原始的严格错误。把它降级成「title 不变」「这一步没做完」就是 04 立下的那条红线——替用户报告一个操作没说过的话。用例 `a_patch_whose_own_field_is_unusable_is_still_skipped` 与 `a_nested_field_whose_value_is_unusable_is_still_skipped` 钉住。
- **丢字段只丢在这一次回答里**：行里的原字节从不被重写，前滚回新版本后，游标仍落后的设备照样能拿到完整 patch（演练 B 第 3 步实测）。
- **唯一够不着的地方**：带载荷的枚举变体内部（契约里的枚举全是无载荷变体）。够不着时的行为是「整行跳过」，即修复前的行为，不会读成别的意思；`deserialize_enum` 的注释写明了这一点。

### 参数选择（本地可决部分，均给了默认值与理由）

| 参数 | 默认 | 理由 |
|------|------|------|
| `BACKUP_DIR` | `todo-server-backups` | 与 `DATABASE_PATH` 默认 `todo-server.db` 同一风格：自托管仍是「跑二进制」，不需要先建目录 |
| `BACKUP_INTERVAL_SECONDS` | `3600`（每小时） | 只活在库里、丢盘即没的操作窗口 ≤ 1 小时；快照是每条操作一行的小文件，拍得起。单位取秒而非小时，是为了恢复演练不用等一小时才看到调度生效 |
| `BACKUP_KEEP` | `72`（≈3 天） | 覆盖一个周末：周五出的问题周一才发现，仍有出问题之前的快照。**按份数而非按天龄保留**——按天龄的规则会让「停机一周后重启」的服务器一上来就把仅有的副本全删了 |
| 存放位置 | 与库同盘（进程旁的目录） | 本地可决部分只做到这里；异地/对象存储要选区域、要采购，属 发布工程/14 与用户拍板范围，本轮不做（见遗留问题 2） |

另外三条本地决定：① 启动即拍一张——目录配错在启动时就听得见，新部署从起来那一刻就有副本；② `BACKUP_INTERVAL_SECONDS=0` 显式关闭并 `warn!`，而不是静默不拍；③ 快照失败只 `error!` 不停服——开库失败必须停服是因为服务会把操作确认进虚空，而少拍一张快照不会让任何一个回答变错，为它停服是把「少一份副本」升级成「服务不可用」。

### 恢复流程（`todo-server restore <snapshot>`）

`fs::copy` 覆盖库文件是有坑的，所以恢复没有留给一句 `cp`：

1. **先验后动**：以只读方式打开快照（`SyncStore::open_snapshot`，不建库、不写 `user_version`），先 `PRAGMA quick_check` 走一遍全部页面（第 2 轮加，见评审建议 5），再读出 `MAX(revision)`。路径打错、文件被截断、页面级损坏的快照都会在这里被拒，而不是覆盖掉好数据之后才发现。
2. **确认没人在用**：`SyncStore::is_in_use(target)`——以独占锁模式打开现场库跑一个不写东西的事务，还有连接开着就会被答 `SQLITE_BUSY`，此时**一个字节都不动**地返回 `TargetInUse`（第 2 轮加，见评审建议 1）。
3. **先落临时名再改名**：拷到 `<库>.restoring` 再 rename，半途失败不会留下半个库；此后每条失败路径都会把 `.restoring` 清掉。
4. **旧库移开而非删除**，且 `-wal` / `-shm` 跟着一起移，**主库在不在都移**（第 2 轮改，见评审阻塞 2）：留在原地的 WAL 边车会被回放进刚恢复的库；跟着走则被保留的那份仍然自洽。恢复错快照是操作者应当能撤销的错误。
5. **停机执行**：子命令跑完即退，天然避开「运行中的服务持有唯一连接」这条前提；第 2 步是这条前提的实际校验，而不只是文档里的一句要求。

### 恢复演练记录（真实进程，可复现）

| 步骤 | 实际观测 |
|------|---------|
| 1. 启动 | 日志三行：`sync log opened` → `snapshot schedule started (interval_seconds=5 keep=3)` → **启动即拍**的 `sync log snapshot taken … 012929708Z.sqlite3` |

| 7. `todo-server restore <快照>` | `sync log restored from a snapshot … latest_revision=3 preserved=…/live.db.before-sync-log-20260723T013003349Z`，随后两行 warn：「设备须重置 cursor 0 重新全量拉取」与「保留物不会被自动清理」。目录核验：两个孤儿边车被移到 `live.db.before-…-wal` / `-shm`，`live.db` 旁边**一个边车都不剩** |
| 8. 从恢复后的库拉起服务，新设备 `cursor: 0` 全量拉 | **3 条**变更、`nextCursor: 3`，与 restore 自报的 `latest_revision=3` 一致（第 1 轮此处是 4 条、含快照之后的 op-4）；patch 逐字段原样返回，含 `subtasks:[{"id":"s1","title":"拍快照","done":true}]` 与整条 recurrence |

**演练 B · 服务端二进制回滚，新字段在嵌套结构里（阻塞 1，实测而非推演）**

手法：给 `crates/contracts` 的 **`Subtask`** 临时加一个字段 `note`（第 1 轮加的是顶层的 `TodoPatch::focus_minutes`，评审指出顶层通得过、嵌套通不过，故改用嵌套字段复跑），编出「超前一版」的二进制；`git checkout` 还原契约后，分别编出「第 1 轮实现的二进制」与「本轮实现的二进制」；三者读写**同一个库文件**。

1. **先复现第 1 轮的故障**：超前版写入 op-a / op-b / op-c，其中 op-b 的 patch 为 `{"title":"新字段","important":true,"subtasks":[{"id":"s1","title":"步骤","done":false,"note":"只有新版本认得"}]}`（`nextCursor: 3`）→ 第 1 轮版以 `cursor: 0` 拉取，**只返回 2 条（op-a、op-c），`nextCursor` 仍是 3**；日志 ``skipping a sync log row with an unreadable patch … error=unknown field `note`, expected one of `id`, `title`, `done` ``。即评审说的那条路径确实可达，后果是 op-b 永久丢失。
2. **本轮实现重跑同一手法**：**三条全部返回**，op-b 的 patch 为 `{"title":"新字段","important":true,"subtasks":[{"id":"s1","title":"步骤","done":false}]}`（只少了叫不出名字的那一个），日志一行 `serving a sync log row without the patch fields this build cannot name … fields=subtasks.0.note`；同一请求推入的 op-d 正常得到 revision 4。
3. **再前滚**：用超前版重新打开同一个库，op-b 的 subtask 又完整返回 `"note":"只有新版本认得"` —— 证实回滚期间只是「这一次回答里少一个字段」，行里的原字节从未被重写。

**环境还原核验**：三场进程均已退出（`Get-Process todo-server*, ahead, back, prefix` 为空），scratchpad 里的 `drill/` 目录（库、快照、三个临时二进制、脚本、日志）已删除；仓库 `git status --porcelain` 只剩本次的 6 处改动（任务文件、`.gitignore`、`TODO.md`、server 三个文件 + 新增 `backup.rs`），契约与 `Cargo.lock` 无残留改动，仓库根目录无 `todo-server.db*` / `todo-server-backups/` / `.restoring` 残件。

### 遗留问题（供编排者裁决，本轮未做）

1. ~~**恢复会回退 revision 序列，游标已越过快照的设备会漏变更**~~（**主体已按编排者裁决转 数据与同步/07-登录绑定同步；兜底已在第 2 轮做完**）：演练 A 里 desktop-1 的 cursor 已是 4，恢复后服务端把 revision 4 发给了 op-5；该设备的 `revision > cursor` 过滤会把它滤掉，从此再也拉不到。根治需要给日志加「世代号」（恢复后换 epoch，设备见到新 epoch 即从 cursor 0 全量重拉），属契约变更（`SyncResponse` 加字段 + 视图端配合），超出本子任务改动面。本轮兜底：**运维口径「恢复后需让设备重置 cursor 全量重拉」已打进 `restore` 的输出**（演练 A 第 7 步日志），操作者不再需要读任务文件才知道这件事。
2. **快照与库同盘**：默认放在进程旁的目录，整盘损坏时副本一起没。异地/对象存储要选区域、要采购，属用户拍板与 发布工程/14 的部署面，按 workflow 全局规则 5 未擅自决定。
3. **快照期间同步请求要等**：`VACUUM INTO` 持连接锁，日志越大暂停越久；日志压实（04 遗留问题 1）未做，两者长期相关。本次演练日志仅数行、一轮拍照+清理约 8 ms，无度量支撑不做优化；建议把「快照耗时」纳入 06 的观测面后再谈。
4. **降级读的 warn 每读一次刷一次**：与 04 已知的坏行重复告警同源（已归 06）；`patch_from_json` 的回退路径还要「每摘掉一个未知名字就重解一遍」（n 个未知字段 = n+1 次解码，且每次克隆一份 `Value`），只在解码失败时发生、只在回滚期间成立、patch 是几百字节的小对象，未做缓存也未做单遍化。

5. **`is_in_use` 的探测挡不住「库已经烂了但服务还开着」**：探测遇到「不是数据库」一律判为没人用（否则坏盘后就没法恢复了）。这个组合下 POSIX 的静默换库仍然可能，但此时服务本身也已经在答错，属更靠前的问题；`quick_check` 与 `is_in_use` 都没有覆盖它。
