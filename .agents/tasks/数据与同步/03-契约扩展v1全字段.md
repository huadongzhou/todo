### 编排者并入项（来自 02-Store迁移 评审第 2 轮，均已裁决「转任务处理」）

以下 6 项是本任务范围的正式扩展，与字段扩展同批实现、同批验收。第 1 项是**前置必办**，须在改动 `SCHEMA_VERSION` 之前处置。

1. **【前置必办】`user_version` 误判纠偏**（02 评审第 2 轮，`src-tauri/src/todo_db.rs:143-170`）：本机与任何跑过中间版本的库，`user_version` 已被写成 **2**，而 02 定论「`user_version` = schema 版本」且当前 `SCHEMA_VERSION` = 1。若本任务把 `SCHEMA_VERSION` 抬到 2，这些库会被判成「已是目标版本、无需迁移」而**跳过真正的字段迁移**，同时 `initialise` 的 `stored > SCHEMA_VERSION` 告警在纠偏前每次启动误报。请二选一并写明理由：跳号到 3，或加一次性纠偏逻辑。务必给出「已被写成 2 的旧库」的实测证据。
2. **`WriteOutcome` 覆盖三个吞信号的执行点**（`src/lib/todo-repository.ts:294-313` 及联动点）：`save` 忽略 `clearPendingWrites` 返回值、`recordPendingUpsert` 忽略摘墓碑结果（会造成「upsert 与墓碑同 id 并存 → 重放先写后删」）、`quarantine` 忽略写失败后仍无条件重写 `todos.items`。这三处是 02 新不变式（「键里的条目永远比库里新」）的真实破口，须纳入 `WriteOutcome` 体系。
3. **malformed 条目的隔离覆盖非启动路径**（`src/lib/todo-repository.ts:143-163`）：目前只有启动重放会隔离坏行，非启动路径上任何一次日志写回都会**静默删除**读不回 `Todo` 的条目；浏览器运行时更是从不隔离，而 `todos.items` 正是浏览器主存储。本任务扩字段后，缺新字段的旧结构条目必然大量出现（旧条目读不回 `Todo`），此项若不做即等于批量静默丢数据。
4. **`isTodo`/`TODO_FIELDS` 编译期锁定**（`src/lib/todo-repository.ts:99-132` 对照 `crates/contracts/src/lib.rs`）：前端手写的运行时校验与契约字段集会随本任务扩字段立刻漂移。按评审建议用 `satisfies Record<keyof Todo, true>` 之类写法把字段集锁到生成类型上，使漏加字段变成编译错误。
5. **`startupBacklog` 复位路径**（`src/stores/todos.ts:36-47,71-75`）：置真后无任何复位，横幅整会话不消失且文案与事实脱节。属 `WriteOutcome` 消费侧收尾，与第 2 项同段代码。
6. **新字段的迁移与兼容**：既有库与既有待写日志里的旧结构数据必须无损升级；按 AGENTS.md「无版本号机制下以可选字段 + serde default 保持前后兼容」处理，并确认 `deny_unknown_fields` 不会让旧客户端发来的载荷被拒。

### 并入项第 1 条：`user_version` 纠偏（前置，已先于 `SCHEMA_VERSION` 变更落地）

**选的是「加纠偏逻辑」，但纠偏的判据不是版本号本身，而是列。** 理由：跳号到 3 会让 2 永远是一个语义未定义的空号，此后每个读版本位的人都得记住这个坑；而无论选哪种，问题的根子都在「**recorded revision 是一个关于布局的声明，不是布局本身**」——一旦声明与事实不符，任何只读版本号的方案都会再错一次。所以迁移改为**列驱动**：`reconcile_columns` 读 `PRAGMA table_info(todos)`，缺哪列补哪列（全部可空，`ALTER TABLE ADD COLUMN`，既有行不重写），然后才处理版本位：

- `stored == SCHEMA_VERSION`：不动（被误盖成 2 的旧库正好落这里，而它的列已经在上一步补齐了）；
- `stored > SCHEMA_VERSION` 且一列都没缺：只可能出自更新的 build，保留并 `log::warn!`；
- 其余（含 `stored > SCHEMA_VERSION` 却缺列，即误盖的一般情形）：补完列后把版本位改写为 `SCHEMA_VERSION`，并记一条 warn 说明是在纠偏。

误报告警随之消失：本 build 认得的值就是 2，误盖的库不再落进 `stored > SCHEMA_VERSION` 分支。

**「已被写成 2 的旧库」的实测证据**（要点：本机库在 02 走查结束时已被还原为 `user_version = 1`，见 02 实现记录末尾的还原核验，所以现场没有现成的误盖库；下面是先量本机、再按第 1 轮 build 留下的**确定形态**（v1 七列 + `user_version = 2`，即当时 `import_legacy` 在导入事务里写 `LEGACY_IMPORT_VERSION = 2` 的结果）重建该文件，然后让新 build 真跑）：

1. 走查前直接读本机 `%APPDATA%/com.todo.crossplatform/todos.db`：`user_version = 1`、列 = 原七列、0 行 —— 与 02 的还原结论一致。
2. 用 `node:sqlite` 重建误盖库：七列布局 + 两行真实数据（一条带 `due_date`/`reminder_at`，一条 `completed` 带 `completed_at`）+ `PRAGMA user_version = 2`。读回确认：`user_version = 2`，列只有 7 个。
3. `pnpm run tauri:dev` 启动（未删库）。原生日志出现 `Brought the todos table up to schema revision 2 (+14 columns)`，**没有**任何 `... is newer than the ... this build knows` 告警。
4. 在真实运行时内 `nativeCommands.listTodos()`：两行原样返回，`dueDate: "2026-07-23"`、`reminderAt: "2026-07-23T09:30:00.000Z"`、`completedAt: "2026-07-21T10:15:00.000Z"` 逐项无损，新字段读回为空数组/`undefined`。
5. 随后往同一个库写一条**填满全部新字段**的待办并读回（见下「跑法二」），证明补列后的表真的能承载 v2 数据，而不只是列名存在。

Rust 侧另有三个用例锁住这条路径：`a_revision_one_database_gains_the_new_columns_without_losing_data`（stamped 1 的旧库）、`a_database_whose_recorded_revision_overstates_its_layout_is_still_migrated`（**stamped 2 但只有 7 列**，即本条要防的那个文件，迁移后还写入并读回新字段）、`migrating_twice_changes_nothing`（幂等）。

### 契约（`crates/contracts/src/lib.rs`）

- `Todo` 新增 12 组字段：`notes` / `start_date` / `starts_at` / `ends_at` / `estimated_minutes` / `recurrence` / `list_id` / `important` / `urgent` / `sort_order` 为 `Option`（`#[serde(default, skip_serializing_if = "Option::is_none")]` + `#[ts(optional = nullable)]`），`tag_ids` / `subtasks` / `attachments` / `depends_on` 为 `Vec`（`#[serde(default)]`）。
- 新增实体 `Subtask`、`Attachment` + `AttachmentKind`、`RecurrenceRule` + `RecurrenceFrequency` + `RecurrenceCalendar` + `Weekday`，派生与标注与既有 DTO 完全一致（`Clone, Debug, Deserialize, Serialize, TS, Type`、`rename_all = "camelCase"` + `deny_unknown_fields`、`#[ts(rename_all = "camelCase")]`）。
- 校验就近实现为契约方法：`Todo::validate()`、`TodoPatch::validate()`、`RecurrenceRule::validate()`，共用 `validate_id` / `validate_title` / `validate_id_list` / `validate_subtasks` / `validate_attachments`。`ContractValidationError` 增加 8 个变体（`DuplicateEntry` / `InvalidAttachment` / `InvalidEstimate` / `InvalidId` / `InvalidNotes` / `InvalidRecurrence` / `InvalidTimeRange` / `SelfDependency` / `TooManyEntries`）。`TodoSyncOperation::validate()` 里原本内联的 title 检查改为委托 `TodoPatch::validate()`，新字段随之自动纳入服务端校验。
- `TodoPatch` 补齐全部可变字段（含 `reminder_at`），使 op-based 同步的字段级合并覆盖新字段；列表型字段整体替换（`Option<Vec<_>>`，缺省=不变）。
- **`#[ts(optional)]` 与实际写入形状的一致性**（01 踩过的坑）：可空标量一律 `optional = nullable`（前端确实写 `null`）；列表型字段前端只会写 `[]`、绝不会写 `null`，因此不加 `#[ts(optional)]`（ts-rs 也只允许它用在 `Option` 上），生成为必填数组。为此还踩到一个真实的生成器约束：`#[serde(default)]` 不配 `skip_serializing_if` 会让 specta 把序列化/反序列化两个方向的形状**拆成两个类型**，嵌套类型一旦被拆成联合就与 ts-rs 产物不兼容（`Todo_Serialize[]` 无法赋给 `Todo[]`，`pnpm run check` 实测报 TS2322）。因此**新造的嵌套类型不加 serde 默认**（`Subtask.done`、`RecurrenceRule.on_last_day` / `calendar` 为必填）——它们没有任何历史形状需要兼容，加默认只会多制造一处两套形状。

  **（第 2 轮更正）拆型并没有被消除，别照着上一段的字面理解。** 产物现状是：`src/bindings/commands.ts` 里 `Todo`、`Attachment`、`RecurrenceRule` 仍是 `_Serialize | _Deserialize` 两型（`Todo_Deserialize.tagIds?: string[]` vs `Todo_Serialize.tagIds: string[]`），只有 `Subtask`（以及本轮新增的 `WriteRejection`）落成单型。对着产物复核后的准确机制是：**任何让两个方向形状可能不同的 serde 属性**都会触发拆型——无 `skip_serializing_if` 的 `#[serde(default)]` 是一种（`Todo` 的四个列表字段、`RecurrenceRule.weekdays`，两侧确实一必填一可选），`skip_serializing_if` 本身也是一种（`Attachment.name`，两侧渲染完全相同却照样拆）。这两类属性一个都不带的类型才落成单型，本仓库里就是 `Subtask` 与本轮新增的 `WriteRejection`。所以上一段的正确读法是「不给新类型**再添**拆型理由」，而不是「新类型都没被拆」。结论本身不受影响：新类型无任何历史载荷，旧载荷缺新字段由 `#[serde(default)]` 兜住（`a_payload_without_the_new_fields_still_decodes` 已断言），`deny_unknown_fields` 只拒多字段、与缺字段互不相干。
- 新增 8 个契约用例：v1 载荷（缺全部新字段）仍能解码且 `validate` 通过、全字段 JSON 往返、camelCase 上线形状与缺省字段不上线、未知字段被 `deny_unknown_fields` 拒、`Todo::validate` 的六类拒绝、周期规则的四类拒绝、patch 携带新字段时被校验。`crates/contracts/Cargo.toml` 增 dev-dependency `serde_json`（仅测试用，用真实 JSON 断言线上形状而非从属性推断）。

### 视图端（`src/lib/todo-repository.ts`、`src/stores/todos.ts`、`src/types/todo.ts`）

- **并入项 4（编译期锁定）**：`isTodo` 换成 `TODO_FIELDS`——每字段一条规则（`accepts` / `required` / `fallback`），整体 `satisfies Record<keyof Todo, TodoFieldRule>`。契约新增字段 → 重生成 `Todo` → 该对象不再满足约束 → `pnpm run check` 报错。**已实测**：临时给生成的 `Todo` 加一个 `energyLevel` 字段，`pnpm run check` 报 `TS2741: Property 'energyLevel' is missing ... but required in type 'Record<keyof Todo, TodoFieldRule>'`，指向 `satisfies` 那一行；验证后已还原并重新生成。
- **并入项 6（旧结构无损升级）**：`isTodo`（布尔）换成 `readTodo`（返回补齐后的 `Todo` 或 `null`）。缺新字段的旧条目不是坏数据，而是「没有标签的待办」，按 `fallback` 补成 `[]` 后照常入库——与 Rust `#[serde(default)]` 的读法一一对应。真正读不回的条目才是 `null`。
- **并入项 3（隔离覆盖非启动路径与浏览器）**：新增 `sequester()`，日志的**每一次**写回（`recordPendingUpsert` / `recordPendingDeletion` / `clearPendingWrites` / `settle` / `flushPendingWrites`）都先把读不回的条目搬进隔离键再写；隔离键写不进去时条目**留在日志里**，读不回不构成删除的理由。浏览器运行时因此同样受保护（那里 `todos.items` 就是主存储）。
- **并入项 2（三个吞信号的执行点）**：① `save`/`remove` 原生成功后 `clearPendingWrites` 失败 → 返回 `"degraded"` 并写 error 诊断（行已入库，但日志里那条会在下次重放盖回旧值，不算结清）；② `recordPendingUpsert` **先摘墓碑、摘不掉就不写 upsert** 并返回 `false`（顺序很关键：`replay_pending` 先 upsert 后 delete，两个键同时留着同一 id 会把刚编辑的待办删掉）；③ `quarantine` 返回布尔，隔离失败经 `sequester` 回流到日志，不再无条件重写 `todos.items`。`WriteOutcome` 的三态注释按新语义改写（`stored` = 存储与应用一致、无欠账）。
- **并入项 5（`startupBacklog` 复位）**：`TodoRepository` 新增 `outstanding()`（浏览器实现恒为 0——那里 localStorage 就是主存储，落盘即无欠账）；`noteWriteOutcome` 每次都据此重算 `startupBacklog`。横幅从此表示「此刻还欠多少」，不是「启动时曾欠过」。
- `stores/todos.ts`：`add` 与 `applyRemoteUpsert` 的物化补齐列表字段；`applyRemoteUpsert` 的字段级合并**逐字段列全**（漏一个字段就等于该字段静默不同步）。出站 patch 仍只带 title/status/dueDate/completedAt——目前没有任何 UI 能产生新字段的值，等各业务母任务落界面时随之扩展；入站必须先全，否则对端/新版本发来的变更会被丢掉。
- `src/types/todo.ts` 只增再导出（无手写实体），供 repository 的结构镜像引用生成类型。

三条阻塞/建议表面上分散在 Rust 命令、SQLite 读列、TS 日志三处，实际都是同一个缺口的不同切面——**系统发现某份数据处理不了时，没有一条统一的、诚实的出路**，于是各处各自发明了一个：直写路径把它塞进「会重试」的日志（然后重启时丢掉），`decode_json` 把它降级成空值（然后被下一次写抹掉），`settle` 把写失败咽掉（然后横幅在错误的时刻出现）。本轮统一到 02 已经确立的那条出路上：**保留字节 → 隔离 → 诊断 → 让调用方看得见**，并按「重试有没有意义」分流：

| 情形 | 本轮之前 | 本轮之后 |
|------|---------|---------|
| 契约永久拒收的直写 | 进待写日志 → 横幅承诺「重启后会自动补写」→ 重启时被隔离、条目消失 | `WriteRejection.permanent` 带回视图端 → **不进日志** → 立即报 `"failed"`，条目留在列表里 |

| 重放后日志回写失败 | 静默 | error 诊断 + `outstanding()` 如实计入横幅 |
