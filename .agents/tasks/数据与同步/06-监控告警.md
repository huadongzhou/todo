# 监控告警

- 级别：直达
- 状态：完成

## 需求（产品）

- 目标与场景：服务可用性与错误率可观测、异常可告警，公测后问题定位的底线。
- 范围（做 / 不做）：做 健康检查端点、错误率/可用性告警接线；不做 商业化监控平台选型之外的扩展。
- 验收标准（逐条可检查）：
  - [ ] 健康端点可用并纳入探活。
  - [ ] 故障注入触发告警，恢复后告警解除。

### 编排者并入项（来自 04-服务端SQLite持久化 评审第 1 轮，已裁决「转任务处理」）

1. **同步请求的时延观测**（`crates/server/src/lib.rs:106-111`）：handler 在 async 上下文里同步 fsync（`synchronous = FULL`）并抢连接锁，并发超过 worker 数会拖住整个 Tokio 运行时——性质已由内存锁变为磁盘落盘。评审判定行为正确、无吞吐类验收标准，故不改代码；请把同步请求时延纳入本子任务的观测面，有数据支撑时再决定是否改用 `spawn_blocking`。
2. **坏行诊断面**（`crates/server/src/sync_store.rs:139-161`）：读不回的 `sync_changes` 行每被读一次就 `warn` 一次，缺 02/03 端侧那种「一次性隔离 + 可清点」的诊断面。请在告警设计中给出坏行的可清点口径（有多少、从何时起、是否在增长）。

补充验收标准：

- [ ] 健康端点或指标可反映同步请求时延；坏行数量可清点且异常增长能触发告警。

### 编排者并入项（来自 05-备份容灾 评审第 2 轮，已裁决「转任务处理」）

3. **`patch_from_json` 的重解循环是二次方**（`crates/server/src/sync_store.rs:372-410`）：评审 release 实测 10/20 键 → 0.19 ms、50/100 → 4.7 ms、**200/400 → 63 ms**（200 是 `MAX_LIST_ENTRIES` 合法上限），翻倍即四倍；且跑在连接锁里、对读出的**每一行**都跑。与上面第 1 项「同步请求时延观测」是同一件事的两面：先量，再按评审给出的 O(n) 单遍化方案改。
4. **跳过行的日志报的不是真正读不回的原因**（`crates/server/src/sync_store.rs:459-466`）：`{"aaaUnknown":1,"title":42}` 会报 ``unknown field `aaaUnknown` ``，而真正读不回的是 `title:42`——会把回滚现场的操作者引向前滚，而前滚救不了。与第 2 项坏行诊断面是同一处代码。

补充验收标准（追加）：

- [ ] `patch_from_json` 在合法上限规模下的耗时有度量；若确认为瓶颈则已单遍化。
- [ ] 跳过行的诊断报出的是真正导致读不回的字段与原因。

## 实现记录（开发）

### 落点：一个端点、两条本地告警通路，度量记在发生的地方

| 交付物 | 落点 | 形状 |
|-------|------|------|
| 健康端点 | `crates/server/src/lib.rs` 的 `/v1/health`（`create_router` 内，`/v1/` 前缀） | handler 只做「取报告 + 选状态码」；`GET /health` 一字未动，仍是应用问「有没有服务在」的那个 |
| 报告 DTO | `crates/contracts/`（`HealthReport` / `HealthStatus` / `SyncHealth` / `LogHealth` / `RowFaults` / `HealthAlert`） | 与既有 `HealthResponse` 同风格（响应体只派生 `Serialize`），HTTP DTO 仍单源于 contracts |
| 何时算不健康 | `crates/domain/`（`HealthThresholds` / `HealthConcern` / `evaluate_health` / `overall_status`） | 纯规则：只读两个 DTO 的数字，不碰 HTTP、不碰 SQLite |
| 采集 | `crates/server/src/metrics.rs`（新增） | `RequestMetrics`（请求怎么样了）与 `LogObservations`（读这个文件付了什么代价、有什么读不回） |
| 组装与告警 | `crates/server/src/health.rs`（新增） | 独立 service：拼报告、记住每条告警「从何时起」、开与解各写一行日志；`spawn_watch` 线程按 `HEALTH_INTERVAL_SECONDS` 自查 |

**为什么是 `/v1/health` 而不是改 `/health`**：`/health` 被 `src/lib/sync-transport.ts` 用作「能不能连上服务端」的探测（`syncNow` 前先问它）。一个正在忙的服务端应当回答「我在」，把它改成会因为库忙而说「不在」，会让应用误判成离线。所以活性（liveness，`/health`，不看任何东西）与就绪/健康（`/v1/health`，看请求记录与库）分开，两个端点各回答一个问题。

### 观测面：两个问题，两套记录

一台出了问题的同步服务端会被问两件事，本次就记两件事：

1. **请求怎么样了**（`RequestMetrics`，记在 `SyncService::sync` 外圈）：窗口内的请求数、失败数、被契约拒绝数、平均与最慢耗时，加上全程累计数。**「设备发错了」与「服务端答不出来」分开计**——把 400 计入错误率，一台行为异常的设备就能把服务端判死。
2. **读这个日志付了什么代价、有什么读不回**（`LogObservations`，记在 `SyncStore` 里）：等连接锁的最长时间、读不回的行、被降级读出的行。记在 store 而不是 service，是因为它们是「读文件和拿锁」当场发生的事。

两套记录都同时保留**滚动窗口**（120 秒，30 个槽）与**全程累计**：窗口是告警能自己解除的前提（故障停了就滑出窗口），累计是留给事后清理的人的。窗口长度取 120 秒的理由写在 `metrics::WINDOW` 上——够长到一次慢请求不惊动人，够短到修完的人还在看着就能看到解除。

### 先量后改 ①：`patch_from_json` 的二次方重解 —— 确认是瓶颈，已单遍化

**先量**。把 05 的实现与本次的实现**逐行原样**复制进 scratchpad 的临时 crate，对真实 `TodoPatch` 跑同一批输入（release 构建，每档预热一次后取平均；输入＝N 个子任务、每个带 2 个本 build 叫不出名字的键）：

| 子任务 / 未知键 | patch 字节 | 05 实现 | 本次单遍 | 倍数 |
|---------------|-----------|--------|---------|------|
| 10 / 20 | 995 | 0.198 ms | **0.024 ms** | 8× |
| 25 / 50 | 2 435 | 1.130 ms | **0.063 ms** | 18× |
| 50 / 100 | 4 835 | 4.144 ms | **0.118 ms** | 35× |
| 100 / 200 | 9 635 | 15.829 ms | **0.219 ms** | 72× |
| 200 / 400 | 19 435 | **60.226 ms** | **0.471 ms** | **128×** |
| 200 子任务、无未知键（日常路径） | 9 035 | 0.018 ms | 0.018 ms | 持平 |

05 评审报的 200/400 → 63 ms 复现无误（本机 60.2 ms），翻倍即四倍也复现；改后逐档翻倍即翻倍，是线性的。**日常路径（严格解一次即成功）前后完全一致**——两条实现在没有未知字段时都只跑一次 `from_str`。

**再量端到端**，因为「跑在连接锁里、对每一行都跑」才是它真正的代价形状：用 python 直接造一个「超前一版的 build 会留下的」日志（50 行，每行 200 子任务、每子任务 2 个未知键，645 KB），用 `git archive HEAD` 在 scratchpad 里编出 **05 的二进制**、和本次的二进制，各自对**同一份库**做 `cursor: 0` 全量拉取：

| | 05 二进制 | 本次二进制 |
|---|---|---|
| 三次全量拉取 | 4 458 / 5 066 / 5 040 ms | **47.9 / 47.1 / 46.6 ms** |
| 三次拉取产生的 warn 行 | **150 行**（每行每读一次） | **50 行**（每行一次） |
| 服务端自报最慢请求 | 无此端点 | 27.5 ms（差额是 HTTP 序列化与传输，在服务调用之外） |

一次回滚期间的全量拉取从 **5 秒**（全程占着连接锁，别的设备全在排队）降到 **47 毫秒**，约 107×。**结论：是瓶颈，已按评审给的 O(n) 方向改。**

**怎么改的（与评审给的方案有一处不同，理由如下）**。评审建议「`next_key_seed` 拒到名字后不立刻 `Err`，用 `IgnoredAny` 吃掉值再继续」。这条在 Rust 里走不通：`DeserializeSeed::deserialize(self, …)` 消耗 seed，被拒的那个键已经把 seed 吃掉了，同一次 `next_key_seed` 调用里没有第二个 seed 可以用来接着问下一个键（实测编译错误 E0382）。所以换了个提问时机——**问 serde 要字段表**：派生代码调用的是 `Deserializer::deserialize_struct(name, FIELDS, visitor)`，`FIELDS` 正是那个结构体**编译时**带的名字表，在**任何深度**都由它自己交出来。`Watched` 于是实现 `deserialize_struct`，在把键交给 seed **之前**就用这张表筛掉认不出的名字、记下位置、继续读下一个键。一遍读完收齐全部未知名字，摘干净后**再做一次**严格解——交出去的 patch 仍然是普通 serde 从摘干净的 `Value` 解出来的，适配器仍然只负责指位置。这既不是在 server 侧抄一份会漂移的清单（表来自 contracts 的编译产物），也没有削弱「认识但值坏 → 整行跳过」那条红线。

`deserialize_any` 保留了旧的「等 seed 拒」路径作为退路：只有 `#[serde(flatten)]` 的结构体不给 `FIELDS`，contracts 里没有。

**差分核验**：把两份实现放进同一个二进制，对 20 条输入逐条对照（评审第 1、2 轮列过的路径归属反例、同名跨层、跨类型同名、坏值与未知名字的六种先后组合、重复键、缺必填字段、非 JSON），**「送出 / 跳过」的判定与 dropped 名单逐条一致**，无一条降级。差异只在跳过时报的原因上——那正是并入项 ④ 要的改变，见下。

### 先量后改 ②：handler 的同步 fsync —— 确认拖住运行时，已改 `spawn_blocking`

**先量**（release 二进制、32 核机、单独一台 client 每 20 ms 打一次 `GET /health`，PORT=3111、`BACKUP_INTERVAL_SECONDS=0`）：

| 并发 | sync p50 / max（改前） | `/health` p50 / max（改前） | sync p50 / max（改后） | `/health` p50 / max（改后） |
|-----|--------------------|------------------------|--------------------|------------------------|
| 1（逐个） | 0.67 / 27.8 ms | — | 0.69 / 1.6 ms | — |
| 8 | 1.56 / 24.4 ms | 0.69 / 0.83 ms | 2.12 / 20.2 ms | 0.70 / 0.93 ms |
| 32 | 15.98 / 40.4 ms | 0.45 / 17.7 ms | 13.85 / 53.1 ms | 0.43 / 0.91 ms |
| 64 | 56.5 / 103.8 ms | **18.2 / 69.8 ms** | 52.1 / 116.4 ms | **0.46 / 26.0 ms** |
| 128 | 132.8 / 352.5 ms | **62.9 / 240.5 ms** | 161.7 / 386.3 ms | **0.42 / 64.3 ms** |
| 256 | 290.1 / 1772 ms | **123.4 / 592.3 ms** | 581.8 / 677.5 ms | **0.52 / 25.7 ms** |

吞吐（256 并发）450/s → 433/s，在噪声内；256 并发下 sync 的 **max 从 1772 ms 降到 678 ms**（阻塞池是先来先服务，工作窃取则不是），p50 反而变大，属同一现象的两面。

**数据说了两件事，指向同一个决定**：

1. **排队排在连接锁上，不在运行时**。服务端自报：64 并发时最慢请求 69.5 ms，其中 **68.6 ms 是等连接锁**。这解释了为什么 `spawn_blocking` 不改善吞吐——也说明「fsync 慢」不是当前的形状（单发 0.67 ms）。这条是把 lock wait 单独记出来才看得到的，所以它值得占一个指标位。
2. **但异步 worker 确实被占住了**：改前 256 并发下 `/health` p50 123 ms、max 592 ms——**恰恰是最需要它回答的时候答不上来**；改后 p50 0.5 ms、max 26 ms，250 倍。本子任务交付的正是「服务端能不能自己报告状态」，让报告在负载下失真，等于交付一个只在闲时准的仪表。

因此 `async fn sync` 改为 `tokio::task::spawn_blocking`，新增 `ServerError::Interrupted`（任务被中断/panic，映射同既有 500、响应体不变）。数据与理由写进 handler 的文档注释，含上表。

### 诊断质量 ①：坏行可清点

`read_change` 不再每读一次 warn 一次。`LogObservations` 按 revision 去重登记两类行，**第一次遇到才写日志，之后只计数**：

- `unreadableRows`：谁也读不回的行（revision 越界 / kind 认不出 / patch 读不回）——设备永远收不到它们。
- `partlyReadRows`：能送出、但少了本 build 叫不出名字的字段的行——回滚期间的形状，前滚就能救回来。

两类**分开计**，因为要做的事相反：一个前滚就好，另一个前滚没用。每类报五个数：`rows`（去重后有多少）、`reads`（被读过多少次，即旧口径会刷多少行日志）、`firstSeenAt`（从何时起）、`newestSeenAt`（最近一条是什么时候发现的）、`newest`（最近一条是哪一行、哪个字段、什么原因）、`newInWindow`（窗口内新增几条 —— 「是否在增长」）。

**告警只看 `newInWindow`**：还在长才告警，停了就自动解除，而 `rows` 留在报告里给事后清理的人。一条永远解除不了的告警等于没有告警。

日志行本身也收了口：一个 patch 合法上限是 200 个子任务，回滚时能带 400 个未知名字，全打出来是一行没人读得完的字（实测 05 的口径下这一行约 10 KB）。`named()` 只报前 5 个再说「and N more」——足够判断是哪一类字段，也就足够决定要不要前滚。

### 诊断质量 ②：跳过行报的是真正读不回的原因

05 的实现在跳过时报的是**最初那次严格解**的错误。`{"aaaUnknown":1,"title":42}` 会报 `unknown field \`aaaUnknown\``，把回滚现场的操作者引向前滚，而前滚救不了 `title: 42`。

`Watched` 现在除了记未知名字，还在 `next_value_seed` / `next_element_seed` 的失败路径上记下**最内层**那个读不下去的位置（内层先失败，所以第一条记录就是最贴近出错值的那条）。`patch_from_json` 的失败改为返回 `PatchFault { field, reason, dropped }`：`field` 与 `reason` 是真正让它读不下去的那一个，`dropped` 是路上摘掉的未知名字，作为**上下文**排在后面。日志行随之变成：

```text
WARN skipping a sync log row with an unreadable patch (once per row; the count is in /v1/health)
     revision=2 operation_id=op-2 field=title error=invalid type: integer `42`, expected a string dropped=aaaUnknown
```

嵌套同理：`{"subtasks":[{…,"done":"maybe"}]}` 报 `field=subtasks.0.done`；缺必填字段报 `field=subtasks.0` + `missing field \`id\``；重复键与非 JSON 无字段可归，报 `the patch itself`。演练 A 第 3 步是真实进程下的实测。

### 告警：判定在 domain，通道只用本地两条

`evaluate_health` 是纯函数（`crates/domain/`），只读两个 DTO 的数字：

| 名字 | 何时开 | 级别 | 阈值与理由 |
|------|-------|------|-----------|
| `sync_log_unreachable` | 上次探测既没答上也不是「忙」 | unhealthy | 无阈值。**「忙」不算病**：探测不等锁，正在服务的服务端本来就会答忙，拿它告警等于在服务端最正常工作时报警 |
| `sync_failure_rate` | 窗口内失败/请求 ≥ 50%，且请求数 ≥ 3 | unhealthy | 自托管服务端面向的是几台设备，3 不是样本量而是「不止一次出错」；失败只计「日志答不出来」，契约拒绝另计 |
| `sync_slow` | 窗口内最慢 ≥ 1000 ms | degraded | 上表实测：单发 < 1 ms、64 并发最慢约 120 ms。1 秒是健康状态够不到的数，只会为坏盘或远超自托管规模的排队而响 |
| `unreadable_rows_growing` | 窗口内新出现读不回的行 | degraded | 见上：只看「在不在长」 |
| `partly_read_rows_growing` | 窗口内新出现降级读的行 | degraded | 同上，且它提示的动作是「把二进制前滚回去」 |

**通道**（这是本轮刻意收窄的地方）：自托管单文件服务端默认不接任何监控系统，所以只做服务端自己能做的两条——

1. **HTTP 状态码**：`/v1/health` 在 unhealthy 时回 **503**，ok/degraded 回 200。探活探针（uptime 监控、容器 healthcheck、反代健康检查）直接接这一个 URL 即可，不需要解析 body。degraded 不回 503，是不想让一次慢请求把服务从轮转里摘掉。
2. **日志行**：告警**开**写 `ERROR ... health alert opened`，**解**写 `INFO ... health alert cleared`，都带 `alert=<稳定名字>`；只在状态跳变时写，不重复刷。`spawn_watch` 线程按 `HEALTH_INTERVAL_SECONDS`（默认 60，0 关闭并 warn）自查一次，所以**没人来拉 `/v1/health` 也照样有告警落到日志里**。

**邮件 / webhook / 托管监控一律没做**：属选服务商、可能涉及采购与备案，按 workflow 全局规则 5 与本任务范围边界，交用户拍板（见遗留问题 1）。多区域部署同样未碰（归 发布工程/14）。

### 分层与规范符合性

- **`/v1/` 前缀**：`/v1/health` 注册进 `create_router`；handler `health_report` 只做「取报告 → 选状态码 → Json」三行，判定全在 `HealthService` 与 `todo_domain`。

### 遗留问题（供编排者裁决，本轮未做）

1. **外部告警通道未选型（需用户拍板）**：邮件 / webhook / 托管监控接入涉及选服务商、可能有费用与备案，按 workflow 全局规则 5 与本任务范围边界未擅自决定。本轮交付的是两条不需要外部依赖的通路（503 状态码 + 结构化日志行，告警名字稳定可 grep）。接第三方时的落点已经就位：`HealthService::reconcile` 是唯一的状态跳变点，加一个通知器只需在那两条日志旁边多调一次。
2. **阈值是常量，不可配置**：`min_requests=3` / `failure_ratio=0.5` / `slowest_millis=1000` 与窗口 120 秒都写死在 `HealthThresholds::default()` 与 `metrics::WINDOW`，只有自查间隔 `HEALTH_INTERVAL_SECONDS` 可配。理由是「不做没要求的可配置性」，且阈值有实测支撑；真有多规模部署需求时再按 `BACKUP_*` 的风格补环境变量。
3. **坏行清点是「进程内 + 被读到过」的口径**：从没有任何设备的 cursor 落在它下面的坏行不会被计入（它也确实还没伤到任何人），进程重启后计数归零（`firstSeenAt` 同样是本次启动后的第一次）。要给出「库里一共有多少坏行」需要整表扫描，那是每次探活都做不起的活；若将来需要，宜作为一次性子命令（如 `todo-server check`）而不是塞进健康端点。
4. **`/v1/health` 无鉴权**：与 `/v1/sync` 现状一致（TODO 5.x「服务端鉴权：/v1 接口携带凭证」尚未做）。报告里含 revision 数、请求量与坏行的字段名，属运维信息，公网直连时会被匿名读取——建议在做服务端鉴权时把 `/v1/health` 一并纳入（或只对 `/health` 保持匿名）。
5. **快照耗时未单独计时**：05 遗留问题 3 建议把「快照耗时」纳入 06 观测面。本轮**部分**满足——`VACUUM INTO` 走同一把连接锁，拍照期间的暂停会体现在 `lockWaitSlowestMillis` 与请求时延里，但没有一个「上次快照花了多久」的独立指标。日志压实（04 遗留问题 1）未做前，这两者仍相关。
