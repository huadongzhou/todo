# 监控告警

- 级别：直达
- 状态：开发

## 需求（产品）

- 目标与场景：服务可用性与错误率可观测、异常可告警，公测后问题定位的底线。
- 范围（做 / 不做）：做 健康检查端点、错误率/可用性告警接线；不做 商业化监控平台选型之外的扩展。
- 验收标准（逐条可检查）：
  - [ ] 健康端点可用并纳入探活。
  - [ ] 故障注入触发告警，恢复后告警解除。

### 编排者并入项（来自 04-服务端SQLite持久化 评审第 1 轮，已裁决「转任务处理」）

1. **同步请求的时延观测**（`crates/server/src/lib.rs:106-111`）：handler 在 async 上下文里同步 fsync（`synchronous = FULL`）并抢连接锁，并发超过 worker 数会拖住整个 Tokio 运行时——性质已由内存锁变为磁盘落盘。评审判定行为正确、无吞吐类验收标准，故不改代码；请把同步请求时延纳入本子任务的观测面，有数据支撑时再决定是否改用 `spawn_blocking`。
2. **坏行诊断面**（`crates/server/src/sync_store.rs:139-161`）：读不回的 `sync_changes` 行每被读一次就 `warn` 一次，缺 02/03 端侧那种「一次性隔离 + 可清点」的诊断面。请在告警设计中给出坏行的可清点口径（有多少、从何时起、是否在增长）。

补充验收标准：

- [ ] 健康端点或指标可反映同步请求时延；坏行数量可清点且异常增长能触发告警。
