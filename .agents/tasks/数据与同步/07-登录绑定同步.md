# 登录绑定同步

- 级别：直达
- 状态：开发

## 需求（产品）

- 目标与场景：同步归属从 deviceId 升级为账号，换机登录取回数据。（外部前置：账号与登录/01–02 完成）
- 范围（做 / 不做）：做 同步链路账号化、deviceId 与账号关联迁移；不做 账号本体（账号与登录母任务）。
- 验收标准（逐条可检查）：
  - [ ] 同步随账号而非仅 deviceId；换机登录取回全部数据。
  - [ ] 未登录不同步且不报错阻断；cargo test 覆盖归属迁移。

### 编排者并入项（来自 05、06 评审，均已裁决「转任务处理」）

1. **恢复会回退 revision 序列**（来自 05 评审第 1 轮）：从快照恢复后，游标已越过快照的设备会**永久漏掉**恢复后重发的那些编号（05 演练 A 实证：op-4/op-5 撞号 revision 4，老设备 `cursor:4` 拿到 `changes=0`）。当前运维口径是「恢复后让设备重置 cursor 全量重拉」，仅打在 restore 日志里。根治需要给日志加「世代号」并让设备据此重拉。
2. **跳过行仍推进 `nextCursor`**（来自 06 评审第 1 轮）：读不回的行被跳过后游标照样前进，设备游标越过后**永不再读**——因此坏行计数是一次性的、重启归零且无法重新发现，`rows=0` 不等于库里没坏行。

这两条是同一个问题域：**游标语义，以及「设备该重拉哪一段」的定义**。本子任务把同步从「仅 deviceId」改为「随账号」，正是重新定义设备身份与游标归属的地方，请一并想清楚，不要只做账号绑定而把游标语义原样搬过去。

补充验收标准：

- [ ] 服务端从快照恢复后，已越过该段编号的设备能自动察觉并重拉，不需要人工重置 cursor（须以演练证明）。
- [ ] 存在读不回的行时，设备不会因游标前进而永久错过它；坏行可被重新发现（例如全量重扫或世代号驱动的重拉）。
