# 邮件通道与密码找回

- 级别：直达
- 状态：开发

## 需求（产品）

- 目标与场景：外发邮件通道（SMTP/第三方，选型定案）与忘记密码邮件重置流程。
- 范围（做 / 不做）：做 通道封装、重置 token、重置流程；不做 注册验证邮件之外的营销邮件。
- 验收标准（逐条可检查）：
  - [ ] 忘记密码收信重置成功；重置 token 一次性且限时。
  - [ ] 通道凭证经环境配置注入，不入库不进仓库。

### 编排者并入项（用户 2026-07-23 拍板：服务端告警走邮件通知）

**邮件通道须同时服务两个消费方，不得只按密码找回设计：**

1. **密码找回**（本子任务原有范围）。
2. **服务端告警出站通知**（来自 数据与同步/06 评审第 1 轮第 7 条，用户已选定「邮件通知」档）：`06-监控告警` 已交付 `/v1/health`（503 探活）与结构化日志两条**被动**通路，缺的是无人值守时的主动通知。接入点已由 06 收口在 `crates/server/src/lib.rs` 的 `HealthService::reconcile`——告警开启与解除各触发一次通知即可，不要每次自查都发。

因此通道要做成可被两处复用的 service（一个发送抽象 + 一份配置），而不是嵌在密码找回流程里的私有函数。告警邮件的收件人是**运维方**（自托管者本人），与用户邮箱是两类地址，配置上要分开。

**外部前置（阻塞项，须用户先拍板）**：SMTP 服务商与凭据尚未选定，涉及费用、可能涉及备案与发信域名配置。本子任务可以先把发送抽象、配置形状、失败重试与本地假发送（dev 模式打日志不真发）做完并测通，但**「真实发信可用」这条验收标准在服务商定下来之前无法达成**——届时请停下上报，不要自行选购或写死某家服务商。

补充验收标准：

- [ ] 邮件发送为独立 service，密码找回与告警通知两处复用同一抽象与配置。
- [ ] 告警通知在告警开启与解除时各发一次，不随自查间隔重复发送（须实测）。
- [ ] 运维收件人与用户邮箱在配置上分离。
- [ ] dev 模式下不真实发信但可验证调用（本地假发送 + 日志）。
- [ ] 【待外部前置】真实 SMTP 通道发信成功——服务商未定前此条挂起，不得以假发送冒充通过。
