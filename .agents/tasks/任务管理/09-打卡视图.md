# 打卡视图

- 级别：简化
- 状态：开发

## 需求（产品）

- 目标与场景：每日/每周周期任务以习惯打卡形态展示（原独立习惯模块并入此处）。
- 范围（做 / 不做）：做 打卡/补卡交互与连续记录；不做 热力图统计（视图与统计 7.4）。
- 验收标准（逐条可检查）：
  - [ ] 打卡/补卡可用，连续记录（streak 数据）正确入库。
  - [ ] 打卡即完成当日实例，与 08 实例生成一致。

## 规格（UI/UX）

本节接着 `任务管理/08`（周期标识 pill、`completeRecurring` 完成即生成下一实例、`recurrenceLabel`）与 `05`（归档区「区非页」的可搬迁做法、「不新增第四类提示来源」、`.ts` 扫描与 `focus-ring` 两条既有缺陷的书写口径）写。上述已定而本节未明写改动的，一律继承不动。

> **一句话结论（供快读）：** 打卡视图**不是新列表、不是新区块、不是新页**——它是主列表里**每日/每周周期任务那一行的呈现变体**：完成圈即打卡（＝08 的 `completeRecurring`），行内增一枚 streak pill 与「补卡」按钮。但**「补卡」与「streak 入库」都表达不了于 08 的完成/生成模型之上**——两者都需要一份契约里还不存在的「打卡历史」数据（见第 3、8 节）。因此本规格把交互写全、把数据前置点明，**状态保持「设计」，请编排者先裁决第 8 节的契约/数据前置与实例语义分叉，再决定进「开发」**。

### 0. 现状核对（写规格前实读）

### 1. 表态：变体，不是列表 / 不是区 / 不是页

**结论：打卡视图＝主列表里「每日/每周周期任务」那一行的呈现变体（增强版 `TodoItem`），就地渲染。不新增列表、不新增区块、不新增页、不新增路由、不新增导航。**

编排者点名要在「主列表变体」与「独立区域/页面」之间选一个，逐条给理由：

| 候选形态 | 为什么不选 |
|---------|-----------|
| **独立页 / 视图切换** | 导航壳（`桌面端形态/01`）与视图切换（`视图与统计`）都还没做（均在「拆解」态）。自建一套导航去装「打卡页」，就是造一个三个月后被 `桌面端形态/01` 整体替换的模式——与 05 第 4.1 节拒绝自建「归档页」、08 不自建详情面板是同一条理由。 |
| **独立「打卡区」（仿 05 归档区的 disclosure）** | 05 的归档区能独立成立，是因为**归档件已被 `visibleItems` 过滤出主列表**，放进区里不产生重复。习惯不同：它是**活任务**，必须留在主列表里才能被勾选完成/打卡。若再开一个「打卡区」列出同一批习惯，要么它们在页面上出现两次，要么得先把它们从主列表过滤掉——而「主列表按类型过滤」这个接缝归 `视图与统计`（05 第 4.5 节已把 `visibleItems` 留成唯一过滤口径，新增过滤维度不该由本任务私自加）。 |
| **主列表变体（选它）** | 需求原文「每日/每周周期任务**以习惯打卡形态展示**」「原独立习惯模块**并入此处**」——习惯不再是独立模块，而是周期任务的一种呈现。8/05 已经让周期任务的 open 实例就在主列表里、带周期 pill；本任务只是给「每日/每周」这一档再叠加 streak 与补卡。**可搬迁性**与 05 归档区等价：增强逻辑全部收在 `TodoItem` 的周期分支里、只读 store，导航壳/习惯视图落地那天，是「换一个容器渲染同一个增强行」，行内一行不改。 |

**「不是又一个列表」如何在结构上成立：** 本任务**不**新增任何 `v-for`、不新增任何 `<section>`、不新增任何组件文件；所有新增元素都长在 `TodoItem.vue` 非编辑态中列内部（徽标行 + 其下一行补卡按钮）。它对行的**横向宽度零增加**（沿用 08 的 `flex-wrap` 中列换行），最坏只是习惯行在窄屏多折一到两行。

**作用范围（哪些行是「习惯」）：** 仅 `recurrence.frequency ∈ {daily, weekly}` 的 open 实例。`monthly/yearly/workday/lunar` 与一次性任务**不加** streak/补卡，维持 08 的纯周期 pill——「连续几个月」不是需求要的打卡语义（需求写死「每日/每周」）。习惯身份**由频率推得，不新增 `isHabit` 开关**（少一个契约字段）。

### 2. 要求 a 的正面回答：打卡＝完成圈，不是第二个按钮

**打卡今天这一次＝行首那枚既有完成圈，点它就是 `completeRecurring`。打卡视图不再加一个和完成圈打架的「打卡」按钮。**

- 验收标准第 2 条写死「打卡即完成当日实例，与 08 实例生成一致」。完成圈今天做的正是这件事（`toggle`→`completeRecurring`：完成当前 open 实例＋生成下一实例）。**再摆一个独立「打卡」按钮＝两个控件干同一件事**，既占行宽又要向用户解释区别，是净损失。
- 因此：**完成圈就是打卡按钮**。打卡视图给它加的只有 (i) 完成时**顺带把「这一次的排期日（该 open 实例的 `dueDate`）」记进打卡历史**（这是唯一的新副作用，也是 streak 的数据来源），(ii) 行内的 streak 呈现与补卡入口。
- **完成圈的可访问名随习惯身份走**（呈现层微调，非新增提示源）：每日/每周习惯的 open 实例，圈的 `aria-label` 由「标记为完成」改读「为 {标题} 打卡」，其完成态读「撤销 {标题} 打卡」；非习惯行不变。理由：让读屏用户听到的是「打卡」而非泛泛的「完成」，语义由文字承载、不靠图标。
- **锚点口径与 08 对齐**：打卡记的是「被完成的那一次的排期日」＝该 open 实例的 `dueDate`（08 生成后继时也以 `dueDate` 为锚，见 08 实现记录第二节）。提前完成一个排期在明天的 open 实例，记的就是明天那一格——历史始终按排期日对齐，而非按「点击的墙钟时刻」。
- **撤销一致（04/08 在场）**：08 已把「完成＋插入后继」合成一个 `batch`。打卡新增的「历史写入」必须并进同一个 `batch`，使**一次 Ctrl+Z 连 streak 一起复原**（当前行回 open、后继消失、历史里那一格撤回、streak 回到打卡前）。这是 04「一次撤销＝完全复原」的既定不变量，不新增机制、只往既有 batch 里多加一条。

### 3. 要求 b 的正面回答：补卡——以及它逼出的契约/数据前置

**补卡＝把一个「过去漏掉的排期日」标记为已完成。这是本任务最难、也是最诚实的一点：08 的「完成当前实例→生成下一实例」模型里，没有任何地方能表达它。**

**为什么 08 的模型表达不了补卡（三条，都是结构性的）：**

1. **漏掉的排期日不留痕**：没打卡时，到期路径 `advanceRecurrences` 只把那一个 open 实例的 `dueDate` 往前挪，不生成任何「周一那次」的记录。等你想补周一，列表里根本没有「周一那一次」可勾。
2. **没有补进历史的操作**：`completeRecurring` 只作用于**当前 open 实例**并生成**下一次**；它无法「插入一条排期在过去、状态为已完成的实例」。硬要做，就得凭空造一条 `dueDate=周一、status=completed` 的 Todo 行——那正是「又一个列表」：每补一次卡多一条行，且补进来的行还会污染归档区与列表。
3. **实例之间没有系列身份**：就算造了那条行，它也无从归到「同一个习惯」名下（`buildNextInstance` 不写系列 id，第 0 节）。streak 要「把这个习惯的历次打卡连起来数」，靠 `title` 归组既不可靠也会串味。

**结论：补卡与 streak 都需要一份「打卡历史」——一个稳定的习惯身份 + 一组已打卡的排期日期。这两样契约里都没有，是本任务的契约/数据前置（第 8 节）。**「具体字段形态由开发定」，但 UI/UX 必须点明：**光靠 08 的完成/生成模型，补卡和 streak 无处安放。**

**补卡的交互（数据到位后即可落地，形态已定死）：**

- **补卡目标＝有界窗口内、排期日已过、且未打卡的那几天**，逐个呈现为一枚 **`补 周一` / `补 3日` 小按钮**（`Button` `ghost` 变体，`min-h-11`＝44px 触控达标，宽度随文字，见第 5 节）。窗口有界：每日取**近 7 个排期日**、每周取**近 2–3 个排期周**；并**封顶（最多 3 枚，取最近的）**——补更久以前的卡不是打卡场景（那时 streak 早断了，属回顾，归 7.4）。这条上界也是本任务与「热力图」的物理分界：本任务只给**少量、近期、可操作**的补卡入口，不铺整张日历格。
- **没有漏打时，一枚补卡按钮都不出现**（常态）。规律打卡的人看到的只有 streak pill；漏了几天的人才看到 1–3 枚补卡按钮，而那时 streak 多半已归零、pill 反而不在——两者常态上**互斥**，不会同时堆满一行。
- **补卡只写打卡历史，不建行、不碰任何 Todo 实例**（这正是「必须有历史数据结构」的原因——实例模型没处放它）。写入后 streak 依历史重算。补卡是一条独立的可撤销 `change`（撤销＝把那一格从历史移除、streak 回退），与打卡的 batch 各自独立。
- **只能补排期日**：非排期日（如「每周一三五」习惯的周日）不出现补卡按钮——排期由引擎定义。

### 4. 要求 c 的正面回答：连续记录（streak）的呈现，与热力图划界

**streak＝从「最近一个已到的排期日」向回数、连续被打卡的排期发生次数**；单位随频率：每日→天、每周→周。

- **文案**：`连续 N 天`（daily）/ `连续 N 周`（weekly），前置 lucide `Flame` 图标（描边、`:size=14`，与 08 pill 图标同档）。
- **算不算「今天还没打」**：今天（或本周）这个**当前排期尚未结束**的窗口**给宽限**——尚未打卡不算断，streak 照常显示（数到上一个已完成排期），打了卡则 +1。断裂只由**已经过去、且没补上的排期日**触发。
- **断了怎么显示**：streak 归 0。**0 时不显示 pill**（空状态＝无 pill，不摆「连续 0 天」占位）。补上最近漏的那格后，streak 依历史重算、pill 重新出现。
- **N=1 是否显示**：显示（`连续 1 天`/`连续 1 周`）——第一次打卡就给正反馈，符合习惯养成动机；只有 0 不显示。
- **数据来源**：streak 是**打卡历史（那组排期日）对排期表的纯函数派生**，不落一个会漂移的独立计数器。验收标准第 1 条「streak 数据正确入库」由此满足——**入库的是历史（原始事实），streak 是从它读出来的**，不存在「计数器与事实不符」的中间态。
- **派生放哪**：数「连续排期日」需要枚举窗口内的排期日（第 0 节：引擎今天只会向后走一次、没有 previous/区间枚举）。这属**领域逻辑，应走同一个周期引擎**（Rust/domain），不在前端另写一套日历——与 08「全应用只有一处读日历」同源，跨月/夏令时/农历边界才不会与实例生成给出两套答案。

**streak 数字/状态（本任务）与 热力图（`视图与统计 7.4`）的界——写死，供两边对照：**

| | 本任务 09（呈现） | 7.4 回顾与激励（统计） |
|---|---|---|
| 交付物 | 单个习惯行内的 **streak pill（一个数）** + 少量**近期补卡按钮** | **完成热力图**（整张日历格）、跨全部任务的**「连续完成天数」**、成就周报/徽章/分享卡 |
| 作用域 | **单个习惯**：这一个习惯连续做了 N 次 | **跨全部任务**：任意任务当天有完成、连续 N 天（与本任务的「单习惯 streak」不是一回事） |
| 可视化密度 | 一个 pill + ≤3 枚按钮，**不铺格子** | 逐日方格网格（heatmap） |
| 位置 | 主列表习惯行内 | 成就页（`7.4`，独立汇总视图） |

要点：**7.4 也列了「连续完成天数（streak）」，但那是「跨全部任务的每日完成 streak」，与本任务「某一个习惯的连续打卡」作用域不同**；本任务不做跨任务聚合、不做任何方格网格、不做徽章/分享。本任务只在**那一个习惯行**上回答「这个习惯我连着做了几次、最近漏的能不能补」。

### 5. 五项产出（组件级）

**结构与布局**

- 落点：`TodoItem.vue` 非编辑态、且 `todo.recurrence?.frequency ∈ {daily, weekly}` 的中列。**编辑态不出现任何打卡元素**（沿 01 既定：编辑态 Tab 序只有表单）。
- 新增两处，都在中列内部：
  1. **streak pill**：并入 08 既有徽标行 `<p class="flex flex-wrap gap-2">`，排在周期 pill **之后**（顺序：到期 → 周期 → **streak** → 将来）。非交互 `<span>`，仅 streak ≥ 1 时渲染。
  2. **补卡按钮行**：徽标行 `<p>` **之下**另起一个 `<div class="mt-1 flex flex-wrap gap-2">`——**按钮不能放进 `<p>`**（`<p>` 内不得含交互控件），故补卡按钮单独成行。仅当窗口内有「已过且未打」的排期日时渲染，最多 3 枚。
- Tab 序：完成圈 → 标题 → 补卡按钮（0–3）→ 复制 → 删除；DOM 顺序＝视觉顺序。
- 纯文字逻辑函数放 `src/lib/`（只产出文字、无类串）：`streakLabel(count, frequency): string`；补卡按钮日期文案（如「补 周一」）同理。**颜色/`dark:` 类串一律字面写在 `TodoItem.vue`**（第 6 节）。
- 复用图标：lucide `Flame`（streak）。**不用 emoji `🔥`**（DESIGN 禁忌「emoji 充当图标」）。dev 落地前确认 `Flame` 在 `lucide-vue-next`（同 08 对 `Repeat` 的确认口径；`Flame` 为 lucide 标准图标）。

**状态（默认/悬停/聚焦/加载/空/错误）**

| 元素 | 状态 | 表现 |
|------|------|------|
| streak pill | 默认（N≥1，open 实例） | emerald 底 pill：`inline-flex items-center gap-1 rounded-md px-1.5 py-0.5 text-xs font-medium bg-emerald-100 text-emerald-700 dark:bg-emerald-900/40 dark:text-emerald-300`＋`<Flame :size="14" aria-hidden="true" />`＋`<span class="sr-only">连续记录：</span>`＋文案 |
| streak pill | 完成态实例 | 随完成行褪色：去底、`text-slate-400 dark:text-slate-500`（照抄 08 周期 pill 完成态那对互斥类分支，不靠同权重类拼 emit 顺序） |
| streak pill | 悬停/聚焦/加载 | 非交互、不可聚焦、不进 Tab；历史随 todo 同步到达、无异步、无骨架 |
| streak pill | 空（N=0 或非习惯） | 不渲染，无占位 |

### 8. 契约/数据前置与实例语义分叉（保持「设计」，交编排者裁决）

本任务与 08 的根本差别：08 只消费既有的 `recurrence`；**本任务的补卡与 streak 需要一份契约里不存在的「打卡历史」数据**。以下三件都不是 UI/UX 能私自决定的，按全局规则 5 写在此、状态保持「设计」、停下报告编排者：

**前置一（契约/数据·必办）：打卡历史。** 至少要能表达「某个习惯 + 一组已打卡的排期日期」。具体字段形态由 dev 定，但**两块信息缺一不可**：① **稳定的习惯身份**（现状 `buildNextInstance` 每次换新 id、不留系列指针，无法把历次实例归组）；② **已打卡排期日的集合**（现状漏打不留痕、无插入历史的操作）。这是 05 加 `archived_at` 那种「dev 随实现补契约＋重生 bindings」的同类前置，但比一个可空时间戳重——所以先请编排者确认要不要做、是否因此把本子任务从「简化」上调或再拆（打卡历史落库 vs 打卡视图呈现）。

**前置二（引擎·配套）：排期日枚举。** streak 要「从最近一个排期日向回数连续打卡」，需枚举一段窗口内的排期日；引擎今天只有向后走一次的 `next_occurrence`（`crates/domain/src/recurrence.rs:133`），没有 previous/区间枚举。属 domain 侧一处薄扩展（从习惯锚点向前走、或加 previous_occurrence），随前置一一并落。

**前置三（产品/架构分叉，请产品或编排者定）：习惯的实例语义——两个自洽模型，UI/UX 推荐模型 B。**

| | **模型 A：实例串 + 历史（贴字面）** | **模型 B：单行习惯 + 历史（推荐）** |
|---|---|---|
| 打卡 | `completeRecurring`：完成当前实例、生成下一实例，**另记历史** | 只记历史 + 把这一行的 `dueDate` 推进到下次排期，**不生成「已完成」的兄弟行** |
| 与验收第 2 条 | 逐字满足「完成当日实例、与 08 实例生成一致」 | 「打卡即完成当日这一次」语义仍成立，但**不再留完成实例行**——是否算「与 08 实例生成一致」需产品/编排者定 |
| 每日习惯的列表观感 | 08 现状：每次完成留一条完成行、7 天后才归档 → **一个每日习惯最多堆 7 条褪色完成行 + 1 条 open 行**，正撞「不是又一个列表 / 保持列表轻快」 | 一个习惯**恒一行**，历史/streak 长在这行上，无堆积——真正的「习惯打卡形态」 |
| 数据落点 | 历史需系列 id 把散落实例归组（前置一①更重） | 历史天然长在那一行上，**不需要系列 id** |
| 代价 | 沿用 08 分支最省改，但观感与数据都更绕 | 需给「每日/每周习惯」在 `toggle` 里分出一条「不生成兄弟行、只推进本行 + 记历史」的路径，是对 08 完成路径的**受控改写** |

- **UI/UX 立场**：模型 B 才是「习惯打卡」，也最省数据（无系列 id、无行堆积）；但它**重新诠释了验收标准第 2 条**「与 08 实例生成一致」，所以不能由 UI/UX 单方拍板。**无论选 A 或 B，前置一的「打卡历史」都躲不掉**——分叉只影响实例是否照生。
- 请编排者/产品裁决：(1) 采纳哪个模型；(2) 若采纳 B，第 2 条验收标准是否需重述为「打卡即记录当日打卡并推进到下次排期」；(3) 是否因前置一/二把本子任务升级或拆分。**裁决前状态保持「设计」。**

### 9. 开放问题（次级，随裁决一并处理）

1. **端一致性**：`ArchiveSection.vue`（自绘历史行）与 `TodayCard.vue`（独立投影 `TodayCardTodo`，字段已裁剪）**不显示 streak/补卡**——与 08 同样把这两处留作后续端一致性补齐（08 遗留 6 已在案）。今日卡片若要显 streak，需扩同步投影载荷，超「主列表」范围。
2. **补卡窗口上界的确切值**（每日 7 天、每周 2–3 周、封顶 3 枚）是本规格给的默认；若产品对「能补多久」有别的口径，改的是常量与文案，不动结构。
3. **streak 与到期路径的交互**：模型 A 下，逾期习惯被 `advanceRecurrences` 就地推进 `dueDate`（漏打那天不打卡即算断），与 streak「过去排期日未打即断」口径一致，无冲突；模型 B 下由打卡路径自己推进，同样一致。此点两模型都成立，记录在案。

### 编排者裁决（用户 2026-07-24 拍板）

UI/UX 阶段把「习惯的实例语义」升级为需用户拍板的产品/架构分叉，编排者已就两点征询用户，结论：

1. **采纳模型 B：推进本行 + 打卡历史**（UI/UX 的推荐项）。**适用范围＝仅 `RecurrenceFrequency` 为每日 / 每周的周期任务**（＝习惯）；其余频率（每月/每年/自定义间隔/指定星期几/月末/工作日）**维持 08 现状**（完成即生成兄弟实例行）。因此完成路径按频率分流：
   - 每日/每周：打卡＝完成当日实例，但**不生成兄弟已完成行**，而是把该次排期日记进「打卡历史」并把本行推进到下一次排期。这是「打卡形态」的本义（一周不堆 7 行已完成）。
   - 其余频率：走 08 既有 `completeRecurring`，行为一字不改。
2. **本子任务不拆，整体做完**（像 05 那样：简化级但含契约字段 + schema 演进 + 引擎扩展 + 呈现交互，一轮开发⇄评审做完）。

**这重述了验收标准第 2 条**「打卡即完成当日实例，与 08 实例生成一致」——对每日/每周习惯，「与 08 一致」改为「与 08 的**推进锚点**一致，但不留兄弟已完成行、改记打卡历史」；对其余频率仍严格等同 08。

### 由此确定的三项前置（UI/UX 第 8 节所列，编排者裁决其归属）

- **打卡历史（契约·必办）**：需要「稳定的习惯身份 + 一组已打卡排期日」。字段形态由开发定（参考 03 的 `Option<Option<T>>` 与 05 的 `archived_at`，但这是一组日期而非单个时间戳）；契约变更后跑 `pnpm run types:generate` 并同步全部调用方与端侧 SQLite schema（沿用 03 的列驱动迁移）。
- **排期日反向枚举（引擎·配套）**：`crates/domain/src/recurrence.rs` 今天只有向后走一次的 `next_occurrence`；streak 要向回数连续排期日，需薄扩展（注意 08 已把候选改为增量推进的 `Cursor`，反向枚举请与之一致，不要另造一套「什么时候重复」的理解）。
- **补卡**：只写打卡历史、不建行、不改本行锚点（补的是过去的排期日，与本行「下一次」无关）。streak 从打卡历史纯函数派生，不落会漂移的计数器。

上述三项均在本子任务范围内一并完成。
