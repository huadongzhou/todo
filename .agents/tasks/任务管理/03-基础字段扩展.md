### 2. 字段表的渲染分支扩展方式（需求节并入项 2 的正面回答）

#### 2.1 判别式：字段声明「控件形态」，不再声明「input 的 type」

`FieldDefinition` 由「一个 `inputType` 字符串」升为**按 `control` 判别的联合**。共有部分（`key` / `label` / `group` / `span` / `note` / `error` / `maxChars`）不变，分支只承载该形态**自己需要**的东西：

```ts
type FieldControl =
  | { kind: "input"; type: "date" | "datetime-local" | "number"; inputMode?: "numeric" }
  | { kind: "textarea"; rows: number }
  | { kind: "range"; parts: readonly [RangePart, RangePart] }; // 起止一对，见 2.3

// 后续子任务加入时各自加一支，不动已有分支：
//   | { kind: "select"; options: readonly { value: string; label: string }[] }   // 清单、周期频率
//   | { kind: "checkbox"; triState?: boolean }                                    // 象限 important/urgent（契约是 boolean|null 三态）
```

- **模板对应**：字段外壳（标签行 + 可选计数器 + 控件 + `note` + `error`）是**共用的一段**，只有控件那一处按 `control.kind` 分支（`v-if` / `v-else-if`）。加一种形态＝加一个分支 + 一支类型；加一个字段＝在 `FIELDS` 里加一条，**不新增分支**。
- **为什么不是「每个字段自带渲染函数」**：那会让每个字段都能自造 DOM 与类串，B1 的「两处控件类型、标签、校验、上限口径完全一致」就退回靠人工对齐；判别联合把可用形态钉成封闭集合，评审只需数分支。
- **为什么不是「每种控件一个子组件」**：`src/components/ui/` 今天只有 Button，为 4 个字段先造 4 个基础组件属于为不存在的复用做设计（AGENTS.md「一次性代码不抽象」）。等某一形态出现第三处调用方时再提，届时提取是机械的（外壳已经共用）。
- **容器边界不动的原因**：`control` 只被字段块读，`props` / `emits` / `expose` 的形状与 02 相同（新增的 `expand-details` 是第 1 节机制 3，与控件形态无关）。草稿仍是一个对象，容器仍整体传、整体重置。

#### 2.2 字段可声明的两类反馈与一个上限

| 声明 | 语义 | 视觉 | 是否拦提交 |
|------|------|------|-----------|
| `note?: (draft) => string \| null` | 「这样填是合法的，但你可能想知道」（既有，如「提醒时间已过」） | 整行 `text-xs text-amber-700 dark:text-amber-300` | 否 |
| `error?: (draft) => string \| null` | 「这样填存不下去」（契约拒绝，或起止自相矛盾） | 整行 `text-xs text-red-600 dark:text-red-400`，控件 `aria-invalid="true"` | **是** |
| `maxChars?: number` | 文本长度上限，按**码点**计数 | 剩余 ≤ 阈值时标签行右端出现计数器（同标题） | 否（超出部分不被接受，不整段丢弃） |

- `note` 与 `error` 都拿到**整份草稿**，因此「结束时刻需要开始时刻」这类跨字段规则写在字段自己的定义里，容器仍只调 `validate()`（02 第 11 节第 5 条的原话：带跨字段规则的字段其校验同样写在字段块内）。
- `note` 与 `error` 从本任务起**各自带 id 并进入该字段控件的 `aria-describedby`**（补上 02 遗留的 `note` 未关联；`error` 与标题错误同款）。
- `maxChars` 的计数与截断复用标题那段码点归一逻辑（`Array.from(v).length`，超出取前 N 个码点重组并写回，打字与粘贴同一条路）。**标题不再是特例**：把它表达成「首行那个 `maxChars = MAX_TITLE_CHARS` 的必填字段」，备注只是第二个用户。
- **上限值一律取生成绑定，界面不写字面量**（02 的 C1 口径）：本任务需要 `MAX_NOTES_CHARS` 走与 `MAX_TITLE_CHARS` 完全相同的一条路——契约常量置 `pub` → 重生成 bindings → `src/lib/native.ts` 再导出。**不接受在界面写 20000**。（这与前置必办同属契约改动，一并做。）

#### 2.3 `range`：一个字段、两个草稿键

时间段是唯一需要「一个字段管两个草稿键」的形态，`range` 分支为它而设：

```ts
interface RangePart { key: FieldKey; label: string; type: "datetime-local"; toInput; fromInput; }
```

- 渲染：整行 `<fieldset class="col-span-full m-0 border-0 p-0">` + `<legend>时间段</legend>` + 内部 `grid gap-3 sm:grid-cols-2` 两个子控件，各自有 `<label for>`（「开始时刻」「结束时刻」）。`note` / `error` 属于整个 range，`aria-describedby` 同时挂到两个子控件上。
- **为什么不拆成两个半行字段**：组内顺序被钉死为契约声明顺序（`due_date, reminder_at, start_date, starts_at, ends_at, estimated_minutes`），拆开后两列栅格会把 `starts_at` 排在第二行右格、`ends_at` 排到第三行左格——**起止对被切在两行**，正是 02 把「含多个子控件」判为整行要避免的事。合成一个整行字段后，一对子控件恒在同一行，且 02 的宽度判据原样成立。
- 代价（明写，评审可核对）：「时间」组在 `≥640px` 下会出现一格空位（截止日 | 提醒 / 开始日期 | ⬚ / 时间段跨整行 / 估时 | ⬚）。这是「契约顺序 + 字段自声明宽度」两条规则的确定结果，不是排版失误；宁可留空位也不为好看打乱顺序或让容器插手排版。窄屏单列下不存在空位。

### 3. 本任务落地的四个字段

- 文案：标签分别为「备注」「开始日期」「时间段」（子标签「开始时刻」「结束时刻」）「估时（分钟）」。单位写进标签而不是加后缀控件——省一个控件，且读屏读标签时单位就在名字里。
- 可选字段**不给 placeholder**（与 02 已落的截止日 / 提醒一致，可见 label 已说明字段是什么）。
- 备注 `resize-y`：允许用户自行拉高，不允许横向拉宽（横向可拉会撑出横向滚动）。默认 3 行是**编辑态高度预算的一部分**（第 4 节），不设更大的默认值。
- **不使用 `min` / `max` / `required` / `maxlength` 等原生约束属性**：它们会让浏览器在 `submit` 事件之前拦截提交并弹出系统气泡，绕开本规格的单一 live region 通路，且 Enter 隐式提交会变成「毫无反应」。上限与范围一律由字段表的 `maxChars` / `error` 表达。
- 草稿三个导出（`createEmptyDraft` / `draftFromTodo` / `isSameDraft`）**不需要为新字段单独改写**：前两个各加一个键，`isSameDraft` 走 `Object.keys` 自动覆盖（`TodoFields.vue:38-40`）。
- 「可存」不在界面侧：`stores/todos.ts` 的 `add` / `update` 与其出站 op 必须带上四个字段的全部草稿键（今天只列了 `title` / `dueDate` / `reminderAt`，`:126-205`），否则字段填了也存不住、同步不出去——这是开发必须一并完成的部分，`_母任务` 的「往返一致」验收落在这里。
- **「三处一致可用」的口径**（需求节验收第 1 条）：应用至今没有独立详情页（01 规格已实证、02 需求节「明确不做」重申），因此「创建 / 编辑 / 详情三处」在今天等于**创建表单 + 行内编辑两处**，且两处渲染同一份 `TodoFields.vue`，一致性是结构性的而非对照出来的。将来若出现详情面板，它同样消费这份字段块（第 4 节的复评触发条件已为此留口）。

### 4. 编辑态容器形态阈值：正面评估与结论（需求节补充 1 的正面回答）

#### 4.1 触发确认

01 规格第 0 节第 4 条的经验阈值是「字段数增长到约 5 个以上」。本任务后字段块共 **8 个可见字段**（标题 + 备注 + 截止日 + 提醒 + 开始日期 + 时间段 + 估时，其中时间段含 2 个子控件），**确实触发**，必须表态。

#### 4.2 高度预算（按本规格的类串逐项累加，非估计）

单个半行字段＝标签 16 + `mb-1` 4 + 控件 `min-h-11` 44 ＝ **64**；字段间 `gap-3` 12；组间 `gap-4` 16；组标题 `text-sm` 20 + `mb-2` 8 ＝ 28。

| 区块 | ≥640px（两列） | <640px（单列） |
|------|---------------|---------------|
| 首行（标题） | 64 | 64 |
| 详情区分隔（`gap-4` + `pt-4`） | 32 | 32 |
| 内容组（legend + 备注 3 行 textarea） | 28 + 96 = 124 | 124 |
| 时间组（legend + 4 行 / 6 项） | 28 + 316 = 344 | 28 + 472 = 500 |
| 操作行（取消 / 保存） | 16 + 44 = 60 | 60 |

#### 4.3 结论：**继续行内展开，不改独立详情面板**；但编辑态详情区改为「按需展开」

**不改形态的判断依据（三条，逐条可核对）：**

1. **没有可用的地基**：`src/components/ui/` 只有 `Button.vue`，没有 dialog / popover / sheet。独立详情面板意味着要新造遮罩、焦点圈闭、滚动锁、Esc 关闭、关闭后焦点归还、移动端全屏化与 `aria-modal` 一整套——这是新建一族基础组件，DESIGN.md「待补充」里 dialog 也还没有条目。
2. **不改形态并不会让字段装不下**：详情区不做内部滚动、页面纵向滚动（02 第 1 节禁止清单），624 / 780px 是**页面变长**，不是内容溢出或被裁切。面板同样装不进一屏，同样要滚——换形态换不来「装得下」，只换来一族新组件与一次交互模型变更。
3. **越界**：编辑形态是全应用的编辑模型，牵动 04（撤销重做）、05、10（子任务）、11、12 与三个兄弟母任务；02 的验收 B4「编辑态仍是行内展开」与 01 的 E1 是现行契约。本子任务是**简化级、没有产品阶段**，不能单方面改掉它。01 / 02 两处都写了「届时另起任务」，这条路径仍然有效。

**代价与对冲（本任务内必须做的一条）：** 恒展开会让「点标题改个错别字」也弹出 624px 的表单，包括那些一个可选字段都没填的任务——这才是行内展开真正被撑破的地方。因此编辑态的详情区由 02 的「`details-open` 恒 `true`」改为：

- **开态判定一次**：打开编辑时，若该任务**任一可选字段有值**则展开，否则收起。判定用字段块新导出的 `draftHasDetails(draft: TodoDraft): boolean`（与 `isSameDraft` 同样走草稿自己的键），**容器不点任何字段名**，禁止清单不破。
- 判定**只在打开那一刻做一次**，之后只由用户切换：否则用户清空一个备注就会让表单在脚下自己收起来。
- 编辑态的 `actions` 插槽（02 里留空）放与创建表单同款的展开按钮（`min-h-11 min-w-11 !p-2`、`SlidersHorizontal` 20、`aria-expanded`、`aria-controls="todo-${id}-details"`、`aria-label` 在「展开更多选项」/「收起更多选项」之间切换）。
- 效果：无可选字段的任务，编辑态高度回到 **≈ 124px**（标题行 + 操作行），列表节奏保住；有内容的任务照旧一眼看全。
- **01 已定的编辑交互一条不动**：点标题进编辑、行内展开、显式保存、Enter 等价提交、Esc / 取消丢弃草稿且不写 store、未改动不提交、三条路径焦点归还标题按钮、编辑态隐藏完成圈与删除按钮。02 的 B4 同样成立（仍是行内展开，不是弹层不是整页）。
- 不做额外的滚动控制：打开编辑后焦点进入标题输入，浏览器本就会把它滚入视口；表单其余部分随页面滚动。自造 `scrollIntoView` 会与滚动锚定和 `prefers-reduced-motion` 打架。

### 5. 三类页面提示的优先级与共存规则（需求节并入项 1 的正面回答）

#### 5.1 缺陷复述与要害

现状 `pageAlert = formAlert ?? storageAlert ?? exportAlert`（`App.vue:162`）。02 让 `formAlert` 压过 `storageAlert` 的理由是「表单提示一次输入即消失」——这个理由对**提交被拒**成立，对**标题达上限**不成立：标题停在上限时那条 amber warn 一直在，会持续遮住 `storageAlert` 的「有改动没能保存到本机」（数据丢失级 error）。本任务再加四个字段（备注也带上限反馈），遮蔽窗口只会更长。

#### 5.2 分类：生命期，不是来源

给每条提示两个正交属性，**判据可操作**：

- **生命期**——**一次性**：清除时机与「提示自己描述的那个条件」无关（用户随便下一个动作就走）；**持续性**：只有条件本身消失它才消失。
- **严重度**——`error` / `warn` / `success`（沿用 `ALERT_TONE_CLASS` 三调，`App.vue:134-138`）。

按此判据给今天的五种提示定性（不靠印象）：

| 提示 | 来源 | 严重度 | 生命期 | 判据 |
|------|------|--------|--------|------|
| 提交被拒（标题为空 / 字段 error） | 表单 | error | **一次性** | 下一次输入 / 提交成功 / 编辑态关闭即清，与「标题为空」这个条件无关 |
| 标题或备注达上限 | 表单 | warn | **持续性** | 只有码点数回落到上限以下才清——**清除时机就是条件本身** |
| 有改动没能保存到本机 | 存储 | error | 持续性 | `computed`，`failedIds` 非空就在（`stores/todos.ts:57-68`） |
| 有改动暂存在本地缓存 | 存储 | warn | 持续性 | 同上 |
| 导出结果（成功 / 空 / 失败） | 导出 | success/warn/error | 一次性 | 关闭设置面板即清（`App.vue:166-168`），与导出这件事本身无关 |

#### 5.3 规则：排序键（升序取第一），不共存

```
1. 生命期：  一次性(0) < 持续性(1)
2. 严重度：  error(0) < warn(1) < success(2)
3. 来源：    表单(0) < 存储(1) < 导出(2)
```

判定结果逐条核对（评审可按此表构造场景）：

| 同时成立的两条 | 显示 | 是否符合要求 |
|---------------|------|-------------|
| 标题达上限 warn（持续） + 存储写入失败 error（持续） | **存储 error** | ✅ 本任务补充验收第 1 条要求的正是这条 |
| 提交被拒 error（一次） + 存储写入失败 error（持续） | 表单 error | ✅ 保住 02 的 D1（提交被拒必须能被读屏感知），存储 error 在下一次击键后自己回来 |
| 提交被拒 error（一次） + 存储降级 warn（持续） | 表单 error | ✅ 同上 |
| 标题达上限 warn（持续） + 存储降级 warn（持续） | 表单 warn（来源序） | ✅ 两条都非数据丢失级，任取其一都不掩盖事实 |
| 导出结果（一次） + 标题达上限 warn（持续） | **导出结果** | ✅ 修掉「持续性 warn 吞掉一次性结果」——导出结果没有第二条通路 |
| 导出结果（一次） + 存储 error（持续） | 导出结果 | ✅ 关面板即让位，存储 error 自己回来 |

**为什么「一次性」排在「严重度」前面**：一次性提示是对用户**刚发起的那个动作**的直接答复，且**有与自身条件无关的确定清除时机**——它让位之后，持续性提示会因为条件仍在而自动回到提示条上（`pageAlert` 是 `computed`，不需要任何补偿机制）。持续性提示之间才轮到比严重度，而那正是缺陷所在的那一格。

**共存展示：不需要，也不允许。** 页面只有一个 live region（02 的 D3、01 第 6 节），把两条拼进同一句会让读屏在一次 `aria-atomic` 重读里念出两件不相干的事，且每次任一条变化都整句重读。取而代之是一条**可检查的设计约束**：

> **被压住的提示必须满足二者之一：① 压它的那条有确定清除时机，让位后它会自己回来；② 它另有一条可见通路。**

对本任务的两处遮蔽逐条验证：存储 error 被表单 error 压住 → 满足 ①（下一次击键即回）；上限 warn 被存储 error 压住 → 满足 ②（**字段标签行右端的计数器常驻可见并 amber 变色**，且输入框不再接受字符本身也是反馈）。**将来新增第四类提示时按这条约束核对**，不满足就不许压。

**已知取舍（明写）**：在存储 error 持续存在的设备上，读屏用户打字撞上限的那次**播报**会被吞掉（计数器仍在 `aria-describedby` 里，聚焦时可查询）。取舍理由：一边是「你的改动没能保存」（数据丢失），一边是「标题到头了」（一个字都没丢）。

#### 5.4 实现形状（不新增任何 DOM 节点）

- 三路候选统一为同一形状：`{ tone, message, lifetime: "transient" | "standing", source: "form" | "storage" | "export" }`。
- `announceFormAlert(tone, message, lifetime)` 增加第三个参数：提交被拒 = `transient`，上限 = `standing`。`storageAlert` 恒 `standing`，`exportAlert` 恒 `transient`（各自在产出处标注，不在 `App.vue` 里猜）。
- `pageAlert` 由 `??` 链改为「三路候选去空后按排序键取第一」。live region 元素、`role="status" aria-live="polite" aria-atomic="true"`、`sr-only` 常驻策略**一律不动**（D3：仍只有 `App.vue:301-311` 这一处）。
- 清除时机（全表，任何一条都不靠计时器）：

| 提示 | 清除时机 |
|------|---------|
| 提交被拒 | 出错字段的值发生变化 / 提交成功 / 编辑态关闭（保存、取消、Esc、切到另一行） |
| 上限 | 该文本码点数回落到上限以下（含被清空） |
| 存储 | `failedIds` / `degradedIds` / 积压清空（store 自理） |
| 导出 | 关闭设置面板 / 下一次导出 |

- **一次性提示遮蔽持续性提示的窗口不得超过用户的下一个输入或动作**——这是上表的直接推论，也是评审复核 5.3 约束 ① 的判据。
- 两条一次性提示同时成立（提交被拒 + 导出结果）需要用户在设置面板与创建表单之间往返，实际不可达；真出现可并发的一次性来源时按「后来者胜」扩展（给一次性提示加一个递增序号），现在不预埋。

### 6. 校验的执行、焦点与详情区展开

- `validate()` 的职责扩展为「**校验，并把用户带到需要处理的地方**」，对容器的返回仍只是布尔：
  1. 计算首行标题必填 + 字段表每条 `error(draft)`；
  2. 有错 → 置内部错误态（控件 `aria-invalid="true"`、行内红字、`aria-describedby` 关联）；
  3. 若出错字段位于详情区 → `emit("expand-details")`（创建容器接一行把 `showDetails` 置真；编辑容器若已展开则无事发生，若收起则由同一行逻辑展开）；
  4. 把**第一条**错误（顺序：标题 → 字段表声明顺序）投递给单一 live region（`error`、一次性）；
  5. 焦点落到第一个出错的控件（`await nextTick()` 之后，确保详情区已展开）。
- `focusTitle()` 语义补一条守卫：**当前存在可见校验错误时不做任何事**（焦点已由 `validate()` 放在出错控件上）。这样两个容器现有的「校验失败 → `focusTitle()`」两行**不用改**也不会把焦点抢回标题。其余调用点不受影响：快捷键唤起、提交成功后重置、编辑态打开时都不存在可见错误。
- 草稿对象被整体替换（引用变化）时清空错误态与 `titleEverFilled`：创建成功后的重置、编辑态打开新任务，都从干净状态开始。
- 编辑态 `save()` 里把「未改动」判定提到 `validate()` 之前：草稿与开态完全相同就直接关闭、不校验、不写入。理由：不写入就没有可校验的东西；否则一条从同步进来的、界面规则不接受的历史数据（如 `endsAt` 早于 `startsAt`）会把用户锁死在编辑态里——只能取消，连原样关闭都做不到。「未改动不提交」（01 的 E1）由此更强，不更弱。
- 校验时机沿用 02 第 5.3 节：**提交时必校验**（Enter 与点按钮两条路径）；标题「脏值失焦」校验；不逐键校验；字段级 `error` 随该字段值变化实时重算（输入即消失）。脏值失焦不投递 live region（用户此刻正在移动焦点）。

### 7. 时间段与截止日 / 提醒的关系（要求 e 的表态）

**三者语义不同、互不推导，界面上并列不联动：**

| 字段 | 语义 | 存储形状 |
|------|------|---------|
| 截止日 `dueDate` | 这天之前要做完 | 本地日历日 `YYYY-MM-DD` |
| 提醒时间 `reminderAt` | 在这个时刻通知我 | 瞬时（ISO） |
| 时间段 `startsAt`/`endsAt` | 这件事实际占用这段时间 | 一对瞬时 |
| 开始日期 `startDate` | 这天之前不必看见它 | 本地日历日 |

- **界面组织**：四者同在「时间」组，按契约声明顺序排（截止日 → 提醒时间 → 开始日期 → 时间段 → 估时）。不做分栏、不做二级折叠——组内再分层就是在字段块里重造容器。
- **不做任何自动联动**（如「设了时间段就把截止日填成同一天」「提醒默认取开始时刻」）：契约里四者相互独立；一旦联动就必须定义「改哪个跟哪个、用户改过之后还跟不跟」的全套规则，产品未定义。02 的「不新增跨字段校验规则」同源，本任务只带入**契约已有的**那两条。
- **冲突与校验通路**：

| 情形 | 判定 | 走哪条通路 | 文案 |
|------|------|-----------|------|
| `endsAt` 有值而 `startsAt` 空 | **拦**（契约 `lib.rs:113` 就会拒，`Todo::validate` 直接 `InvalidTimeRange`，放过去就是一次写入失败） | 时间段字段的 `error` | 「先填开始时刻，或清空结束时刻。」 |
| `endsAt` 不晚于 `startsAt` | **拦**（见下方理由） | 时间段字段的 `error` | 「结束时刻需要晚于开始时刻。」 |
| `estimatedMinutes` 非正或非整数 | **拦**（契约 `lib.rs:117` 拒绝 0；负数与小数 `u32` 也存不下） | 估时字段的 `error` | 「估时请填写大于 0 的整数分钟，或留空。」 |
| 提醒时间早于当前时刻 | 不拦（既有） | `note` | 「提醒时间已过，保存后会立即提醒一次。」（02 已落） |
| 提醒晚于截止日 / 开始日期晚于截止日 / 提醒早于开始时刻 | **不拦、不提示** | — | 产品未定义；这类是**两个不同语义字段**之间的关系判断，要做应先由产品定义后另立，不在本任务里替产品决定 |

  「结束不晚于开始」判为阻塞的理由（与上一行的区别要写清）：起止是**同一个字段的两半**，不是两个字段的关系；一个负长度或零长度的时间块没有任何解释，且会被下游直接消费——`视图与统计/13 时间块视图`（一句话验收即「拖入时间块即写任务起止时刻」）与 ICS 导出（`crates/domain/src/ics.rs` 按起止生成事件）都会拿到坏数据。契约没拦是因为它只做了存得下与否的判断。

- **清空语义**：控件清空即「显式置空」，不额外提供「清除」按钮——原生 `date` / `datetime-local` 控件与 `number` / `textarea` 都可直接清空，多一个按钮就多一个触控目标和一处两端不一致的风险。**条件性回退**：若开发实测发现目标平台（WebView2 / iOS / Android）的原生日期控件无法从键盘清空，再补字段级清除按钮（44×44、`aria-label="清除{字段名}"`，作为字段外壳的统一能力而不是某个字段的私货），并写进实现记录。
- 与**前置必办**的接口：草稿永远是**完整对象**，键恒存在，`null` 恒表示「用户要它为空」——界面侧不存在「未提供」这一态。因此契约修好「显式置空」后，容器整体提交的草稿天然携带清空意图，界面无需再为清空造第二条路径。反过来说，前置必办没修完之前，本任务的清空在跨设备一侧不成立（需求节补充验收已列），**先修契约再做字段编辑 UI**。

### 8. 「将来」的边界划分（要求 d 的表态）

**本任务负责的三件事：**

1. **字段本身**：开始日期的录入、回显、存取、清空（第 3 节）。
2. **「将来」状态的判定依据**：新增一个纯函数（`src/lib/startDate.ts`，或并入 `src/lib/dueDate.ts`），口径为「`startDate` 的本地日历日 **晚于**今天的本地日历日 ⇒ 未开始」；无 `startDate` 不算，已完成任务不算。**必须复用 `dueDate.ts` 现有的日历日差算法**（`dayDifference`，需要就把它提为共享导出），不许新写第二套日期口径——两套口径会在跨月、跨夏令时与 23:59 日切时给出不同答案。
3. **最小呈现：列表行的「将来」徽标**。位置在既有徽标行（`TodoItem.vue:195-202`，属展示态那一行，不是编辑容器，禁止清单不适用），文案 `{既有日期文案}开始`（复用 `formatDueDate` 的「明天 / N 天后 / M月D日」分支——未开始时日差恒 > 0，「逾期 / 今天」分支不可达），类串复用 `TONE_LABEL_CLASS.normal`（**零新增令牌**）。徽标行的渲染条件由「有截止日」放宽为「有截止日或未开始」，否则一条只有开始日期的任务什么都不显示。
   - 为什么这一条必须在本任务里：需求节验收第 2 条明写「开始日期未到的任务收进『将来』视图不打扰」。若开始日期设完在界面上没有任何痕迹，用户只会认为这个字段没生效——「可显」不成立。

**本任务不负责（归 `视图与统计/01-列表日期分组`）：** 未开始任务是否从进行中列表移出、是否单独成组、组是否默认折叠、是否计入页头「N 项待完成」、跨天日切时如何自动重新归组。

**必须点名的口径冲突（请编排者转给 `视图与统计/01`）**：`视图与统计/01` 的需求节写的五组是「今天 / 明天 / 本周 / 以后 / 逾期」，这五组是**按截止日**划分的；而「将来」是**按开始日期**判定的正交状态——一条「明天到期、后天才开始」的任务在两套口径里会被同时要求归入两组。两者必须在 `视图与统计/01` 的设计阶段一并收口（正交状态优先于截止日分组？还是「将来」作为第六组？），本任务只提供判定函数与行内标记，不替它定分组规则。

**同样不在本任务**：未开始任务的提醒是否推迟触发——提醒调度归 `提醒通知` 母任务，本任务不动 `src/lib/notifications.ts` 与 `scheduleReminder`。

**备注 / 时间段 / 估时不进列表行**，理由：备注是长文本，行内摘要会改变列表行的高度节奏（列表呈现归 `视图与统计`）；时间段的行内展示需要一套同日 / 跨日的时间格式化，同属列表呈现（`视图与统计/13` 正是消费它的地方）；估时是给统计与排程消费的（`专注计时/02`、`AI助手/07`），对「下一步做什么」没有帮助。三者的「可显」由编辑态回显满足，与 02 对截止日 / 提醒的口径一致。

### 11. 移动端适配

- **触控目标**：新增的三个单控件（开始日期、估时、时间段的两个子控件）一律 `min-h-11`（44px）；备注 `rows=3` 约 84px，天然达标；编辑态新增的展开按钮 `min-h-11 min-w-11`。相邻间隙沿用 `gap-2`(8) / `gap-3`(12) / `gap-4`(16)，均 ≥ 8px（DESIGN.md）。
- **iOS 聚焦缩放**：`textarea` 与 `type="number"` 与既有输入一样写 `text-base sm:text-sm`（移动端 16px、桌面 14px）。**漏掉 textarea 会让 iOS 在聚焦备注时整页缩放**，这是本任务唯一新增的输入形态，必须逐个核对。
- **数字键盘**：估时用 `type="number"` + `inputmode="numeric"` 唤起数字键盘（DESIGN.md 表单基准「语义化 type 唤起正确键盘」）。不写 `min`/`max`（第 3 节：会触发原生约束校验拦截提交）。
- **窄屏布局**（`< 640px`）：详情区单列，半行与整行都是满宽；时间段的两个子控件在单列下上下排列；组标题保留。320px（`body min-width`）与 375px 下逐项验证**无横向滚动**——备注 `resize-y` 只允许纵向拉伸，正是为此。
- **详情区不做内部滚动**：字段变多时页面纵向滚动（02 第 1 节禁止清单；套定高滚动壳会与原生日期选择器抢空间）。
- **原生选择器**：`date` / `datetime-local` 唤起系统滚轮，选择器内的返回 / Esc 由系统接管（继承 01 / 02）。
- 移动端整体导航属「移动端形态」母任务，本任务不引入任何平台分支入口。

### 12. 可访问性

- **可见标签**：五个新控件（备注、开始日期、开始时刻、结束时刻、估时）全部 `<label for>` + `<input/textarea id>` 显式关联（02 已定的口径，不用包裹式 label）。
- **分组语义**：时间段是**嵌套 `<fieldset>` + `<legend>时间段`**（外层是组的 fieldset）——读屏进入起止两个控件时会先报出「时间段」，这正是「这两个框是一对」的可访问表达。组 legend 用 `text-sm text-slate-800`，字段 legend 用 `text-xs text-slate-500`，层级靠既有字号 / 灰阶档区分，不新增令牌。
- **可访问名稳定**：计数器、`note`、`error` 一律在 `<label>` 之外，只经 `aria-describedby` 关联；备注的可访问名恒为「备注」，不随打字变化。
- **描述关联**：每个控件的 `aria-describedby` 由 `[计数器 id?, note id?, error id?]` 拼成（存在才进），顺序固定为 计数器 → 提示 → 错误。
- **错误语义**：出错控件 `aria-invalid="true"`；错误文案紧贴字段下方并说明修复方式（DESIGN.md 表单基准）；提交被拒经**单一 live region** 播报第一条（第 6 节），**不新增第二个 live region**（继承 02 的 D3 与 01 第 6 节）。
- **键盘全通路**：
  - 创建：标题 → 展开按钮 → 添加按钮 →（展开时）备注 → 截止日 → 提醒 → 开始日期 → 开始时刻 → 结束时刻 → 估时。DOM 顺序＝视觉顺序。
  - 编辑：标题 → 展开按钮 →（展开时）同上字段序 → 取消 → 保存；Enter 提交、Esc 取消（01 既定）。
  - 提交被拒时焦点落在第一个出错控件上，且详情区已被展开——焦点不会落进 `display:none` 的区域（这正是 `expand-details` 存在的理由）。
  - 不注册任何 `document` / `window` 级监听（保持 01 给 `任务管理/04` 的边界）。
- **展开控件的 ARIA**：编辑态新增的展开按钮与创建表单同款——`aria-expanded` + `aria-controls` 指向 `v-show` 常驻的详情区容器，`aria-label` 随状态切换。
- **不靠颜色单传**：计数器、上限、字段错误、提醒已过、「将来」徽标全部由文字直接说明。
- **对比度**：取值全部落在 DESIGN.md 已验证的 slate / red / amber 阶内。`default` 按钮白字压 sky-500 的偏差是 DESIGN.md「已知偏差」下的全局待决项，本任务不单独处理。
- **焦点环**：按设计意图书写（`focus-ring` / `focus:ring-2 focus:ring-sky-500`）。已知 `uno.config.ts` 的 `focus-ring` shortcut 实际失效（已转 `外观与设置/04`），本任务不绕开、不自造替代写法。

### 15. 交给编排者 / 开发的说明

1. **`MAX_NOTES_CHARS` 需要经 bindings 导出**：契约里它今天是私有 const（`lib.rs:14`）。本规格要求界面不写字面量（沿 `MAX_TITLE_CHARS` 的既有路径：`pub` → 重生成 bindings → `src/lib/native.ts` 再导出）。这与**前置必办**同属契约改动，一次做完。
2. **实现顺序**：前置必办（`TodoPatch` 显式置空）必须先落，再做字段编辑 UI——本规格第 7 节的清空语义直接建立在它之上，否则四个字段全都是「填得上、去不掉（跨设备）」。落地后按需求节补充要求回归 02 的两条路径（清空截止日、清空提醒在另一端生效）。

### 前置必办：`TodoPatch` 显式置空

**改法**：可空字段 `Option<Option<T>>`——外层是「patch 提没提这个字段」，内层是「提到时设成什么」。`serde` 对嵌套 option 的默认读法会把 `null` 折成外层 `None`（与缺键同形），所以走 `#[serde(with = "present")]`：`deserialize` 只在键存在时被调用，读内层再包一层 `Some`，于是 `Some(None)` 恰是「键在、值为 null」。序列化交回 serde（`Some(None)` → `null`，`None` 被 `skip_serializing_if` 略去）。

选 `with` 而非 `deserialize_with`：ts-rs 认识 `with` 而不认识 `deserialize_with`，后者会在**每次编译 contracts 时刷 13 条** `failed to parse serde attribute` 伪警告。`with` 需配 `#[ts(as = "Option<T>")]`，顺带让生成的 TS 类型不依赖嵌套 option 的塌缩行为。生成结果**逐字未变**（`dueDate?: string | null` …），变的是它终于能在 Rust 侧被表达。

**用例覆盖**（新增 4 条，全部新写）：

- `contracts`：`a_patch_tells_clearing_a_field_from_not_mentioning_it`（`{"dueDate":null}` → `Some(None)`；`{"title":…}` → 其余 `None`）、`a_cleared_field_survives_the_round_trip_a_stored_patch_makes`（解码→再编码仍含 `"dueDate":null`，未提及的字段仍不上线）、`a_patch_setting_a_value_is_unaffected_by_the_clearing_shape`（含「清空估时 ≠ 把估时设成 0」）。
- `server`：`a_patch_that_clears_a_field_still_clears_it_after_the_log`（这正是原缺陷的发生地：写进日志再读回来，`Some(None)` 仍是 `Some(None)`，未提及的字段仍是 `None`）。

**跨设备实测（可复现步骤）**

环境：`DATABASE_PATH`/`BACKUP_DIR` 指向临时目录、`CORS_ORIGIN=*` 的 `cargo run -p todo-server`；设备 A = `pnpm run tauri:dev`（`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222`，经 CDP 驱动）；设备 B = 直接 `POST /v1/sync` 的 curl。

1. **协议层（A=curl，B=curl）**：推 `patch:{... 七个字段全有值}` → B 拉到全部值；再推 `patch:{"dueDate":null,"reminderAt":null,"notes":null,"startDate":null,"startsAt":null,"endsAt":null,"estimatedMinutes":null}` → **B 拉到的回包逐字段仍是 `null`**（改前此处是 `{}`）；再推 `patch:{"title":"只改标题"}` → B 拉到的 patch 里**只有 title**，其余键不出现。「未提供」与「显式置空」在载荷上可区分。
2. **出站（A=界面，B=curl）**：在创建界面填齐标题+备注+截止日+提醒+开始日期+时间段+估时并提交 → B 收到的 upsert patch 含全部七个字段（`revision 5`）。随后在行内编辑态把七个可选字段全部清空并保存 → B 收到 `{"title":…,"dueDate":null,"reminderAt":null,"notes":null,"startDate":null,"startsAt":null,"endsAt":null,"estimatedMinutes":null}`（`revision 17`）。

### 实现中补的一处防护（请评审知悉）

`normalizeNotes`（`src/stores/todos.ts`）：本任务把 `notes` 加进 `NewTodoInput` / `TodoEdit` 后，就多了一条不经界面输入框的写入路径。走查时（用它构造存储失败场景）实测到后果比标题更重——超长 notes 会让**整个 sync 请求**被服务端拒绝，被拒的 op 永不确认，于是它会毒死这台设备的整条队列（不只是它自己）。因此比照既有 `normalizeTitle` 加了同款码点截断；键入路径上它不做任何事（输入框已按 `MAX_NOTES_CHARS` 截断）。

### 与规格的一处形状调整（不改交互与视觉）

规格 2.2 写的是 `maxChars?: number`，实现为 `maxChars?: { max: number; counterFrom: number }`。理由：规格自身要求标题计数器阈值「剩余 ≤ 20」、备注「剩余 ≤ 200」（第 9、14 节），一个数字表达不了两个数；把两者绑在一起声明，比在字段外另设一张阈值表更不易漂移。语义、文案、视觉与规格完全一致。

命名按规格第 15 节第 4 条的授权保持 `validate()` / `focusTitle()` 不改——两个容器的四处调用点一行未动。
