- 级别：简化

## 需求（产品）

- 目标与场景：备注、开始日期、估时、时间段四个字段可设可存可显。
- 范围（做 / 不做）：做 四字段的界面与存取（契约字段已由 数据与同步/03 落定）；不做 估时统计对比（专注计时）。
- 验收标准（逐条可检查）：
  - [ ] 四字段在创建/编辑/详情三处一致可用。
  - [ ] 开始日期未到的任务收进「将来」视图不打扰。

### 编排者并入项（来自 数据与同步/04 评审第 1 轮，已裁决「转任务处理」）

**【前置必办】`TodoPatch` 无法表达「显式置空」**（`crates/contracts/src/lib.rs`，联动 `src/stores/todos.ts` 的 `applyRemoteUpsert`）：可空字段是 `Option<T>` + `skip_serializing_if`，于是「把 dueDate 设为 null」与「patch 里没有 dueDate」在线上形状里**无法区分**——实测推 `patch:{"dueDate":null}`，服务端库里与回包里该 patch 均为 `{}`，视图端 `!== undefined` 的合并约定也读不到清空意图。结果是**这些字段只能设、不能清**。

本子任务交付的正是「基础字段」的编辑交互，「清空截止日 / 清空备注 / 清空估时」是其题中之义，缺了它字段一旦填上就再也去不掉。修复需同时改契约形状、重生成 bindings、并调整视图端的合并约定，请在做字段编辑 UI 之前先解决。

补充验收标准：

- [ ] 任一可空字段被用户清空后，本地、服务端与另一台设备三处都反映为「已清空」，而不是保持原值。
- [ ] 「未提供该字段」与「显式置空」在契约与同步载荷上可区分，并有用例覆盖。

### 编排者补充（来自 任务管理/02 产品阶段的提示）

1. **编辑态容器形态阈值**：01 的 UI/UX 规格约定「字段超约 5 个需评估『行内展开 → 独立详情面板』」。02 只落 3 个字段不触发，本子任务再加 4 个（备注/开始日期/时间段/估时）后**必然触发**。请在本子任务的 UI/UX 阶段正面评估容器形态，若判定需要改为独立详情面板，写进规格并说明对 `TodoItem.vue` 与 `TodoFields.vue` 的影响；不要在字段塞不下的情况下硬撑行内展开。
2. **`TodoPatch` 显式置空落地后需回归 02 的两条路径**：02 允许清空截止日与提醒，本机生效但跨设备读不到清空意图。本子任务的前置必办修好该缺口后，请一并回归这两条路径（清空截止日、清空提醒在另一端生效）。

### 编排者并入项（来自 任务管理/02 评审第 1 轮，已裁决「转任务处理」）

1. **三类页面提示的优先级规则**（`src/lib/form-alert.ts:22` 与 `src/App.vue:161`）：当前 `pageAlert = formAlert ?? storageAlert ?? exportAlert`，`formAlert` 压过 `storageAlert` 的理由是「表单提示一次输入即消失」——但该理由**不覆盖标题上限的 warn**：标题停在上限时 amber 提示持续存在，会一直遮住「有改动没能保存到本机」这条 error（数据丢失级）。本子任务再加四个字段后表单类提示更多、遮蔽窗口更长，请在此一次把三类提示（表单 / 存储 / 导出）的优先级与共存规则定完，而不是单点修补。
2. **字段表的渲染分支扩展方式**（`src/components/TodoFields.vue:70` 与 416-422）：02 交付的字段表目前只能表达单行 `<input :type>`。本子任务的备注（textarea）、以及后续的清单（select）、象限（checkbox）都需要新的渲染分支。请在本子任务的 UI/UX 阶段定下扩展方式（字段表如何声明控件形态、容器与字段块的边界如何保持不变），02 刻意没有预设分支以免为不存在的需求做设计。

补充验收标准（追加）：

- [ ] 存储失败告警在任何表单提示存在时仍能被用户看到（构造「标题达上限 + 存储写入失败」同时成立的场景验证）。
- [ ] 新增非 `<input>` 形态字段后，`App.vue` 与 `TodoItem.vue` 两个容器仍无需改动（沿用 02 验收 B2 的判据）。
