### 1. 边界：本任务做什么、不做什么

需求节的一句话验收是「复制含子任务/标签/象限/清单；归档页可查；顺延可开关」。这句话里的四个名词今天**大多没有对应实体**：

| 名词 | 今天仓库里有什么 | 归属 | 本任务能做到的最大限度 |
|------|----------------|------|---------------------|
| 子任务 | 契约有 `Subtask` 结构与 `Todo.subtasks: Vec<Subtask>`；**没有界面、没有增删改、store 的 `add` 从不写它**（恒 `[]`） | `任务管理/10`（全流程，未开始） | 复制时把 `subtasks` 数组的**值**搬过去（并按第 3 节重置每项 id 与 `done`） |
| 标签 | 契约有 `tag_ids: Vec<String>`；**标签实体本身不存在**（`标签/01` 未开始），没有任何界面能加标签 | `标签` 母任务 | 搬 `tagIds` 数组的**值** |
| 象限 | 契约有 `important` / `urgent`（三态 `Option<bool>`）；没有界面 | `四象限` 母任务 | 搬两个布尔字段的**值** |
| 清单 | 契约有 `list_id`；**清单实体不存在**（`清单/01`、`02` 未开始） | `清单` 母任务 | 搬 `listId` 字段的**值** |
| 附件 / 依赖 | 契约有 `attachments` / `depends_on`；没有界面 | `任务管理/11` / `12` | 附件搬值（重置 id）；依赖**不搬**（理由见第 3 节） |

**因此本任务对「复制含子任务/标签/象限/清单」的口径必须写死为：复制的是这些字段的值，不是复制那些还不存在的实体。** 具体地——本任务不渲染任何子任务列表、不渲染标签芯片、不渲染象限标记、不渲染清单归属，也不为它们做任何选择器；它只保证：**当上述子任务把实体做出来、往这些字段里写进值之后，复制会原样带走它们，不需要回头改复制的实现。** 这一点是可证伪的：第 3 节给的是一张**逐字段的全量表**（覆盖 `Todo` 今天的每一个字段 + 本任务新增的 `archivedAt`），而不是一份「今天有界面的字段」清单；新字段进契约时，若不在这张表里出现，就是复制漏了它。

**本任务不做（逐条给出归属）：**

1. **不做手动归档入口**（行内、菜单、批量都不做）。需求节写的是「已完成任务**定期**归档」与「归档页可查可恢复」——归档的发起方是规则，不是用户；用户手上的动作是**还原**。加一个手动归档按钮会立刻把行内密度问题引回来（第 2 节），且要向用户解释「我都点完成了，为什么还要再点一次归档」。若产品后续要它，最自然的落点是导航壳落地后的批量操作条，归 `视图与统计` / `桌面端形态`。
2. **不做归档策略的配置项**（几天后归档、归档保留多久、自动清理）。需求节「不做 归档数据清理策略之外的扩展」；阈值取常量（第 4.3 节），不进设置面板。
3. **不做手动顺延 / 改期按钮**。「改期」是键盘全操作与列表操作的能力，归 `桌面端形态/02`；今天改截止日的路径已经有（点标题进编辑）。本任务的顺延只有「自动规则 + 一个开关」两件东西。
4. **不做顺延 / 改期次数统计**。`视图与统计/10-拖延洞察` 的一句话验收就是「顺延/改期次数统计与卡壳提示正确」，而契约里**没有**记录次数或原始截止日的字段——这是一个需要契约扩展的缺口，见第 15 节第 4 条。
5. **不做导航、不做路由、不做独立页面**（第 4 节详述）。
6. **不新增第四类页面提示来源**（第 12 节详述）；反馈一律由焦点与可见结构承担。
7. **不动 `TodoFields.vue` 一行**：三个能力都不是字段。这是本任务对 02 验收 B2 / B3 的最强形式——加能力不必碰字段块，加字段不必碰容器。

### 2. 要求 a 的正面回答：三个操作的入口放哪，行内会不会挤爆

**结论：待办行只新增一个按钮（复制）。归档与顺延都不进待办行。**

标题按钮是 `block w-full text-left`（**会换行，不截断**），100px 下一行约放 6 个汉字、标题自然折行、行高随之增长——这与今天一条长标题的行为完全一致，不产生横向滚动、不产生省略号。**320px 下仍然装得下，所以不需要弹层、不需要菜单、不需要新造基础组件。**

**关于新造基础组件的表态（编排者点名要求）：** 本任务**不新造** dropdown / menu / dialog / popover。理由三条：① 上表证明不需要它——一个按钮装得下；② 一个可用的下拉菜单要自建触发、定位（含视口翻转）、焦点圈闭、Esc、点击外部关闭、`role="menu"`/`menuitem` 键盘导航（↑↓/Home/End/首字母）与移动端全屏化，DESIGN.md「待补充」里 dialog 也还没有条目——这是一族新组件与一次视觉语言扩展，不是一个 简化 级子任务能顺带交付的；③ 真正需要它的是「行操作变多」的那一天（改期、移到清单、加标签、设象限、转子任务…），那是 `桌面端形态/02-键盘全操作` 与各母任务共同的需求。**因此：若将来确需菜单，应另立任务（建议归 `桌面端形态/01-主窗导航壳` 之后，与 `02-键盘全操作` 同期），本任务不预埋任何菜单结构。**

**删除按钮必须一并对齐（本任务范围内的必要改动，非顺手重构）：** 现状删除按钮是 `!p-2` + 17px 图标 = **33×33**，低于 DESIGN.md「待办行：操作按钮（完成/删除）触控区 ≥ 44px」的硬性基准。新增的复制按钮按基准取 44×44 后，两个相邻同类图标按钮尺寸不一致是同一控件组内的视觉断裂。**因此删除按钮改为与复制同形**（`min-h-11 min-w-11 !p-2`，图标 `Trash2 :size="20"`），两处一起达标。这是新增按钮直接导致的必要改动，改动面是一行类串 + 一个数字。

### 3. 复制的字段口径（全量表）

**语义定义：复制 = 以源任务为模板新建一条**「要再做一遍的」**任务**——不是做一个历史快照。这条语义决定了下表每一行的取舍：凡是描述「这条记录是谁、走到哪一步了、在图里的哪个位置」的，一律重置；凡是描述「这件事是什么、什么时候做、属于哪一类」的，一律复制。

| 字段 | 处置 | 理由 |
|------|------|------|
| `id` | **重置**：`crypto.randomUUID()` | 两条任务同 id 会在同步日志里互相覆盖 |
| `title` | 复制，**原样，不加「副本」后缀** | 见下方「为什么不加后缀」 |
| `status` | **重置**：`"open"` | 复制一条已完成的任务，要的是一条待做的任务 |
| `createdAt` | **重置**：当前时刻 | 它是这条新记录的诞生时间 |
| `completedAt` | **重置**：`null` | 随 `status` |
| `archivedAt`（本任务新增） | **重置**：`null` | 副本是活的任务，不是归档件 |
| `dueDate` | 复制 | |
| `reminderAt` | 复制 | 若已过期，按 03 既有规则处理（保存后立即提醒一次）——**不静默清空**，那会让用户以为提醒没复制过来 |
| `notes` | 复制 | |
| `startDate` | 复制 | |
| `startsAt` / `endsAt` | 复制（成对，要么都在要么都不在，契约规则天然满足） | |
| `estimatedMinutes` | 复制 | |
| `recurrence` | 复制（字段值） | 规则计算归 `06`/`08`；今天没有界面能设它，但入站同步可能带来值，原样带走比丢掉正确 |
| `listId` | 复制（字段值） | 实体归 `清单` 母任务 |
| `important` / `urgent` | 复制（字段值，含 `null` 三态） | 实体与界面归 `四象限` 母任务；`null`=「用户没说过」必须原样保留，改成 `false` 等于替用户表态 |
| `sortOrder` | **重置**：`null` | 手动排序归 `视图与统计/02`。副本是一条新行，位置由插入规则决定；继承源的 `sortOrder` 会让两行争同一个位置 |
| `tagIds` | 复制（**新数组**，元素为同一批 tag id） | 标签是共享实体，指向同一个标签是对的；数组必须新建，不能与源共用引用 |
| `subtasks` | 复制，**每项重新生成 `id`，`done` 一律重置为 `false`**，`title` 原样 | ① 子任务 id 是契约 id，两条任务持同 id 子项会让「按 id 定位子任务」二义；② 复制是为了再做一遍，把已勾选的一起搬过去，用户得逐个取消勾选 |
| `attachments` | 复制，**每项重新生成 `id`**，`kind`/`url`/`name` 原样 | 复制的是引用（本地路径或 URL），不复制文件本体；文件本体的处置归 `任务管理/11` |
| `dependsOn` | **重置**：`[]` | **本任务唯一判「不复制」的集合字段。** 依赖是这条任务在任务图里的位置，不是它的内容：复制一条「等 A 完成」的任务，得到第二条同样在等 A 的任务，几乎不是用户要的；且 `12` 要拒绝环依赖，复制会批量制造需要重新校验的边。母任务拆解清单给本任务的一句话验收也只点名了子任务/标签/象限/清单，未含依赖 |

**这张表的维护规则（写给后续往契约加字段的子任务）：** 每新增一个 `Todo` 字段，必须在此表补一行并明确「复制 / 重置」；不在表里出现即视为复制漏了它。判据就是本节开头那句语义定义。

**为什么标题不加「副本」后缀：** ① 「xxx 的副本」是文件管理器的语言，不是待办的语言——用户复制「周报」多半就是要再写一次「周报」，后缀反而要手工删掉；② 一旦加后缀就得定义「再复制一次」的编号规则（副本 2？副本的副本？），凭空多一条产品规则；③ 「哪条是新的」这个问题由**位置与焦点**回答，不用文案：副本恒插在源行**正下方**，且复制后立即进入副本的编辑态（第 8.2 节），焦点就在它的标题输入框里。

**插入位置：** 源行索引 + 1（复用 04 已有的 `insertTodo(todo, index)`，不新写插入逻辑）。**不是列表顶端**——顶端是 `add` 的位置，用于「刚刚新写的」；副本紧邻源行才说明「它是从这条来的」。
> 已知取舍：本任务不引入排序持久化（归 `视图与统计/02`），因此重启后副本相对源行的位置取决于仓库返回顺序。这与 04「撤销删除按原索引恢复」是同一处既有取舍，不新增。

### 4. 要求 b 的正面回答：归档「页」交付到什么程度

#### 4.1 事实前提

- **没有导航壳。** `桌面端形态/01-主窗导航壳`（「任务/视图」两段切换，视图页容器就位）状态是**拆解**，未开始；`桌面端形态` 与 `视图与统计` 两个母任务整体都在「拆解」态。
- 应用今天是**单页单栏**：`<main>` 里依次是页头、提示条、设置面板、创建表单、快捷键提示、列表。没有路由、没有页面概念、没有任何「切到另一个页面」的先例（设置面板是同页内的 `v-if` section）。

**若本任务自建一套导航去承载「归档页」**，结果是：造一个 `桌面端形态/01` 三个月后必须整体替换的导航模式，同时把「页面切换」这个交互模型的决定权从那个母任务手里拿走。这正是 03 第 4.3 节拒绝自建详情面板时用的同一条理由（没有地基就不要造一层新形态）。

#### 4.2 交付边界：交付「归档区」，不交付「归档页」

**本任务交付：主列表下方一个默认收起的 disclosure 区块（`src/components/ArchiveSection.vue`），展开后按归档时间倒序列出已归档任务，每条可还原、可删除。** 需求节的验收是「归档页可查可恢复」——**可查、可恢复两件事在归档区里全部成立**，成立方式与页面无关。

**为什么这是正确的边界，而不是偷工减料：**

1. 它满足验收的每一个字，且零导航、零路由、零新基础组件。
2. 它是**可整体搬迁**的：归档区做成一个只依赖 store 的独立组件，不读 `App.vue` 的任何状态、不发任何事件出来。导航壳落地那天，「变成一个页面」＝把 `<ArchiveSection />` 这一行从 `App.vue` 挪进新页面的模板，**组件内部一行不改**。
3. 它不预设任何将来必须推翻的形态——收起态只占一行，展开态就是一张与主列表同款的卡片列表。

#### 4.3 归档规则（自动执行）

| 项 | 取值 | 理由 |
|----|------|------|
| 判据 | `status === "completed"` **且** `archivedAt == null` **且** `completedAt` 的本地日历日距今 **≥ 7 天** | |
| 阈值 | 常量 `ARCHIVE_AFTER_DAYS = 7`，不可配 | 一周内完成的任务用户还会回头看（周报、成就页按周口径，`视图与统计/07`/`08`）；超过一周即历史。需求节明写不做归档策略的扩展 |
| `completedAt` 为空的已完成任务 | **不归档** | 无从判断"完成多久了"；这种组合只可能来自入站同步，凭空归档它是替另一端做决定 |
| 未完成任务 | **永不归档** | 归档一条没做完的任务＝把待办藏起来，那是「开始日期 / 将来」的语义（03 已承担），两条路会互相打架 |

| 播报 | 不播报（第 12 节） | |

#### 4.4 还原的语义

**还原 = 取消归档 + 取消完成**（`archivedAt → null`、`status → "open"`、`completedAt → null`），一次写入、一条 `change` 历史条目。

**为什么必须一并取消完成（这是一个正确性问题，不是偏好）：** 若还原只清 `archivedAt` 而保留 `completed` + 旧 `completedAt`，那么下一次自动归档一跑，这条任务**立刻又被归档回去**——用户点还原，看到它闪一下就没了。要么改写 `completedAt`（伪造完成时刻，会污染 `视图与统计` 的热力图与统计），要么加一个「不再自动归档」的标记（新字段），两者都比「还原＝把它拿回来继续做」更贵也更绕。

界面上必须说清楚，因为这不是「还原」二字的字面含义：归档区展开后第一行是一句说明——**「还原会把任务放回待办列表，并标记为未完成。」**（`text-xs text-slate-500 dark:text-slate-400`），还原按钮的 `aria-label` 为 **`还原 {标题} 到待办列表`**。

### 5. 要求 c 的正面回答：顺延

#### 5.1 开关放哪：设置面板，不是每条任务

放在**设置面板新增的「任务」fieldset** 里，一个 checkbox 行，与「关闭按钮隐藏到托盘」「显示今日卡片」同款结构。

- **为什么不是每条任务一个开关**：那需要一个新的契约字段（今天没有）、一个新的字段表控件（checkbox 形态，03 已为它留了分支但没人用）、以及「这条顺延那条不顺延」的持续心智负担；而 TODO.md 的原文「逾期未完成自动滚到今天（可开关）」是**全局规则的语气**，不是任务属性的语气。

- **默认值：关。** 理由：自动改写用户亲手设定的截止日是有副作用的行为，且本任务**不记录原始截止日**（契约里没有该字段，见第 15 节第 4 条）——默认开会让用户某天早上发现所有逾期日期都变成了今天且无法追溯。默认关 + 开关旁一句说明，是把这个决定交还给用户。
- **持久化 key**：`behavior.rolloverOverdue`，走既有 `loadBooleanPreference` / `saveBooleanPreference`（与 `behavior.closeToTray` 同路），store 加 `rolloverOverdue` + `setRolloverOverdue`，形状与 `showTodayCard` 逐行对齐。

文案：

- 标题行：**「逾期任务自动顺延到今天」**
- 说明行：**「每天开始时，把逾期未完成任务的截止日改为今天。提醒时间与时间段不变。」**
- 同一 fieldset 内另有一行不带控件的说明（归档的可发现性）：**「已完成超过 7 天的任务会自动归档，可在列表下方「已归档」中查看与还原。」**

#### 5.2 顺延的语义（逐条表态）

| 问题 | 回答 | 理由 |
|------|------|------|
| 顺延到明天还是今天？ | **今天** | TODO.md 原文「逾期未完成自动滚到今天」。顺延到明天等于替用户又推迟一天 |
| 按原间隔顺延？ | **不** | 「按间隔」是周期任务的语义，归 `06`/`08`。本任务的顺延对一次性任务与周期实例是同一条规则：把过去的截止日拉到今天 |
| 只对过期任务生效？ | **是**：`status === "open"` 且 `dueDate` 的本地日历日 < 今天 | 判据直接复用 `dueDate.ts` 既有的 `isOverdue(dueDate, completed)`，不新写 |
| 已完成 / 已归档的任务 | **不动** | 已完成的任务谈不上逾期 |
| **无截止日的任务顺延意味着什么？** | **什么都不意味着——一个字都不改** | 没有截止日就没有「过期」这件事。**绝不给它安一个今天的截止日**：那是凭空替用户造数据，而且会让「没有截止日」这个用户的明确选择在某天早上被静默改掉。开始日期（`startDate`）同理不动 |
| 改哪些字段？ | **只改 `dueDate`** | 提醒是绝对时刻、时间段是实际占用的一段时间、开始日期是「何时可以开始看见它」——把它们一起平移等于替用户重新排一次程；且被平移到过去的提醒会立刻触发一次。「顺延」直觉上像「整体推迟」，所以这条必须在设置说明里明写（见 5.1 文案） |
| 一次顺延多少条？ | 全部符合条件的行，逐条 `applyChange(id, { dueDate: 今天 })` | 每条产生一条出站 op（与用户手改截止日走同一条路），无批量协议 |

#### 5.3 触发时机：启动一次 + 日切一次 + 回到前台补一次

新增 `src/lib/day-rollover.ts`，导出 `registerDayRollover(handler): () => void`（形状与 04 的 `registerUndoShortcut` 一致，返回注销函数），由 `App.vue` 在 `onMounted` 注册、`onBeforeUnmount` 注销，卡片窗口沿用既有 `isCard` 提前返回**不注册**。

| 触发 | 机制 | 为什么需要它 |
|------|------|-------------|
| 启动 | `onMounted` 里立即跑一次（此时 `hydrate()` 已在 `main.ts` 中 await 完成） | 关了三天再打开的那一次 |
| 日切 | 一次性 `setTimeout` 到**下一个本地 00:00 之后数秒**，触发后执行并重新武装（不是轮询） | 长期开着的桌面窗口跨过午夜 |
| 回到前台 | `document.visibilitychange` 变为可见时补检一次 | 定时器在系统睡眠/挂起期间不可靠；这一条是它的兜底 |

- **不做轮询**：一个每分钟醒一次的定时器只为了等一天一次的事件。
- **不引入第三个全局监听源**：`day-rollover.ts` 只挂一个 `document` 级 `visibilitychange`；全仓监听源随之为三处（`appearance.ts` 的 `matchMedia`、`undo-shortcut.ts` 的 `window keydown`、本任务），各自有注销函数。
- **让位规则**：执行时**跳过当前处于编辑态的那一行**（`App.vue` 把 `editingId` 作为 `skipId` 传给 store）。否则日切会在用户打开的编辑表单底下改掉 `dueDate`，而草稿里还是旧值——用户一点保存，就把刚顺延的结果又改回去了（一次用户完全不知情的"编辑"）。归档同理跳过：一行不能在自己的编辑表单打开时从列表里消失。这与 04 的「编辑态让位给原生撤销」同源。
- **一次遍历同时做两件事**：store 暴露一个入口 `runDayStart({ rolloverOverdue: boolean; skipId: string | null })`，内部先归档后顺延（顺序无副作用交叉：归档只碰已完成、顺延只碰未完成）。

### 6. 要求 d 的正面回答：归档 / 删除 / 完成三者的关系

| | **完成** | **归档** | **删除** |
|---|---|---|---|
| 一句话语义 | 这件事做完了 | 做完的事不必再看见 | 这条记录不该存在 |
| 谁发起 | 用户（行首完成圈） | **规则**（完成满 7 天） | 用户（行尾垃圾桶） |
| 数据 | `status="completed"` + `completedAt` | `archivedAt` = 归档时刻 | 整行从 `items` 移除 |
| 在主列表 | **仍在**，删除线 + 低对比文字 | **不在** | 不在 |
| 在归档区 | 不在 | **在** | 不在 |
| 怎么反悔 | 再点一次完成圈 | 归档区「还原」（＝拿回来并变回未完成，4.4） | Ctrl+Z（04 既有） |
| 撤销栈 | 入栈（04 既有） | 自动归档不入栈；还原入栈（第 7 节） | 入栈（04 既有） |

**「归档的任务还出现在列表里吗」——不出现。** 这是归档存在的唯一理由：需求节写「保持列表轻快」，而今天主列表显示的是**全部** `items`（含所有历史完成项，`App.vue:565`）。若归档后仍留在列表里，这个能力就等于什么都没做。

**三者在界面上如何区分（用户不需要读文档就能建立的心智）：**

- **完成**是一次可逆的状态切换，痕迹留在原地（划掉的那一行还在你眼前）。
- **归档**是位置的改变——一行从上面的卡片消失，下面「已归档（N）」的计数加一。用户第一次遇到它时，计数变化就是解释；再展开就看到它在哪。**归档没有按钮，所以不需要教用户"什么时候该点归档"**——这是不做手动归档入口的额外收益。
- **删除**是唯一的破坏性动作，且是唯一用 red 语义色的（`hover:text-red-600`，DESIGN.md「破坏性操作用 red 语义色并与常规操作在视觉上分离」）。归档区里同样保留删除按钮：否则一条任务一旦被归档就再也删不掉，那是死路。

### 7. 撤销栈的参与规则（需求节并入项的正面回答）

#### 7.1 两条判据（写死，后续任何新操作照此判）

> **判据一（入撤销栈）：** 用户在本设备亲手发起 **且** 改变的是一条**已存在**任务的字段或存在性（删除）。**产生新任务的操作不入栈**（新建、复制）。
>
> **判据二（清空重做栈）：** 用户在本设备亲手发起的**任何**变更都清空重做栈，不论它是否入撤销栈。系统自动规则（定期归档、日切顺延）与入站同步**不清空**。

**判据一为什么把「产生新任务」划出去**（这条必须给技术理由，否则它只是 04 的历史遗留）：撤销一次复制＝移除刚刚创建的那一行，而**焦点此刻就在那一行里**（第 8.2 节：复制后进入副本的编辑态）。04 的撤销栈**没有也不该有**焦点管理——Ctrl+Z 可以在页面任何地方按下，它无从知道该把焦点还到哪。让「产生新行」的操作进栈，等于引入一个撤销栈解决不了的焦点缺口（焦点掉进 `<body>`，键盘用户被踢回页面顶部）。反悔通路另有其人且更近：副本此刻就在编辑态里，Esc 关闭后它那一行的删除按钮就在原地。新建同理（04 已定，本任务不推翻）。

**判据二为什么把自动规则与入站同步划出去**：重做栈的语义是「用户刚撤销掉的那几步，还能再走回去」。让它失效的应当是**用户自己又走了一条别的路**，而不是一个后台规则或另一台设备在他没看的时候动了别的任务——用那些去清空重做栈，等于让 Ctrl+Y 在任意时刻随机失效。正确性上不留洞：`applyEntry` 既有的陈旧判据（行已不存在则丢弃并向下取、id 已存在则拒绝插入）对自动规则与远端改过的行同样生效，04 走查证据第 9 条已实测这条路径。

#### 7.2 逐操作判定表（评审可按此表逐行构造场景）

| 操作 | 性质 | 入撤销栈 | 清空重做栈 | 撤销它意味着什么 |
|------|------|:---:|:---:|------|
| 完成 / 取消完成（既有） | 用户 · 改既有行 | 是 | 是 | 回到原来的 `status` 与 `completedAt`（原时刻） |
| 编辑（既有） | 用户 · 改既有行 | 是 | 是 | 字段级写回旧值 |
| 删除（既有） | 用户 · 移除既有行 | 是 | 是 | 整行按原索引复原 |
| **新建**（既有） | 用户 · 产生新行 | 否（04 已定，不改） | **是**（本任务修的那一行） | — |
| **复制**（新增） | 用户 · 产生新行 | 否（与新建同形，7.1） | **是** | — |
| **还原 / 取消归档**（新增） | 用户 · 改既有行 | **是**（一条 `change` 条目，同时携带 `archivedAt` / `status` / `completedAt` 三个字段的前后值） | **是** | 该任务回到归档区，并恢复为已完成、恢复原 `completedAt` |
| **归档区内删除**（新增入口，既有操作） | 用户 · 移除既有行 | 是（走既有 `remove`） | 是 | 整行复原，仍在归档区 |
| **自动定期归档**（新增） | 系统规则 · 批量 | **否** | **否** | — |
| **自动逾期顺延**（新增） | 系统规则 · 批量 | **否** | **否** | — |
| 入站同步（既有） | 另一端 | 否 | 否（不变） | — |

**自动批量为什么不入栈（两条，都可验证）：** ① 一次日切可能顺延或归档数十条，而栈深上限是 50（04 定），一次自动执行就能把用户真正想撤的条目全部挤出栈底；② 撤销的心智是「撤掉我刚做的那一步」，而用户对这一步没有任何动作记忆——按 Ctrl+Z 撤掉一件自己没做过的事，比按了没反应更糟。**反悔通路**：归档 → 归档区逐条还原；顺延 → 关掉开关 + 点标题改回截止日（编辑态本来就能改）。已知取舍见第 15 节第 4 条。

#### 7.3 落地要求（并入项验收「`recordHistory` 的注释与实际行为相符」的判据）

1. `recordHistory` 内的 `redoStack.length = 0` **保持不动**；其注释改为陈述判据二的完整规则（哪些路径清、哪些不清），而不是只解释"新动作分叉"。
2. `add` 成功后、`duplicate` 成功后**各自** `redoStack.length = 0`（都不入撤销栈）。这一行是并入项点名的「一行可修」，本任务在同一条规则下一次改完。
3. 自动路径（`runDayStart` 内的归档与顺延）走 04 已有的**核心写入层** `applyChange`，**不经** `update`、**不调** `recordHistory`、**不碰** `redoStack`——两层结构 04 已经建好，本任务零新增机制。
4. `unarchive` 走 `update` 同款路径（写入 + `recordHistory`），因此自动获得「空操作不入栈」的保护（04 的 `PlannedEdit`）。

- 复制按钮**只在展示态出现**（在 `v-else` 分支里），编辑态照 01 的既定规则隐藏——编辑态里 Tab 序仍然只有表单本身。


**逐条决定与理由：**

- **`v-if="store.items.length"`**：一条任务都没有的全新应用不显示归档区（不与「暂无待办」空状态并排出现两块空卡片）。**只要有任务就显示**，哪怕归档数为 0——见下一条。
- **归档数为 0 时仍然渲染（显示空状态）**，这是刻意的，三条理由：① **焦点永远有落点**——还原或删除最后一条时区块不会整体卸载，焦点可以稳稳落回展开按钮，不会掉进 `<body>`；② **可发现性**——用户不必等满 7 天才知道有归档这回事；③ 收起态只占一行（约 50px），不违背「保持列表轻快」。
- **默认收起，展开态不持久化**（组件内的一个 `ref`）：重启回到收起与「轻快」的目的一致，且省掉一个设置 key。
- **标题不是按钮**：归档件不可就地编辑（要改先还原）。这避免了「编辑一条归档任务」这种没有定义的状态，也让归档区的 Tab 序只有两个按钮。
- **标题样式按 `status` 分两支**：本机产生的归档件必然是已完成（划掉），但入站同步可能带来「已归档且未完成」的组合——那时不该让它假装自己完成了。两支的类串都是 `TodoItem.vue` 展示态已有的写法。
- **归档日期文案 `{M}月{D}日归档`**（今天则「今天归档」）：**不复用 `formatDueDate`**——那套文案是「离到期还有多久」的相对表达，套在归档时刻上会读出「逾期 3 天归档」这种不成句的话。
- **不显示到期徽标 / 备注 / 估时**：归档区是「找回来」的地方，不是浏览详情的地方；到期日对一条已完成的历史任务也没有意义。
- **卡片包住整块**（一个 `surface-card` + `overflow-hidden`，头部与列表在同一张卡里），不是「一张头部卡 + 一张列表卡」——后者在收起/展开之间会读作两个不相干的块。

#### 8.5 类串落地方式（受 UnoCSS 既有缺陷约束）

**本任务新增的每一个类串都必须出现在 `.vue` 文件里（模板或 `<script>` 均可——UnoCSS 扫整份 `.vue`）；禁止把任何类串写进 `.ts` 文件。**

理由是仓库里已被实证的事实：`uno.config.ts` 未配置 `content`，默认扫描管线不含 `.ts`，写在 `.ts` 里的类名不会生成 CSS。`src/lib/dueDate.ts` 的 `TONE_LABEL_CLASS.normal` 之所以还有一半样式，是因为它的浅色类恰好也出现在某个 `.vue` 里；它的 `dark:bg-slate-800` / `dark:text-slate-300` 在 `src/` 中**只出现在那一个 `.ts` 文件**，因而至今从未生效（03 评审已用 `pnpm run build` 产物核实）。

对本任务的具体约束：归档区的所有类串写在 `ArchiveSection.vue` 内；复制按钮的类串写在 `TodoItem.vue` 内；**不要**为归档新建一张 `.ts` 的类串映射表。若将来确实需要跨文件共享类串，正确的修法是放开 `uno.config.ts` 的 content 范围（已并入 `外观与设置/04`），在那之前不要制造新的受害者。

### 11. 移动端适配

- **触控目标**：新增的三个图标按钮（复制、还原、归档区删除）与对齐后的主列表删除按钮一律 `min-h-11 min-w-11`（44×44）；归档区头部是整行按钮，`min-h-11` + `px-4 py-3`，实际高度约 50px。相邻按钮间隙沿用行内 `gap-3`（12px），满足 DESIGN.md「相邻可点目标间隙 ≥ 8px」。
- **窄屏无横向滚动**：第 2 节已按 320 / 375 逐档核算，标题按钮换行而不截断，`documentElement.scrollWidth === clientWidth` 在 320 / 375 / 640 / 900 四档均应成立（与 03 走查同一判据）。归档区行结构与待办行同构（左侧文字 `min-w-0 flex-1` + 右侧两个定宽按钮），窄屏下同样只增高不增宽。
- **归档区不做内部滚动**：归档件多时页面纵向变长（继承 02 第 1 节的禁止清单精神——套定高滚动壳等于写死高度）。默认收起本身就是它对「列表轻快」的贡献。
- **手势**：**不做左滑归档 / 右滑完成等滑动手势。** 三条理由：① 仓库没有任何手势基础设施（无手势库、无 `touch` 事件处理），自建要处理滚动方向判定、阈值、回弹、取消与 `touch-action`，是一族新交互；② 滑动手势对键盘与读屏用户等于不存在，必须再补一套可见入口（那就是现在这套按钮），等于做两遍；③ 移动端整体形态归 `移动端形态` 母任务，滑动操作应与其导航、列表容器一并设计。本任务在移动端与桌面端是**同一套点击入口**（DESIGN.md 设计原则 2「跨端一致」）。
- **顺延开关**在移动端同样可见（不带 `isDesktop` 分支，5.1）。
- **日切触发器**在移动端尤为重要：应用被系统挂起后定时器不可靠，`visibilitychange` 补检是移动端的主路径（5.3）。

### 12. 可访问性

- **可访问名**（全部由文字直接给出，不靠图标形状）：
  - 复制 → `复制 {标题}`；主列表删除 → `删除 {标题}`（现状不变）
  - 归档区还原 → `还原 {标题} 到待办列表`（把「还原会变回未完成」这个非字面语义直接写进可访问名）
  - 归档区删除 → `删除 {标题}`
  - 归档区头部按钮 → 可见文字「已归档（N）」即其可访问名；箭头 `aria-hidden="true"`
  - 顺延开关 → 可见 `<label>` 包裹，可访问名＝「逾期任务自动顺延到今天」
- **分组与结构语义**：归档区是 `<section aria-labelledby="archive-heading">`，头部按钮包在 `<h2>` 里并持有该 id——读屏用户既能按标题跳转到「已归档」，也能就地展开它。展开按钮带 `aria-expanded` + `aria-controls` 指向 `v-show` 常驻的列表容器（与 02/03 的展开按钮同款，`v-show` 而非 `v-if` 正是为了让 `aria-controls` 始终指向存在的元素）。
- **键盘全通路**：
  - 待办行 Tab 序：完成圈 → 标题 → **复制** → 删除；DOM 顺序＝视觉顺序。
  - 复制后：焦点自动进入副本的标题输入框（01/03 既有机制），Esc / 取消把焦点归还副本的标题按钮（01 既定的三条归还路径原样生效）。
  - 归档区：头部按钮 → （展开时）每行的 还原 → 删除。
  - 还原 / 删除后焦点归还头部按钮——**这正是「N=0 时区块仍渲染」的直接理由**：归还目标恒存在，焦点永不掉进 `<body>`。
  - 本任务**不注册任何键盘快捷键**，不动 04 的 Ctrl+Z / Ctrl+Y 让位判据。
- **提示与播报——本任务不新增第四类页面提示来源。** 03 第 5.3 节允许新增第四类（并要求重跑那套核对），本规格**主动选择不用它**，因为反馈由更强的通道承担：
  | 事件 | 用户怎么知道 |
  |------|------------|
  | 复制 | 副本的**编辑表单打开、焦点进入其标题输入框**——焦点移动本身就会被读屏播报，且它同时回答了「新的那条在哪」 |
  | 还原 / 归档区删除 | 焦点归还头部按钮，读屏读出**更新后的**「已归档（N）」，计数变化即回执 |
  | 自动归档 | 「已归档（N）」计数增加；设置面板「任务」节明写规则 |
  | 自动顺延 | 逾期徽标（red）变为「今天」（amber）；设置面板开关旁明写规则 |
  这样做的收益是不必重跑 03 的优先级核对，也不引入「一条 transient success 长期压住 standing 存储 error」的风险（transient 在 03 的排序里优先于 standing，而一条成功提示没有天然的清除时机）。
  **已知取舍（明写）：** 自动归档与自动顺延**发生的那一刻没有任何播报**——读屏用户只有在再次浏览列表时才会察觉。取舍理由：两者都不丢数据、都可逆（归档区还原 / 关掉开关后手改），而为它们开一条提示通路要付出「重跑 03 全套优先级核对 + 承担遮蔽存储 error 的风险」。若编排者认为需要播报，最小改法是给 `page-alert.ts` 加第四个来源并按 03 第 5.3 节逐行复核，见第 15 节第 6 条。
- **不靠颜色单传**：归档计数、归档时间、空状态、顺延后的到期徽标全部由文字直接说明（徽标文案「今天」本身就是内容）。
- **对比度**：取值全部落在 DESIGN.md 已验证的 slate / amber 阶内，未引入新色。
- **焦点环**：按设计意图书写（`focus-visible:focus-ring`）。已知 `uno.config.ts` 的 `focus-ring` shortcut 实际失效（已转 `外观与设置/04`），本任务不绕开、不自造替代写法。
- **动效**：归档区箭头只动 `transform`（`rotate-180`），200ms 落在 DESIGN.md「微交互 150–300ms」内，并带 `motion-reduce:transition-none`（DESIGN.md「尊重 `prefers-reduced-motion`」）。列表增删**不加入场/退场动画**——列表项动画会与撤销/重做的即时状态切换打架，且 DESIGN.md 要求动画不得阻塞输入。

### 15. 交给编排者 / 开发的说明

1. **【前置必办】契约需要 `archivedAt`。** 今天 `Todo` 与 `TodoPatch` 里**没有任何归档字段**，`TodoStatus` 也只有 `Open` / `Completed`——**归档这件事今天存不下来**。落地要求：
   - `crates/contracts/src/lib.rs`：`Todo.archived_at: Option<String>`（ISO 瞬时，紧随 `completed_at`，配 `#[serde(default, skip_serializing_if)]` + `#[ts(optional = nullable)]`，与相邻可空字段同款）；`Todo::validate` **不加**新规则（时间戳格式全仓一律不校验，与 `completed_at` 一致）。
   - `TodoPatch.archived_at`：**必须**是 03 建立的 `Option<Option<String>>` + `#[serde(with = "present")]` 形状——否则「还原」（`archivedAt → null`）在另一台设备上读不到清空意图，归档件在对端永远回不来。
   - **选 `archivedAt` 字段而不是第三个 `TodoStatus::Archived` 变体**的理由：归档与完成是正交的两件事（「做完了」与「不必再看见」），合成一个枚举会丢掉「它是完成后被归档的」这个事实，并让 `activeItems` / `completedItems` / 统计口径全部要重新定义；AGENTS.md 也要求契约枚举优先保持无载荷、变更时复核服务端的未知字段放宽路径——加一个普通可空字段不触碰那条路径。
   - 重跑 `pnpm run types:generate`；`crates/server` 侧无需手改（`patch_from_json` 依赖 serde 派生的 `FIELDS` 表）。
   - **视图端同步点（漏一处＝归档同步不出去）**：`stores/todos.ts` 的 `FieldChange`、`patchFromTodo`、`applyRemoteUpsert`（两个分支）、`add` 的出站 op。

2. **实现顺序**：先落契约与 bindings，再做归档区与自动规则；复制与顺延不依赖契约改动，可先行。
