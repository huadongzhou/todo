# 统一创建界面

- 级别：全流程
- 状态：完成

## 需求（产品）

### 目标与场景

README「产品定义 › 待办任务」写定：「新建待办在同一个创建界面内一次完成全部设置」。今天的现状离这句话有两段距离：

1. **容器不成形**：`src/App.vue:453-509` 的创建表单是「一行标题输入 + 一个展开按钮 + 两字段详情区（截止日 / 提醒）」，详情区是写死的 `sm:grid-cols-2` 两格（`App.vue:484-508`）。v1 目标字段有十余个（契约 `crates/contracts/src/lib.rs:33-100` 已落 12 组），这个形状装不下，而且每加一个字段都要改容器本身。
2. **创建与编辑两套字段**：`任务管理/01` 已给编辑态（`src/components/TodoItem.vue`）做了与创建表单详情区 **DOM 同构** 的字段块，并在其规格第 0 节明确留给本任务：「共用字段块、不共用容器形态」，字段块提为 `src/components/TodoFields.vue`。现在两处是两份手抄的相同结构，任何一处改动都会漂移。

**本任务解决的是「容器与创建流程」这一件事**：交付一个能容纳 v1 全字段、且新增字段不必改容器的统一创建界面，并把字段块提取为创建与编辑共用的单一来源。各字段的业务语义（周期怎么算、标签从哪来、子任务怎么排序）不在本任务，见下方范围表——本任务是它们共同的落点，先把落点做对。

服务对象是两类用户，且必须同时成立（README「发布基线 › 目标用户：全场景通用」）：

- **轻量用户**：多数任务只有一个标题。他们的路径必须比现在更短或一样短，绝不能因为界面能装十几个字段而多出一次「展开」。
- **重度用户**：一次录入就把截止日、提醒、标签、象限、清单、周期设全，不接受「先创建、再点进去补齐」。

### 范围

#### 一、字段：哪些字段的**控件**在本任务进创建界面

判定原则（两条同时成立才进）：**① 该字段今天在应用里端到端可用**（契约 + store + 本地持久化 + 同步 + 界面回显都在）；**② 没有兄弟子任务持有它的业务语义**。字段在 `crates/contracts/` 里存在只满足了「有地方存」，不等于本任务要做它的界面。

| 字段 | 本任务是否做控件 | 理由 / 归属 |
|------|-----------------|------------|
| 标题 `title` | ✅ 做 | 端到端已通；本任务另需重做输入控件以对齐码点口径（见并入项） |
| 截止日 `dueDate` | ✅ 做 | 端到端已通（`stores/todos.ts` 的 `add`/`update`、出站 op、列表徽标均已支持） |
| 提醒 `reminderAt` | ✅ 做 | 端到端已通；创建路径的出站 op 漏字段由并入项修复 |
| 备注 `notes` | ❌ 不做 | 归 `任务管理/03-基础字段扩展`（其一句话验收即「备注/开始日期/估时/时间段可设可存可显」），且 03 依赖 02 |
| 开始日期 `startDate` | ❌ 不做 | 同上，归 03；且「未到开始日收进将来」是 03 的验收内容 |
| 时间段 `startsAt`/`endsAt` | ❌ 不做 | 同上，归 03；契约还带跨字段规则（`endsAt` 需有 `startsAt`，`lib.rs:113`），该规则的界面表达属 03 |
| 估时 `estimatedMinutes` | ❌ 不做 | 同上，归 03 |
| 周期 `recurrence` | ❌ 不做 | 规则计算归 `任务管理/06-周期规则引擎`（domain 层，尚未开始），界面与实例生成归 `08-实例生成与周期标识`（依赖 06、02）。06 未落地时做周期选择器＝做一个选完不会发生任何事的控件 |
| 标签 `tagIds` | ❌ 不做 | 归 `标签/03-任务贴标签`（一句话验收：「创建与编辑时可加/移多标签」），其外部前置正是本任务；且标签实体本身尚不存在（`标签/01-标签实体与契约` 未开始），没有可选项 |
| 象限 `important`/`urgent` | ❌ 不做 | 归 `四象限/02-快速设置入口`（一句话验收：「列表/详情/创建界面三处可标象限」），其外部前置正是本任务 |
| 清单 `listId` | ❌ 不做 | 清单实体与管理界面均未开始（`清单/01`、`清单/02`），没有可选项可选；归属操作归 `清单/03-任务归属操作`。⚠️ 清单母任务两处措辞自相矛盾，见「留给编排者裁决」第 1 条 |
| 子任务 `subtasks` | ❌ 不做 | 归 `任务管理/10-子任务`（全流程，依赖 02） |
| 附件与链接 `attachments` | ❌ 不做 | 归 `任务管理/11-附件与链接`（依赖 03） |
| 依赖 `dependsOn` | ❌ 不做 | 归 `任务管理/12-任务依赖`（依赖 03） |
| 手动排序 `sortOrder` | ❌ 不做 | 不是创建时录入的字段，由拖拽产生，归 `视图与统计/02-手动拖拽排序` |

**结论：本任务落地 3 个字段的控件（标题 / 截止日 / 提醒），但必须交付一个装得下上表全部行的容器。** 这两件事不矛盾，也正是本任务成立的理由：现在只有 3 个字段，是重做容器成本最低的时刻；等 6 个子任务各自往里塞字段时再改容器，就是 6 次返工。容器的「装得下」在本任务用结构性验收证伪（见验收标准 B 组），不靠承诺。

#### 二、除字段外，本任务做什么

- 重做主窗口的统一创建界面容器与创建流程：字段增加时不必改容器、不必改提交/校验/重置逻辑。
- 把字段块提取为 `src/components/TodoFields.vue`，由创建表单与 `TodoItem.vue` 编辑态共同消费（继承 `任务管理/01` 规格第 0 节的既有约定：**共用字段块、不共用容器形态**——创建是页面顶部常驻表单，编辑是行内展开，两者外壳不合并）。
- 重新定义表单校验反馈机制，并同时覆盖创建与编辑两处（并入项要求）。
- 标题输入的码点口径对齐与上限反馈（并入项要求）。
- 创建路径出站同步 op 补 `reminderAt`（并入项列为前置必办）。

#### 三、明确不做

- **不做任何字段的管理界面**：标签管理、清单管理、象限视图各归其母任务。
- **不做详情页 / 详情面板**：应用至今没有详情页（`任务管理/01` 规格已实证），本任务不新建。编辑仍是行内展开。
- **不改 01 已定的编辑交互**：点标题进编辑、显式保存、Esc/取消丢弃草稿、焦点归还标题按钮、未改动不提交——一条都不动。本任务碰 `TodoItem.vue` 只为两件事：字段块换成共用组件、接入新的校验反馈机制。
- **不做其他创建入口**：迷你捕捉窗（`桌面端形态/03`）、卡片快添（`桌面端形态/05`）、移动端语音与分享接入（`移动端形态`）、`todo://` 深链（`开放与集成`）均不在本任务。本任务只保证它们将来接入时无需绕开校验与归一化（统一经 store 的创建路径，规则不下沉为界面组件私有）。
- **不做草稿持久化**：关闭应用后未提交的草稿不保留。「秒记不丢」是迷你捕捉窗要解决的问题，不是常驻表单的。
- **不做字段粘性（创建后保留上次取值）**：本任务三字段一律清空。粘性策略是字段自身的产品语义（例如「在某清单视图里创建默认归该清单」），由需要它的子任务提出，本任务不预埋机制（AGENTS.md：一次性代码不抽象）。
- **不新增跨字段校验规则**：如「提醒不得晚于截止日」等，产品未定义；契约已有的跨字段规则随其字段进入对应子任务。
- **不改契约、不改服务端**：`TodoPatch` 的显式置空缺口不在本任务修，见「留给编排者裁决」第 2 条。

### 留给编排者裁决 / 遗留问题（不阻塞进入设计）

1. **`清单` 母任务内部措辞矛盾**：`.agents/tasks/清单/_母任务.md` 的「范围」写「不做：……创建界面清单入口（归「任务管理」）」，但同文件拆解清单第 03 行的一句话验收写「创建与编辑可选清单」，且其「外部前置」写 `任务管理/02` 完成。两处指向相反。本任务按仓库事实判定**清单控件不进本任务**（`清单/01` 契约与 `清单/02` 侧边栏均未开始，没有任何清单可选，做出来的只能是一个空下拉），只在字段块留接缝。请编排者裁决并统一其中一处措辞，避免两个母任务都以为对方在做。
2. **`TodoPatch` 无法表达「显式置空」**（已立案于 `任务管理/03` 的前置必办，本条只标注对本任务的影响面）：本任务允许用户清空截止日与提醒，清空在本机完全生效（内存、SQLite、本地提醒定时器都对），但推给其他设备的 op 里读不到清空意图，另一台设备会保留旧值。本任务**不修契约、也不因此禁止清空**（字段一填就去不掉是更糟的产品行为）。建议 03 落地后，回归本任务的「清空截止日 / 清空提醒」两条路径。
3. **编辑态容器形态的阈值**：`任务管理/01` 规格约定字段数增长到约 5 个以上时，需评估「行内展开 → 独立详情面板」。本任务只落 3 个字段控件，不触发；但 03（+4 字段）、10、11、12 累计后必然触发。届时属于新的界面形态，应另起任务，本任务不预埋任何面板结构。
4. **母任务一句话验收的口径**：拆解清单给本任务的验收是「一个界面完成全部字段设置并创建成功」。按上表的范围界定，本任务完成时该句只能对**已实现字段**成立；「全部字段」的完整成立点是母任务集成验收（各字段子任务落地之后）。请编排者在集成验收时按此口径核对，不要求本任务提前实现兄弟子任务的字段——否则本任务将同时吃掉 03、06、08、10、11、12 与三个兄弟母任务的范围。

### 1. 容器与字段块的分工（本任务的关键交付）

**一句话：容器只知道「有一个字段块」和「详情区是否展开」，不知道字段块里有什么。**

| 关注点 | 归属 | 说明 |
|--------|------|------|
| 字段清单、分组、排布、宽度 | `TodoFields.vue` | 新增字段只动这里 |
| 字段的控件类型、可见标签、校验规则、长度上限口径 | `TodoFields.vue`（及其配套组合式函数） | 两处消费同一份，B1 的「逐字段对照一致」由此结构性成立，而非靠人工对齐 |
| 草稿对象的创建与重置 | 字段块提供 `createEmptyDraft()`，容器整体替换 | 容器**不得**逐字段赋空值——那是 A4 与 B3 的直接冲突点 |
| 提交时把草稿交给 store | 容器 | 容器传**整个草稿对象**，不逐字段列举 |
| 校验的执行 | 容器调用字段块暴露的 `validate()`，只读布尔结果与错误文案 | 容器**不得**自己写「标题是否为空」这类规则 |
| 焦点 | 容器只持有「标题输入」一个入口（字段块 `defineExpose({ focusTitle })`） | 容器不为其他字段持有 ref |
| 外壳形态、按钮、展开开关、提交入口 | 容器 | 创建与编辑各写各的 |

**容器上的可证伪禁止清单**（评审做 B2 时按此逐条查，命中任一条即容器写死了）：

- 容器元素上不得出现 `grid-cols-*`、`sm:grid-cols-*`——列数规则在字段块内，随分组走。
- 容器上不得出现 `h-*`、`max-h-*`、`min-h-*`（`min-h-11` 只允许出现在控件本身）、`overflow-*`——详情区**不做内部滚动**，长了就让页面纵向滚动。给详情区套滚动壳等于写死了高度，且会在 375px 下把日期原生选择器裁掉。
- 容器的模板与脚本里不得出现除 `title` 外的任何字段名。`title` 是唯一例外，因为它是唯一必填字段（校验结果与焦点归位要指向它）。
- 提交、重置、校验、焦点四段逻辑不得按字段展开成分支或列举。

**接口约定**（供开发与 B3 判定，不是最终签名）：

```
TodoFields.vue
  props:  modelValue: TodoDraft   // 草稿对象；新增字段＝加一个键
          idPrefix: string        // id 前缀（创建用 "create"，行内编辑用 `todo-${todo.id}`）
          detailsOpen: boolean    // 详情区是否展开；编辑态恒 true
          detailsId: string       // 详情区容器 id，供容器的展开按钮 aria-controls 指向
  emits:  update:modelValue
  slots:  actions                 // 渲染在标题行尾；创建放「展开 + 添加」，编辑不用
  expose: validate(): boolean     // 校验并写入内部错误态
          focusTitle(): void
  另导出: createEmptyDraft(): TodoDraft
```

`actions` 插槽是「创建把两个按钮塞进标题行」与「编辑把按钮放在表单底部」这两种外壳的唯一差异点，也是不共用容器形态这条约定的落点。

### 2. 字段块的分组与排布规则

#### 2.1 可见性：什么进首行，什么进详情区

**必填字段进首行，可选字段一律进详情区。** v1 唯一必填字段是标题，所以首行恒为标题一个。这条规则不随字段数量变化——03 起加进来的全是可选字段，全部落详情区，首行形状永不变，A2 的「最短路径不退化」因此是结构性成立而不是承诺。

#### 2.2 分组：四组，按「这个字段回答哪个问题」归位

| 组 | 回答的问题 | 现在有 | 将来落进来的（产品判定表所列） |
|----|-----------|--------|------------------------------|
| 内容 | 这件事是什么 | —（标题在首行） | 备注 |
| 时间 | 什么时候 | 截止日、提醒 | 开始日期、时间段、估时、周期 |
| 归类 | 属于谁 / 是哪一类 | — | 清单、象限、标签 |
| 关联 | 挂了什么别的东西 | — | 子任务、附件、依赖 |

- **组内顺序＝契约 `crates/contracts/src/lib.rs` 中 `Todo` 的字段声明顺序**。取契约而非「重要性」排序，是因为它是仓库里唯一不会因人而异的顺序来源；今天按此得到「截止日 → 提醒」，与现状一致，本任务不产生顺序变更。
- **只渲染有可见字段的组**：今天只有「时间」组有字段，详情区里就只有它。
- **组标题在「详情区内可见组 ≥ 2」时才出现**。今天 1 组 → 无组标题 → 详情区外观与现状一致；03 加入备注后自然变成 2 组，组标题自动出现，**容器与已有字段一行都不用改**。
- **新字段四个问题都不沾时停下上报编排者，不许新开第五组**——新开组是界面形态变更，属新任务（与 01 第 8 节「行内展开 → 详情面板」的阈值同理）。

#### 2.3 排布：字段自己声明宽度，容器不排版

每个字段只声明两种宽度之一：

- **整行**（`col-span-full`）：控件高度随内容增长（多行文本、集合列表），或由多个子控件组成（时间段、周期、象限）。→ 备注、时间段、周期、象限、标签、子任务、附件、依赖。
- **半行**（默认占一格）：单一标量控件（单行文本 / 日期 / 时间 / 数字 / 单选或下拉 / 开关）。→ 截止日、提醒、开始日期、估时、清单。

用 `col-span-full` 而不是 `sm:col-span-2`，是为了让宽度声明与「组内几列」解耦：将来组内列数若变，整行字段不用跟着改。

**字段自身的辅助提示**（如现有的「提醒时间已过」）作为该字段定义的一部分紧随其后，取整行。这样提示随字段一起进出，不会像现状那样吊在栅格外面、加字段时需要重新安放。

#### 2.4 窄屏退化

- `< 640px`（`sm` 断点以下）：组内单列，整行与半行都是满宽；组标题保留；`col-span-full` 在单列下无副作用。
- `≥ 640px`：组内两列（`sm:grid-cols-2`）。页面主体是 `max-w-2xl`（672px），两列时每列约 300px，正好是日期与时间控件的自然宽度；不做三列——那会把 `type="datetime-local"` 的原生控件压到出现内部省略。
- 任何宽度下都不出现横向滚动（DESIGN.md 硬性；B2 的 375 / 900 两点即验此）。

### 4. 标题长度：码点口径与上限反馈（并入项 2 / C 组）

#### 4.1 口径

- **移除 `maxlength` 属性**——它按 UTF-16 code unit 计数，与契约 `validate_title` 的 `trimmed.chars().count()`（码点）不一致，emoji 场景下只肯收约一半。
- 改为在输入事件里按**码点**归一：`Array.from(v).length > MAX_TITLE_CHARS` 时取前 `MAX_TITLE_CHARS` 个码点重组并写回。上限值一律取 `MAX_TITLE_CHARS`（`src/lib/native.ts:12` 再导出的生成绑定），界面侧不写任何字面量，文案里的数字也用插值。
- 该归一同时覆盖打字与粘贴（粘贴同样触发 `input`），因此 C3 的「保留前 N 个码点、不整段丢弃」由同一段逻辑成立。
- 已知取舍：按码点截断可能切开 ZWJ 组合序列（如家庭 emoji）。这是 C1 钉死的口径（不是 grapheme cluster）带来的必然结果，与契约一致优先。

#### 4.2 可见反馈：计数器

- **何时出现**：仅当「剩余码点 ≤ 20」时出现，其余时间不占位。理由：500 字上限对绝大多数标题永远不会触及，常驻计数器是纯噪声；20 是「还剩一句话」的量级，足够在撞上限之前给出预告。
- **放在哪**：标题字段的标签行右端（`flex items-baseline justify-between`）。标签行本就存在，计数器出现时**不产生任何布局位移**——不新增行、不撑高输入框。
- **文案**：未达上限 `还可输入 {n} 字`；达到上限 `已达上限 {MAX_TITLE_CHARS} 字`。
- **视觉**：`text-xs tabular-nums`（DESIGN.md 字体：12 辅注、计数用 `tabular-nums` 防跳动）；未达上限 `text-slate-500 dark:text-slate-400`（同字段标签），达到上限 `text-amber-700 dark:text-amber-300`（DESIGN.md 语义色 soon 行字色，纯文字提示只取字色）。**不用 red**：达到上限不是错误，用户输入的内容一个字都没丢。

#### 4.3 屏幕阅读器反馈

- 计数器节点的 id 进标题输入的 `aria-describedby`（与错误文案 id 并列）。这解决「聚焦时可查询」，但**不解决**「打字过程中被告知」——读屏不会重播 describedby。
- 因此「撞上限」这个**事件**走第 5 节的单一 live region（tone = `warn`）：
  - 打字触顶：`标题已达上限，最多 {MAX_TITLE_CHARS} 字。`
  - 粘贴被截断：`标题已达上限，最多 {MAX_TITLE_CHARS} 字；粘贴内容超出的部分未加入。`
- **去抖规则**：同一次「触顶」只播报一次；标题码点数回落到上限以下后重新武装。否则用户按住一个键会把提示条刷成连续播报。
- C4：创建与编辑两处共用同一个标题控件，机制与文案天然一致，不需要各写一份。

### 5. 校验反馈机制（并入项 2 / D 组）

#### 5.1 问题与选型

01 的实测缺陷是：Enter 提交路径上焦点未移动，新出现的 `aria-describedby` 不被播报，错误只有视觉可见。三条候选：

| 方案 | 判定 |
|------|------|
| 给行内错误加 `role="alert"` | **否决**——这是页面上的第二个 live region，直接违反 D3 与 01 第 6 节；且列表里每行编辑态各带一个，数量随列表长度增长 |
| 提交失败时 blur→refocus 输入框骗读屏重读 | **否决**——依赖读屏实现细节，不同软件表现不一，且会打断 IME 组词 |
| **把校验结果投递进既有的单一 live region** | **采纳** |

#### 5.2 采纳方案

- `App.vue` 的 `pageAlert` 新增第三路来源 `formAlert`，**不新增任何 DOM 节点**。取值顺序改为 `formAlert ?? storageAlert ?? exportAlert`。
  - 与现状「storageAlert 永远优先」相反，理由：`formAlert` 是对用户**刚刚发起的动作**的直接答复且极短暂（下一次输入即消失），`storageAlert` 是常驻状态提示、被遮挡后会自己回来；若让 storageAlert 压住校验提示，D1 就会在「本机写入曾失败过」的设备上永久失效。
- 创建表单直接写 `formAlert`；`TodoItem.vue` 经 emit（或一个放在 `src/lib/` 的共享组合式函数）投递，具体由开发选——规格只要求两条：**不新增 DOM live region**、**两处文案与出现时机一致**。
- 提示条补 `aria-atomic="true"`，保证内容替换时整句重读（现状只有 `role="status" aria-live="polite"`）。
- 承载语义的扩展要写清：该提示条从「页面级状态」扩展为「页面级状态 + 表单结果」。这是有意的，因为 D3 不允许第二个通道。

#### 5.3 校验时机与文案（创建与编辑完全一致，D2）

- **提交时必校验**（两条路径：Enter 隐式提交、点提交按钮）。
- **脏值失焦校验**：标题「曾经非空、现在为空」时失焦即报；从未输入过内容的空标题**不报**。这一条规则同时给出两处的正确行为——创建表单刚打开时失焦不会弹红字（空是它的合法初始状态），编辑态清空一个已有标题时立刻报（与 01 现状一致）。DESIGN.md「失焦时校验而非逐键校验」由此满足。
- **不逐键校验**；用户重新输入后错误立即消失（01 现状行为保留）。
- 文案（两处逐字相同）：
  - 行内可见错误（`aria-describedby` 关联）：`标题不能为空，请输入内容。`
  - live region 投递：同一句。
- **只有「提交被拒」投递 live region**；脏值失焦校验只出视觉 + `aria-invalid` + `aria-describedby`，不投递——用户此刻正在移动焦点，读屏正在读新焦点元素，插播只会互相打断。
- 提交被拒时：**不清空任何已输入字段**（A5），焦点移到（或留在）标题输入框（继承 01）。
- `formAlert` 的清除时机：标题变为合法 / 提交成功 / 编辑态关闭（保存、取消、Esc、切到另一行）。

#### 5.4 提交按钮的禁用策略（D4）

**两处一致：都不禁用。**

- 编辑态「保存」：沿用 01 的理由——把已有标题清空后看到灰按钮会读作「界面卡了」，且禁用的 submit 会关掉浏览器隐式提交，Enter 变成毫无反应。
- 创建态「添加」：**由 `:disabled="!draft.trim()"` 改为不禁用**，理由三条：① A5 要求空标题提交时给出可见且可访问的原因说明，禁用态既拦不住也解释不了，Enter 直接静默无反应；② 禁用 submit 会使表单隐式提交失效，与 A3「快捷键唤起后直接 Enter」的反馈预期冲突；③ 两处策略一致，B1 的漂移面少一处。
- 代价与对冲：失去「按钮变灰＝还没输入」这条弱提示。对冲是第 5.3 节的明确错误反馈——用文字说明替代靠灰度暗示，本身也更符合 DESIGN.md「信息不单靠颜色/视觉状态传达」。

### 9. 可访问性

- **可见标签**：三个字段全部有可见 `<label for>`（DESIGN.md 表单基准）。这一并修掉现状创建表单标题只有 `aria-label="待办标题"` 的偏差（01 已指出并留给本任务）。
- **可访问名稳定**：计数器与错误文案都在 `<label>` 之外，只经 `aria-describedby` 关联，标题输入的可访问名恒为「标题」，不随打字变化。
- **键盘全通路**：
  - 创建：Tab → 标题输入 → 展开按钮 → 添加按钮 →（展开时）截止日 → 提醒。DOM 顺序＝视觉顺序（第一行从左到右，再往下）。Enter 在任一输入内隐式提交（提交按钮未禁用，故始终可用）。
  - 编辑：继承 01——标题 → 截止日 → 提醒 → 取消 → 保存 → Enter 提交 / Esc 取消。
  - 创建表单不注册任何 `document` / `window` 级监听（保持 01 给 `任务管理/04` 的边界：编辑态内 Ctrl+Z 让位给输入框原生撤销）。
- **展开控件的 ARIA**：`aria-expanded` + `aria-controls="create-details"` 指向 `v-show` 常驻的详情区容器；`aria-label` 随状态在「展开更多选项」/「收起更多选项」之间切换。
- **分组语义**：组用 `<fieldset>` + `<legend>`，读屏进入组时会报出组名（组标题隐藏时——即只有一组时——不渲染 `<legend>`，此时 `<fieldset>` 无名，与「详情区只有一堆字段」的实际结构相符）。
- **校验**：`aria-invalid="true"` + `aria-describedby` 指向错误文案；错误文案说明修复方式；提交被拒经单一 live region 播报（第 5 节）。**不新增 live region**（D3）。
- **不靠颜色单传**：计数器、上限、校验错误、提醒已过全部由文字直接说明。
- **对比度**：取值全部落在 DESIGN.md 已验证的 slate / red / amber 阶内。`default` 按钮白字压 sky-500 的偏差是 DESIGN.md「已知偏差」下的全局待决项，本任务不单独处理。
- **焦点环**：按设计意图书写（`focus-ring` / `focus:ring-2 focus:ring-sky-500`）。已知 `uno.config.ts` 的 `focus-ring` shortcut 实际失效（被 UnoCSS 当作 `focus` 变体 + `ring` 工具匹配），已转 `外观与设置/04` 处理，本任务不绕开、不自造替代写法。

### 11. 交给编排者 / 开发的说明

1. **对 01 规格文字的三处细化（请编排者过目；均不改 01 第 0 节的四条约定）**：
   - **包裹式 `<label>` → `for`/`id` 显式关联**。原因是硬的：计数器与错误文案若留在 `<label>` 内会并进标题输入的可访问名，并随打字持续变化。01 的「DOM 同构以便机械提取」是为本任务服务的手段，本任务正在执行提取，提取后两处共用同一份 DOM，同构问题消失。
   - **编辑态错误文案去掉尾句「或按 Esc 取消编辑」**，统一为「标题不能为空，请输入内容。」。原因：D2 要求两处措辞一致，而创建表单没有 Esc 语义；Esc 的可发现性由编辑表单里既有的「Enter 保存 · Esc 取消」提示行承担，没有丢失。

### 与规格的两处补充（未改动交互与视觉决策）

1. **提示条改为常驻 DOM，无内容时 `sr-only`**（`App.vue`）。规格第 5 节要求「不新增任何 DOM 节点」并补 `aria-atomic`，但现状的 `v-if="pageAlert"` 会让 live region 与它的第一条消息**同时**被插入 DOM——这是公认会导致读屏完全不播报的写法（live region 必须先于内容变化存在）。若保留 `v-if`，D1 的整套机制在实现层面就不成立。改法是：节点**始终**渲染（**仍然只有这一个节点，没有新增**），有内容时是原来的 `mb-6 rounded-lg px-3 py-2 + ALERT_TONE_CLASS`，无内容时整串类换成 `sr-only`。实测无内容时计算样式为 `position:absolute; width:1px; height:1px; margin:-1px; padding:0; clip:rect(0,0,0,0)`，**不占任何布局空间、页面观感与改造前完全一致**；`document.querySelectorAll('[role="status"]').length` 仍为 1。未新增设计令牌。
