# 任务依赖

- 级别：简化
- 状态：完成

## 需求（产品）

- 目标与场景：前置任务完成后，依赖任务才解锁可见/提醒，适合流程式任务。
- 范围（做 / 不做）：做 依赖设置、解锁逻辑、环检测（domain 校验）；不做 多级依赖可视化。
- 验收标准（逐条可检查）：
  - [ ] 前置未完成时依赖任务不提醒且有依赖标识；前置完成即解锁。
  - [ ] 环依赖被拒绝并提示；cargo test 覆盖环检测。

## 规格（UI/UX）

> 取值出处：色值/字号/间距均引自 `DESIGN.md` 或 `uno.config.ts`，逐处标注来源；末尾「设计令牌自查」列全部取值与出处，结论为**无新增设计令牌**。
> 契约事实（写规格的依据，非本任务改动，已实读 `crates/contracts/src/lib.rs`）：`Todo.depends_on: Vec<String>`（前置任务 id 列表，L114–115），`#[serde(default)]` 空列表默认；`validate_id_list`（L491–503）限制上限 200 项（`MAX_LIST_ENTRIES`）、id 去空白非空、id 不重复；自依赖由 `SelfDependency`（L160–162、错误文案 L803「a task cannot depend on itself」）拒绝。**契约不含环检测**——环检测需要看整个任务图，是 domain/store 侧逻辑（见「交编排者知悉」）。本子任务不改契约、不需 `types:generate`。

### 0. 组织方式与四个正面表态（编排者点名）

**组织方式 —— 平行的第四个兄弟区块 `DependencyList.vue`，不进 `TodoFields`、不进 `TodoDraft`。**

- 结论：在 `TodoItem.vue` 编辑态 `<form>` 内，**新增组件 `src/components/DependencyList.vue`**，渲染在 `<AttachmentList>` **之后**、「Enter 保存 · Esc 取消」动作条之前，成为 10/11 建立的 `<TodoFields>` → `<SubtaskList>` → `<AttachmentList>` 之后的**第四个平行兄弟区块**（顺序：`<TodoFields>` → `<SubtaskList>` → `<AttachmentList>` → `<DependencyList>`）。对外只收 `todo`（读 `dependsOn`）、对内直接调 store。
- 为什么不进 `TodoFields`（与 10/11 逐字同理）：`TodoFields` 同时被创建界面（`App.vue`）与编辑态渲染，任何进 `TodoFields`/`FIELDS`/`TodoDraft` 的东西都会一并出现在统一创建界面。依赖是「选**其他已存在的任务**作前置」——该任务必须已在任务图中才能被别人依赖或依赖别人，属**已存在任务**上的关联操作，不属统一创建阶段（与附件「挂在已存在任务上」同理）。故必须在 `TodoFields` 之外。**`TodoDraft`/`TodoFields.vue`/`FIELDS` 零改动，02 验收 B2（容器不被污染）不破**：`TodoItem.vue` 编辑态只多一行 `<DependencyList :todo="todo" />`，不因此获知任何标量字段名、列数、高度或滚动。`App.vue` 创建表单零改动，依赖不入统一创建界面。
- 关于 `TodoFields` 里预留的 `relation/关联` 组（`GROUPS` 常量含此键但当前无字段）：**本任务不往该组加字段**。依赖不是「单值控件」（它是「选一组其他任务的关系」，还牵动跨任务图的环检测与解锁派生），塞进 `control` 联合会炸掉「模板只 branch 于 `kind`」的封闭小集合，且一旦进 `FIELDS` 就会污染创建界面。依赖走独立兄弟区块，与子任务/附件同姿态。
- 依赖写入**不进 `TodoDraft`**：草稿仍只装标量字段。依赖的每次变更由 `DependencyList` 直接调 store（复用 `applyChange` + `recordHistory` 的既有编辑路径；开发侧需为 `FieldChange` 的 `Pick` 联合补 `"dependsOn"` 并新增承载 `dependsOn` 数组的 edit 通道 `editDependsOn(id, next)`，附 `sameDependsOn` 守卫使未变更不写空 op、不记空撤销——与 10 的 `editSubtasks`/11 的 `editAttachments` 同构；本规格只约定交互与提交粒度，不设计 store）。它独立于父任务草稿的「Enter 保存 / Esc 取消」：依赖是即时落库的离散操作，不随草稿保存/取消而提交或回滚。

**a) 选前置任务的入口 —— 搜索框 + 结果列表（就地组合原生 input 与 Button），不是原生 `<select>`。**

- 约束复述：`src/components/ui/` **没有**下拉/combobox/搜索选择器，只有 `Button.vue` 与原生 input；任务可能很多（列表已见 seed 200 项）。
- 结论：底部一枚 ghost「＋ 添加前置任务」触发按钮（占位与子任务/附件添加触发一致），点它**就地展开一枚搜索输入**（`<input type="search">`，`placeholder="搜索任务标题…"`）并聚焦；输入下方渲染一段**结果列表**（`<ul>`，每项一枚真实 `<button>`），按标题子串实时过滤候选任务；点某结果即把它加为前置（在上方「已选前置」清单里出现一行）。这套是「就地组合原生 input + 一列真 `<button>`」的最小可访问 combobox，与 `SubtaskList`/`AttachmentList` 的「点触发→就地展开输入→连续录入」节奏一脉相承。
- **为什么不用原生 `<select>`（含 `multiple`）**：① **无搜索**——任务多时（几十上百项）一个长下拉不可用，正是编排者点名要避免的「难用的长列表」；② 原生 `<select multiple>` 的多选交互（Ctrl/⌘+点）在触屏与新手用户上极不友好，移动端呈现更糟；③ 选项文本长（任务标题可达 500 码点）在原生下拉里无法截断/换行控制。搜索过滤 + 短结果列表在「多任务」下才可用。
- **不让它变成难用的长列表（关键）**：
  1. **结果列表封顶**：最多渲染前 **8** 条匹配（8 是一屏内可扫、Tab 停靠点可控的数量）；匹配超过 8 时在列表末尾显示一行非交互提示「还有 N 项，继续输入以缩小范围」（`text-xs` 次要文字）。Tab 停靠点因此始终 ≤8，不会把整份任务列表灌进 Tab 序。
  2. **空查询不是死路**：搜索框刚展开、查询为空时，默认列出**最近的、可作前置的开放任务**（同样封顶 8 条），让用户不必先打字也能选到常见项；打字即缩小。
  3. **候选剔除**（不出现在结果里）：任务自身（自依赖，契约 `SelfDependency` 亦会拒绝）、已选为前置的任务、以及**会构成环的任务**（由 store/domain 提供的「可达集」判定预先剔除，见 c）。这样绝大多数非法项根本不作为选项出现，用户少踩坑。
  4. 已完成任务**可**作前置（加进去即「前置已满足」），默认空查询列表优先开放任务、搜索可命中任意任务；不硬性排除已完成项。
- 可访问性（本入口）：搜索输入有可见/可访问 label「搜索任务」（`aria-label="搜索任务标题"`）；结果 `<ul>` 有可访问名（`aria-label="搜索结果"`），每条结果是**真实 `<button>`**（`aria-label="添加前置任务 <标题>"`，Tab 可达、Enter/点击加为前置），焦点可见（见「应对已知缺陷」用显式 `focus:ring-2 focus:ring-sky-500`）。选完一条后**保留搜索框与焦点**，可连续加多条（呼应添加框节奏）；结果为「真按钮列表」而非 roving-tabindex 的 `role=listbox`——在无 combobox 库、封顶 8 条的前提下，真按钮列表对键盘/读屏最稳妥、与兄弟组件同构（`SubtaskList` 上/下移、`AttachmentList` 触发均为真按钮）。（若日后引入 combobox 基础件，可升级为 `role="combobox"`+`role="listbox"`+方向键的标准模式；本期不做，属可逆增强。）

**b) 锁定态与依赖标识的呈现 —— 显示而非隐藏；折叠行加一枚中性「锁定」徽标，多前置显 `n/m` 计数。**

- **「隐藏 vs 显示」厘清与结论：锁定的依赖任务在列表里【显示且标记】，不隐藏。** 需求同时出现「有依赖标识」（倾向显示+标记）与「解锁可见」（暗示隐藏）两种措辞，取舍如下：
  - **「有依赖标识」要求它可见**——被隐藏的任务承载不了任何标识，两者不可兼得；既然明确要「有依赖标识」，就必须显示。
  - **完全隐藏会让用户找不到自己建的任务**（编排者点名的坑）：用户新建一个带前置的任务后它凭空消失，是严重的「东西不见了」体验。
  - **「解锁」的正确读法是「解锁＝可提醒/可行动」而非「解锁＝出现」**：与现状 `isNotStarted`（开始日在未来）完全同构——未开始的任务也是**显示但降调**（`TodoItem.vue` L447–453 只加一枚「X开始」徽标、不提醒、不隐藏）。锁定＝「已设定，但暂时无需为它行动」，与未开始是同一形态，故沿用同一处理：**显示、加徽标、不提醒**（不提醒见 d）。
  - 因此**不改 store `visibleItems`、不改 `App.vue` 列表**（锁定任务照常在列表里），容器进一步保持干净。
- **折叠行「锁定」徽标**（加在 `TodoItem.vue` 折叠行既有徽标 `<p>`（L365–454）那条 `flex-wrap items-center gap-2` 段落里，**与 10 的子任务进度徽标同处一处、同一手法**）：
  - `Lock` 图标（`lucide-vue-next`，16 内联档，`:size="14"` 与 Repeat/Flame/ListChecks 一致，`aria-hidden="true"`）+ 文本。前置 `sr-only`「依赖未完成：」，信息不孤靠图标/颜色（`DESIGN.md` 可访问性）。
  - **文案与多前置计数**：
    - 多个前置（`total > 1`）：显 `前置 {done}/{total}`（`tabular-nums` 防跳动），如 `前置 1/3`——一眼看出「完成了几个、还差几个」。
    - 单个前置（`total === 1`）：显 `待前置完成`；该前置的标题放进可访问名与 `:title`（标题可长，不进可见徽标以免撑爆行）。
  - **前置全部完成即解锁 → 徽标消失**：徽标仅在 `locked`（尚有前置未完成）时渲染；`done === total` 时 `locked` 为假、徽标不再出现，任务回归普通可行动行。这就是「前置完成即解锁」在界面上的表现。
  - **配色＝中性 slate**（锁定是「等待」不是「逾期」，绝不用 urgency 红；与未开始/周期 pill 同调）：`bg-slate-100 text-slate-600 dark:bg-slate-800 dark:text-slate-300`（未完成父行）／父任务已完成时 `text-slate-400 dark:text-slate-500`——两支与 `TodoItem.vue` 周期/进度 pill 现有分支逐字一致（出处 L390–393）。**tone 类串字面写在 `.vue`**，不抽到 `.ts`（避开 UnoCSS 不扫 `.ts` 缺陷，见「应对已知缺陷」）。非交互，无 focus、无 Tab 停靠，尺寸不作触控目标（同 Repeat/Flame/ListChecks pill）。
  - **徽标行 `v-if` 扩容**：把折叠行徽标 `<p>` 的 `v-if`（L365–366，现为 `todo.dueDate || subtaskTotal || todo.recurrence || notStarted`）追加 `|| lock.locked`，使**只有依赖、无任何日期**的锁定任务也能显示该行（与 10 追加 `|| subtaskTotal` 同法）。
  - **顺序**：`到期 → 进度 → 周期 → streak → 锁定 → 未开始`。锁定与未开始同属「暂不可行动」，紧邻排在末段；锁定比未开始更能解释「为何还不能做」，故置于未开始之前。
  - **不改标题样式**：与未开始一致，锁定只加徽标，**不给标题降对比/删除线**（完成/未完成两支保持原样，`TodoItem.vue` L344–348 不动），最小化容器改动。
  - **不阻止手动完成**：锁定只管「不提醒 + 加标识」，不禁用行首完成圈——用户仍可手动勾完锁定任务（最小惊讶；需求未要求以锁定阻断完成）。
- **锁定态派生是跨任务图逻辑**：折叠行需要一个 `lock = { locked, done, total }`，它要按 `todo.dependsOn` 的每个 id 去查**其他任务**的完成态——这是跨任务派生，`TodoItem` 只收 `:todo`，故由 store 提供一个 getter（如 `dependencyLock(id)`）。属开发/domain（见「交编排者知悉」），非契约改动。

**c) 环依赖的反馈 —— 被拒时走既有唯一 live region（transient error），环检测归 domain/store。**

- 界面表态（我只定「被拒时用户看到什么」）：用户尝试添加一个会构成环的前置（A 依赖 B、又让 B 依赖 A；或更长的传递环）时——
  - **首选：预先剔除**。会构成环的候选任务由 store/domain 的「可达集」判定**预先从结果列表剔除**（同 a/③），绝大多数环在「根本选不到」这一层就挡掉了，用户无需先犯错再被拒。
  - **兜底：提交被拒的播报**。即便预剔除，仍可能有竞态（另一端刚加了反向依赖）导致提交时才发现成环；此时 store/domain 拒绝写入，`DependencyList` 经 `form-alert.ts` 的 `announceFormAlert("error", "无法添加：这会让任务互相依赖（成环）。", "transient")` 写入页面**唯一** `role="status"` 区（`App.vue` L366），沿用 `page-alert.ts` 优先级仲裁——**不新建第二个 live region**。被拒的前置**不加入**（清单不出现该行），焦点留在搜索输入。
  - 与自依赖一致处理：自身已从候选剔除；万一漏过（竞态），契约 `SelfDependency` 亦拒绝，同样经该唯一 live region 播报（文案可用「任务不能依赖自己。」）。
  - 可选一致性增强（同 `AttachmentList` scheme 被拒）：在搜索输入下方就地加一条 `text-red-600 dark:text-red-400` inline 提示 + 输入 `aria-invalid`/`aria-describedby` 关联，作为唯一 live region 的视觉补充；权威播报始终是唯一 live region。默认可只走 live region，inline 为可选。
- **环检测本身归 domain/store**（我不实现）：需要遍历整个任务图判断「加入 P→T 是否成环」，属「范围（做/不做）」里点名的「环检测（domain 校验）」。见「交编排者知悉」。

**d) 「不提醒」的界面含义 —— 提醒时间字段照常可编辑；锁定期间不触发，解锁后按既有调度生效（含解锁时已过则即时补发一次）。**

- 我只定界面预期，调度逻辑归开发/提醒通知母任务。
- **提醒字段不做锁定特化**：用户仍可在 `TodoFields` 的「提醒时间」字段给一个锁定任务正常设提醒时间——**不禁用、不置灰**该字段（置灰会招致「为何不能设」的困惑，且与「锁定只管不提醒+加标识」的最小语义相符）。
- **界面预期的行为**：前置未完成（锁定）期间，该提醒**不触发**（被抑制）；前置全部完成（解锁）后，提醒按既有调度**生效**。若解锁那一刻提醒时刻已过去，则**即时补发一次**——这与现状「过期提醒下次启动即补发一次」（`notifications.ts` `scheduleReminder` 中 `delay <= 0` 分支 L121–124）、以及 `TodoFields` 的「提醒时间已过，保存后会立即提醒一次」提示（L293–298）同构，用户对该语义已有一致预期。
- **折叠行「· 已设提醒」的呈现**：到期徽标现会在 `reminderAt` 存在时追加「· 已设提醒」（`TodoItem.vue` L374）。锁定期间提醒不触发，但它确实「已设」，故**保留**该文字（它陈述「设了」而非「会立刻响」）；「解锁前不会提醒」这层含义由同行的**锁定徽标**承担（其可访问名可含「解锁前不提醒」）。不新增第二处提醒状态标记，避免噪声。
- **调度落地归属**：锁定期间抑制、解锁时（重新）武装、解锁时已过则补发一次——这些定时/调度改动在 store `refreshReminder`/`scheduleReminder`（`notifications.ts`）里做，属开发/提醒通知母任务边界，本规格只设界面预期（见「交编排者知悉」）。

### 1. 结构与布局

- **复用既有组件/令牌**：`Button.vue`（ghost 变体作「添加前置任务」触发、结果项、移除按钮）；`AttachmentList.vue` 的「就地展开输入 + 连续录入」节奏、行结构 `[图标 shrink-0][主标签 flex-1 min-w-0 truncate][移除 shrink-0]`、`min-w-0 truncate` 防横向滚动手法；`CONTROL_CLASS`/`LABEL_CLASS`（`TodoFields.vue` L423–425）；区块分隔线（`AttachmentList.vue` L231 / `SubtaskList.vue` L297）；提示走 `form-alert.ts`/`page-alert.ts` 既有单通道。
- **新增组件**：`src/components/DependencyList.vue`——自持依赖区的行结构/列数/高度/滚动；对外只收 `todo`（读 `dependsOn`）、对内直接调 store。渲染位置：`TodoItem.vue` 编辑态 `<form>` 内、`<AttachmentList>` 之后、「Enter 保存 · Esc 取消」动作条之前。
- **新增只读徽标**：锁定徽标加在 `TodoItem.vue` 折叠行既有徽标 `<p>`（L365）内，顺序/配色见 b。
- **区块内结构**（自上而下）：
  1. 顶部小标签「前置任务 `n`」（`n` = `dependsOn` 数量，`tabular-nums`），仅 `n ≥ 1` 时显示（＝`LABEL_CLASS`）。
  2. **「已选前置」清单** `<ul>`（每项一 `<li>`）：行布局 `[状态图标 shrink-0][前置标题 flex-1 min-w-0 truncate][移除 Trash2 shrink-0]`。
     - 状态图标：该前置**已完成**→ `Check`（`text-emerald-600 dark:text-emerald-300`，成功语义）；**未完成**→ `Circle`（`text-slate-400 dark:text-slate-500`，中性）。图标 `aria-hidden`，状态由行内 `sr-only`「已完成」/「未完成」承载（不孤靠图标/颜色）。
     - 前置标题：纯文本插值（无导航/跳转到该任务，超范围），`truncate` + `:title` 全标题。
     - **无法解析的前置**（id 指向的任务已删除或尚未同步入本机）：标题回退显示「（已删除或未同步的任务）」灰字，行仍可移除——用户不会被一个看不见的依赖卡死（附件「文件丢失降级不崩溃」同精神）。其「已完成/未完成」计入锁定的语义见「交编排者知悉」的边界项。

### 5. 可访问性

- **列表语义**：已选前置行包在 `<ul>`/`<li>`，读屏播报「列表 n 项」；结果列表同为 `<ul>`/`<li>`。区块 `<section aria-label="前置任务">`。
- **可访问名称**：搜索输入 `aria-label="搜索任务标题"`；结果按钮 `aria-label="添加前置任务 <标题>"`；移除按钮 `aria-label="移除前置任务 <标题>"`；「＋ 添加前置任务」触发 `aria-label="添加前置任务"`；前置行状态由 `sr-only`「已完成」/「未完成」承载（图标 `aria-hidden`，**不靠图标/颜色孤表**，`DESIGN.md` 可访问性）；折叠行锁定徽标前置 `sr-only`「依赖未完成：」、计数 `tabular-nums`，其可访问名/`:title` 含单前置标题或「解锁前不提醒」提示。
- **键盘全通路**：Tab 顺序＝视觉顺序（已选行：（标题非交互）→移除，逐行；添加区：触发 →（展开后）搜索输入 → 结果按钮 1..≤8）；结果按钮 Enter/空格加为前置；移除 Enter/空格触发；焦点可见（见「应对已知缺陷」）。结果封顶 8 使 Tab 停靠点有界。
- **ARIA/播报**：上限、成环/自依赖被拒经**唯一** `role="status"`（`aria-live="polite"`）播报（transient）；成环可选就近 inline + 输入 `aria-invalid`/`aria-describedby`（同 `TodoFields`/`AttachmentList` 字段错误模式）。状态不孤用颜色——前置完成态有文字、锁定徽标有图标+文字、移除是命名按钮。为避免占用唯一通道产生抖动，**不做逐键的匹配数播报**；读屏用户 Tab 进结果 `<ul>` 由「列表 n 项」获知数量。
- **焦点归还**：移除某前置后焦点落相邻行的移除按钮，或无剩余项时落「＋ 添加前置任务」触发（不落 `<body>`，与 `SubtaskList` `focusAfterDelete`/`AttachmentList` `focusAfterRemove`/行内编辑器 `returnFocus` 精神一致）。加一条前置后焦点留在搜索输入（连续录入）。
- **编辑态内 Ctrl+Z/Y**：编辑态下文档级撤销被挂起（`App.vue` L99–107 `isSuspended`）；依赖的增/删各记一条撤销条目（提交粒度＝一次离散动作一条记录，由 store `editDependsOn` + `recordHistory` 承担，口径由 04 覆盖）。

### 交编排者知悉（契约/引擎前置，非本规格实现）

1. **环检测（核心，需要跨任务图函数）**：给定任务图，判断「为 T 加入前置 P 是否成环（含传递环）」。需求「范围」已界定为 domain 校验、验收「cargo test 覆盖环检测」，属 domain/store，**契约不含**。理想同时提供：① 提交时的成环拒绝；② 供 a/③ 候选预剔除的「可达集」谓词（T 的传递依赖者集合，落在集合里的候选即会成环）。

3. **`editDependsOn(id, next)` 提交通道**：`FieldChange` 的 `Pick` 联合补 `"dependsOn"`，新增承载 `dependsOn` 数组的 edit 通道 + `sameDependsOn` 守卫（与 `editSubtasks`/`editAttachments` 同构）。`applyRemoteUpsert` 已支持 `dependsOn`（`todos.ts` L1283）、`patchFromTodo` 已含 `dependsOn`（L198）、`duplicate`/`buildNextInstance` 已刻意丢弃 `dependsOn`（L979/L1030），均无需改。
4. **提醒抑制/解锁重排（d）**：锁定期间抑制提醒、解锁时（重新）武装、解锁时已过则补发一次——在 `refreshReminder`/`scheduleReminder`（`notifications.ts`）里落地，属开发/**提醒通知母任务**边界。本规格只设界面预期。

### 编排者裁决（2026-07-24）

UI/UX 第 5 条边界语义：**无法解析的前置（已删除 / 尚未同步到本端）算「已满足」，不算「仍阻塞」**。理由：依赖一个本端根本不存在的任务，若算阻塞就会把依赖任务永久锁死且用户无从解锁（那个前置永远不会在本端「完成」）；算已满足则最坏是提前解锁，可恢复、可被用户重新设置。请开发按此实现并补 domain 测试覆盖（依赖不存在 id 时锁定态判定）。

其余四项前置（环检测跨任务图函数、`dependencyLock` getter、`editDependsOn` 通道、提醒抑制归提醒通知母任务）均确认在本任务范围内实现（提醒抑制的**调度落地**归提醒通知母任务，但本任务要把「锁定任务不排提醒」这条 gating 在现有前端排程路径 `rescheduleAll`/`notifications.ts` 上接通，使验收「前置未完成时依赖任务不提醒」可验；若发现必须改动 Rust 调度才能做，停下报告编排者）。

环检测请落 `crates/domain/`（纯图算法、不依赖 Tauri/HTTP/DB），与 06/07 的 domain 纯规则同层；store 侧候选预剔除可复用该函数的可达集。
