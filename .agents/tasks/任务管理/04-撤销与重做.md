### 【前置必办】「什么算一次改动」的口径

**口径**：与**提交时实际写入的值**同源——即归一化（标题 `trim` + 码点截断、备注码点截断）之后比较，且 `undefined` 与 `null` 视为同一状态（「从未设过」与「用户清空了」在本地是同一件事）。

落在两处，互为兜底：

1. **界面**（`TodoItem.save()`）：两侧草稿都过 `normalizeDraft` 再比。只在标题末尾加空格 → 判为未改动 → 直接关闭编辑态，`store.update` 根本不被调用。
2. **store**（`update`）：`PlannedEdit` 逐字段比对「要写的值」与「现在的值」，`plan.after` 为空就 `return`——不写内存、不落库、不出 op、不入撤销栈。这一层是结构性的：**任何**调用方（含未来的快捷录入、AI 助手）都不可能再把一条空操作塞进栈里，而不是只堵住编辑界面这一个入口。

`planField` 另有一条与同步直接相关的约束：`before` 侧一律存 `?? null` 后的值，绝不存 `undefined`——`undefined` 在 patch 里等于「本次没提这个字段」，撤销一次「设置截止日」时另一台设备就会保留刚被撤掉的日期。实测见下（撤销后末条 op 为 `{"dueDate":null}` 而非空 patch）。

### 撤销与同步的关系（模型与理由）

**模型：撤销是一次新的正向本地变更，产出一条新的出站 op（正向补偿），不试图撤回已推送的 op。**

理由：

- 同步协议是**只追加的操作日志**（`crates/server/src/sync_store.rs` 只有 `append` / `changes_since`，没有任何撤回或墓碑语义），已进入 `pending` 的 op 一旦被服务端确认就成为历史的一部分；客户端侧「从队列里挖掉一条」也不成立——它可能已经被别的设备拉走了。
- 因此撤销走的是与用户手动改回去**完全相同**的代码路径（`applyChange` / `deleteTodo` / `insertTodo`），拿到的收敛保证也完全相同，无需为撤销单开一条同步分支。
- 具体形状：撤销「完成」→ `{status:"open",completedAt:null}`；撤销「编辑」→ 携带**旧值**的字段级 patch；撤销「删除」→ 一条**全字段** upsert（`patchFromTodo`），因为对端此刻已经没有这条任务，patch 必须能把它整条建回来。
- 已知且可接受的一处不对等：`TodoPatch` 没有 `createdAt`，所以撤销删除后对端物化出来的任务 `createdAt` 取的是补偿 op 的 `occurredAt`（本机保留原值）。这是契约形状决定的，与本任务无关；其余字段两端逐字段一致（实测见下）。

### 栈深与溢出策略

- **上限 50 条**（`UNDO_DEPTH_LIMIT`），**溢出弃最旧**（`shift`）。
- 选 50：够覆盖一次连贯的误操作串（几次误点完成 + 一次误删 + 前后几次编辑），又不至于让栈底是用户早已不记得的状态；同时删除条目要留整行快照（备注上限 20 000 字），50 条的内存占用有明确上界。
- 选「弃最旧」而不是「拒收最新」：用户最想撤的永远是刚做完的那一次，满了就不记新的等于恰好丢掉那一条。
- **只在内存、不持久化**：撤销条目是「用户记得自己做过的那个动作」的逆操作，重启后没人记得，而这期间别的设备还在改同一批任务。
- 重做栈由撤销产生，任何新的被记录动作都会清空它（新动作是从被撤销的那个未来分叉出去的）。

### 让位给输入框原生撤销（01 划的硬边界）

- 判据用了 01 留的两个入口**各一半**：`App.vue` 的 `editingId !== null`（有行在编辑就整体让位，哪怕焦点不在输入框里），加上「事件目标是 `input` / `textarea` / `contenteditable`」（覆盖创建表单与设置面板里的输入框——它们不属于 `editingId`，但同样是用户在打字的地方）。
- 让位时**直接 return，不调 `preventDefault`**，浏览器的原生文本撤销原样执行。实测以 `defaultPrevented` 为判据（见下），比「看起来没反应」更硬。
- **确认过 Ctrl+Z 不受既有全局快捷键缺陷影响**：它是 webview 内的 `window.keydown`，`src/lib/undo-shortcut.ts` 不 import `@tauri-apps/plugin-global-shortcut`，与 `global-shortcut:default` 空权限集（`.agents/tasks/修复全局快捷键权限.md`）没有任何关系；反过来也不该走那个插件——全局注册会把 Ctrl+Z 从机器上**所有**其他程序手里抢走。理由写在该文件头注释里。

### 范围说明（明确不做的两件事）

1. **新建不入撤销栈**：需求节范围是「完成 / 删除 / 编辑」三类，`add` 未记录。副作用是新建也不清空重做栈（未被记录的动作不碰两个栈），这是一条可陈述的规则而不是遗漏。
2. **撤销不播报**：页面只有一个 live region，其三类来源的优先级与「被压住的提示必须满足二者之一」的约束是 03 规格第 5 节刚定完的；加第四类来源需要重跑那套核对，超出本任务范围。栈空时按 Ctrl+Z 静默（此时确实无事可撤），而**每一条入栈的条目都对应一次真实状态变化**，所以「按了没反应」只会发生在栈空时。一处如实记录的边界：只改备注这类字段的撤销，其状态变化在**收起的列表行**里看不见（03 规格第 8 节决定备注 / 时间段 / 估时不进列表行），重开编辑态可见值已改回。

### 一处顺带统一的行为（请评审知悉）

`toggle` 与 `update` 合流到 `applyChange` 后，提醒的处置只能有一条规则，取的是 `toggle` 原来那条：**已完成的任务不持有提醒**（`refreshReminder`）。改前 `update` 无条件 `scheduleReminder`，于是「编辑一条已完成任务」会把 `toggle` 刚取消掉的提醒重新装回时钟上；改后与 `rescheduleAll`（启动时只给 `open` 装）也一致了。这是合流的必然结果，不是顺手重构。

### 走查证据（`pnpm run dev` + 浏览器，事件均为派发的真实 `InputEvent` / `MouseEvent` / `KeyboardEvent`）

以下每条都是实测读数，不是自述。`ops` 指 `localStorage["sync.pending"]`。

1. **撤销 / 重做「完成」**：完成 走查A → op `{"status":"completed","completedAt":"…21:46.443Z"}`；Ctrl+Z → 行回到未完成，**新增**一条 op `{"status":"open","completedAt":null}`；Ctrl+Y → 重新完成，`completedAt` 仍是 `…21:46.443Z`（**原时刻，不是新的**）。
2. **撤销 / 重做「删除」**：删除 走查A → `delete` op，行消失；Ctrl+Z → 行回到**原来的位置**（列表第 2 行）、id 不变（`cfab…`）、完成态与所有字段还原，新增一条**全字段** upsert op；Ctrl+Y → 再次 `delete` op；Ctrl+Z → 再次还原。四步共 4 条 op，全部是正向补偿。
3. **撤销「编辑」**：改标题「走查A 撤销目标」→「走查A 改过的标题」，op `{"title":"走查A 改过的标题"}`；Ctrl+Z → 标题回退，op `{"title":"走查A 撤销目标"}`。
4. **【前置必办】只加尾随空格**：把标题改成 `走查A 改过的标题   ` 后点保存 → 编辑态正常关闭，`ops` 数 **10 → 10（零增长）**；随后按一次 Ctrl+Z，撤销的是**上一次真实编辑**（标题回到「走查A 撤销目标」），证明那次空保存没有在栈里留下条目。
5. **store 层空操作守卫**（绕开界面直接调 `update`，逐条读 op 增量）：`{dueDate:null}`（本来就没有）+0、`{title:"   键集对照   "}` +0、`{estimatedMinutes:null}` +0、`{notes:null}` +0、`{title:""}` +0；`{dueDate:"2026-09-01"}` +1（真实改动）。随后 Ctrl+Z → `dueDate` 回到 `null`，末条 op 为 **`{"dueDate":null}`**（显式 null，不是空 patch）——`planField` 的 `?? null` 有效。
6. **编辑态让位**：编辑态打开、焦点在标题框内按 Ctrl+Z → `defaultPrevented === false`、store 快照逐字节不变；焦点移到表单（非输入框）再按 → 同样 `false`（`editingId` 判据生效）；Ctrl+Y 同样 `false`。创建表单标题框内按 Ctrl+Z → `false`、store 不变。取消编辑后同一个 Ctrl+Z → `defaultPrevented === true` 且确实撤销了上一步。
7. **栈深受控**：连点 60 次完成/取消完成（产生 60 条 op 与 60 条记录）→ 按 60 次 Ctrl+Z，**恰好 50 次产生了新 op**，第 51 次起无事发生；再按 60 次 Ctrl+Y，**恰好 50 次**生效。上限与溢出弃最旧双向对齐。
8. **新动作清空重做栈**：完成 B → Ctrl+Z（可重做）→ 完成 A（新动作）→ Ctrl+Y **无任何 op、无状态变化**。
9. **陈旧条目被跳过而不是空转**：编辑 A（条目 E1）→ 完成 B（条目 E2）→ 以入站身份 `applyRemoteDelete(A)`（不记历史）→ Ctrl+Z 撤销的是 E2（B 回到未完成，1 条 op）→ 再 Ctrl+Z 时 E1 的目标已不存在，被丢弃并继续向下取到可执行的一条。反向同理：删除 C（条目）→ 远端把 C 建回来 → Ctrl+Z 到该条目时 `insertTodo` 因 id 已存在而拒绝，跳过，**没有产生重复行**。
10. **同步进来的坏数据仍可原样关闭编辑态**：以入站身份推入 `endsAt` 早于 `startsAt` 的任务 → 打开编辑态（字段红字可见）→ 直接点保存 → **正常关闭、零 op**（归一化比较未破坏 03 建立的这条行为）。
11. **只改备注**：保存 → op `{"notes":"第一版备注"}`；Ctrl+Z → 备注回到原值，op 携带原值。
12. **第二条并入项（提示按身份收回）**——03 评审给的失效路径逐步复现：估时 `0` 提交被拒（提示条=「估时请填写大于 0 的整数分钟，或留空。」）→ 标题打到 500（提示条转为「标题已达上限，最多 500 字。」）→ 把估时改成 `12` → 提示条**仍是「标题已达上限，最多 500 字。」**（修前此处变空），估时的 `aria-invalid` 已撤销，计数器「已达上限 500 字」常驻；再把标题降到 499 → 提示条清空；再回到 500 → **重新播报**（去抖状态未被卡死）。
13. **规格 5.4 清除时机表其余行未变**：提交被拒后在**别的**字段（备注）打字 → 不清除；在出错字段打字 → 立即清除；再次被拒后改成合法值并提交成功 → 清除。全程 `role="status"` 恒为 1 个。
14. **两端数据一致（真服务端）**：把第 1–3 类操作各做一遍并各撤销一次（新建 → 完成 → 撤销 → 改名 → 撤销 → 删除 → 撤销）产生的 **7 条 op 原样 POST 给 `cargo run -p todo-server`**（`DATABASE_PATH`/`BACKUP_DIR` 指向临时目录），7 条全部 acked、`nextCursor=7`；再以设备 B 身份 `cursor=0` 拉取，并把回包按 revision 顺序喂给**应用真实的入站合并路径**（`applyRemoteUpsert` / `applyRemoteDelete`）→ 设备 B 得到 1 行，`title="同步走查任务"`、`status="open"`，其余字段全空，与设备 A 逐字段一致。唯二差异均为既有形状而非本次引入：① `createdAt`（见上「模型与理由」末条）；② `recurrence`/`listId`/`important`/`urgent`/`sortOrder` 五个键在设备 A 上**不存在**、在设备 B 上是 `null`——已单独实证这是 `add` 与入站物化的既有差异（本机 `add` 从不写这五个键），两者语义同为「未设置」。

**零视觉改动**：本任务未增删任何 DOM 节点与类串，不涉及 DESIGN.md 令牌，因此未做暗色 / 响应式复测（无可复测的差异）。今日卡片走既有 `watch(() => store.items, …, { deep: true })`，撤销引起的列表变化与编辑 / 删除走同一条推送路径，机制未改。
