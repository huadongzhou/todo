# 多 Agent 协作流程

本文件定义仓库研发的角色分工、任务文件与编排规则，是多 Agent 流程的唯一事实源。角色职责细节见 `roles/`；工程规范与验证命令一律以根目录 AGENTS.md 为准，本目录不重复、不覆盖其内容。

## 总览

三种任务级别对应三条流程，⇄ 表示评审回路（循环至阻塞问题清零）：

```text
全流程： 产品 → UI/UX → 开发 ⇄ 评审 → 完成
简化：          UI/UX → 开发 ⇄ 评审 → 完成
直达：                  开发 ⇄ 评审 → 完成
```

## 角色

| 角色 | 角色文件 | 职责 | 允许写入 |
|------|---------|------|---------|
| 产品 | roles/product.md | 澄清需求，定义范围与验收标准 | 仅任务文件「需求」节与状态行 |
| UI/UX | roles/ui-ux.md | 依据 DESIGN.md 产出交互与视觉规格 | 仅任务文件「规格」节与状态行；经编排者确认的新增设计令牌可同步进 DESIGN.md（全局规则 3） |
| 开发 | roles/dev.md | 按验收标准与规格实现并自验 | 代码、TODO.md 功能点状态、任务文件的实现记录/处理结果与状态行 |
| 评审 | roles/reviewer.md | 评审代码、运行验证、输出问题清单 | 仅任务文件「评审记录」节与状态行 |

## 任务分级

| 级别 | 判定规则 | 阶段序列 | 任务文件初始状态 |
|------|---------|---------|----------------|
| 全流程 | 新功能、需求变更 | 产品 → UI/UX → 开发 ⇄ 评审 | 需求 |
| 简化 | 需求已明确、只改界面或交互 | UI/UX → 开发 ⇄ 评审 | 设计 |
| 直达 | Bug 修复、重构、文档、构建脚本 | 开发 ⇄ 评审 | 开发 |

拿不准级别时取更高级别；简化级任务不涉及视觉变化时可由编排者降为直达。

## 任务文件

- 位置与命名：单任务为 `.agents/tasks/<任务名>.md` 平铺文件；大型任务为 `.agents/tasks/<母任务名>/` 文件夹，内含 `_母任务.md` 与子任务文件（见「母任务」节）。一个任务一个文件；任务名与文件名用简短中文或小写短横线英文，不含空格与斜杠。
- 创建：单任务与子任务由编排者复制 `tasks/_template.md` 创建，填写级别与初始状态；`_母任务.md` 以 `tasks/_template-epic.md` 为底（见「母任务」节）。
- 单任务与子任务结构固定为五部分：头部（级别、状态）、「需求（产品）」、「规格（UI/UX）」、「实现记录（开发）」、「评审记录」（按轮追加）。
- 简化与直达级不派发产品角色：「需求」节的目标与验收标准由编排者建文件时依据用户请求填写（一两条即可），后续角色照常引用。
- 单任务与子任务状态行取值仅限五个：需求 / 设计 / 开发 / 评审 / 完成；`_母任务.md` 为四值（见「母任务」节）。
- 评审条目下的追加行仅四种：「处理（开发）：」「处理（编排者）：」「复核（评审）：」「裁决（编排者）：」，一律追加、不改写原条目。

## 状态机

状态只能按下表流转，禁止跳转或私自回退：

| 当前状态 | 工作角色 | 该角色做什么 | 完成后置为 |
|---------|---------|-------------|-----------|
| 需求 | 产品 | 写「需求」节 | 设计（编排者确认无界面工作时置「开发」） |
| 设计 | UI/UX | 写「规格」节 | 开发（规格含「新增设计令牌」时保持「设计」待编排者裁决，采纳并同步 DESIGN.md 后置「开发」） |
| 开发 | 开发 | 首次实现并自验；评审记录有未处理的阻塞条目（或带「裁决（编排者）：本轮处理」行的建议条目）时则逐条处理 | 评审 |
| 评审 | 评审 | 新起「第 N 轮」写问题清单并运行验证 | 无阻塞 → 完成；有阻塞 → 开发 |
| 完成 | —（终态） | 编排者收尾 | —（唯一例外：收尾裁决处理遗留建议或争议条目时，编排者可置回「开发」） |

## 编排步骤

编排者是主会话（人 + 主 agent），不设「经理 agent」。逐步执行：

1. **定级**：按「任务分级」判定规则确定级别，拿不准取更高级别。
2. **建文件**：复制 `tasks/_template.md` 为 `tasks/<任务名>.md`，填级别；状态按级别置初始值（全流程=需求，简化=设计，直达=开发）；简化与直达级同时在「需求」节填写目标与验收标准。
3. **派发**：查「状态机」表得到当前状态的工作角色，用下方「派发调用模板」派发，等待其完成。派发回流修复时若要求一并处理某建议条目，先在该条目下追加「裁决（编排者）：本轮处理」再派发——不落盘的口头点名无效。
4. **阶段验收**：角色返回后检查两件事——① 任务文件对应章节已写入实际内容；② 状态行已按状态机表更新。任一不满足，退回该角色补齐：编排者先把状态行改回本阶段对应值（此回退属阶段验收动作，不算违规），再重新派发。设计阶段另查一项：规格含「新增设计令牌」时 UI/UX 会保持状态「设计」等待裁决——采纳则令 UI/UX 把令牌同步进 DESIGN.md 后置「开发」，不采纳则令其改用既有令牌后置「开发」。
5. **循环**：重复步骤 3–4，直到状态为「完成」。
6. **收尾**：裁决对象为两类——条目下没有任何「处理（编排者）」或「裁决（编排者）」行的建议级条目；没有「裁决（编排者）」行的「复核（评审）：不认可，提请编排者裁决」争议条目（已带这些行的条目即已裁决，不重复处理）。逐条裁决，三选一——不处理/维持不改：在条目下追加「处理（编排者）：<理由>」；本次处理：先在原条目下追加「裁决（编排者）：升级为阻塞，见第 N 轮（收尾裁决）」（注意措辞不得写成「本轮处理」，那是派发开发的触发标记），再在「评审记录」末尾新起「### 第 N 轮（收尾裁决）」小节（N＝已有轮数＋1），把该条目以「阻塞」级别复制为新条目并注明「沿自第 X 轮」，状态置回「开发」重入回路——这是唯一允许离开「完成」的流转，仅编排者可执行；超出本任务范围：另建任务并在条目下追加「处理（编排者）：转任务处理」。最后确认 TODO.md 已由开发同步。流程不含 git 提交步骤，是否提交由用户决定。

任务中断后恢复：任务文件已存在时不重建，读其状态行后直接从步骤 3 继续。

### 派发调用模板

派发任一角色时使用以下提示词，尖括号处填实际值：

```text
你现在担任「<角色名>」。
1. 完整阅读 .agents/roles/<角色文件名>，严格遵守其中的职责、工作步骤、产出与禁止事项。
2. 完整阅读任务文件：<任务文件路径>（单任务为 .agents/tasks/<任务名>.md，子任务为 .agents/tasks/<母任务名>/<序号>-<短名>.md，母任务为 .agents/tasks/<母任务名>/_母任务.md）。
3. 本次补充要求：<无，或编排者的具体指示>。
4. 完成后：把产出写入任务文件的规定章节，按 .agents/workflow.md「状态机」更新状态行
   （任务文件为 _母任务.md 时不动状态行，其状态由编排者管理），
   并汇报你写入了什么、状态置为了什么、有哪些遗留问题。
禁止修改角色文件允许范围之外的任何文件。
```

## 母任务（大型任务拆解）

单任务流程处理不下的大型任务，升格为母任务：一个文件夹装下 `_母任务.md` 与 N 个子任务文件；子任务就是普通任务，原封不动走上文的五状态状态机与编排步骤。

### 结构与命名

```text
.agents/tasks/<母任务名>/
  _母任务.md          # 以 tasks/_template-epic.md 为底创建，不走五状态状态机
  01-<短名>.md        # 子任务，以 tasks/_template.md 为底创建，各自走单任务流程
  02-<短名>.md
```

- 子任务文件名＝两位序号-短名；引用子任务写 `<母任务名>/<序号>-<短名>`。
- `_母任务.md` 状态行取值仅限四个：拆解 / 进行 / 集成验收 / 完成。
- 「拆解清单」不设状态列——子任务进度以各子任务文件的状态行为唯一事实源，查进度＝遍历文件夹内除 `_母任务.md` 外所有 .md 的状态行。

### 升格判定

编排者判断任务无法在一次开发 ⇄ 评审回路内完成（跨多个模块、含多个可独立验收的交付物、或验收标准明显装不进一个任务文件）时升格为母任务。拿不准时不升格：先按单任务执行，执行中角色按全局规则 5 停下上报时再拆。

### 母任务步骤

1. **建文件夹**：创建 `tasks/<母任务名>/`，复制 `tasks/_template-epic.md` 为其中的 `_母任务.md`，状态置「拆解」。
2. **整体需求**：全流程级内容派产品角色写「需求（整体）」节（含整体验收标准）；简化/直达级内容由编排者填写。阶段验收只查「需求（整体）」已写实——`_母任务.md` 的状态行由编排者管理，任何角色不动它。
3. **拆解**：编排者填「拆解清单」表——序号 · 子任务文件 · 级别 · 依赖（序号或「无」）· 一句话验收。拆解原则：一个子任务只做一件事、可独立验收、能独立过一轮评审；子任务各自定级，不必与母任务同级。
4. **确认门**：拆解完成后停下报告用户，等确认后状态置「进行」；用户说过「拆完直接跑」则直接置「进行」。
5. **逐个执行**：按「编排步骤」执行子任务，两处替换——跳过定级（级别以拆解清单为准）、建文件路径按本节「结构与命名」；子任务「需求」节从拆解清单与整体需求派生。只派发依赖已全部完成的子任务；默认按序号串行，声明「无依赖」且改动文件集不相交的子任务才允许并行。子任务评审时，工作区中属于此前已完成兄弟子任务的改动不算「清单遗漏」，评审可对照兄弟子任务的「实现记录」排除。
6. **集成验收**：全部子任务状态＝完成后，`_母任务.md` 状态置「集成验收」。编排者对照整体验收标准逐条核对，并派评审角色做一轮跨子任务集成评审——范围＝各子任务「实现记录」的并集，重点查拼接处：重复实现、不一致的交互、端到端链路缺口。结果按评审记录条目格式写入「集成验收」节（按轮追加，规则同评审记录）。评审角色按 roles/reviewer.md「集成评审（母任务）」节执行。
7. **问题回流**：集成验收发现的阻塞问题一律新增修补子任务（追加序号，通常直达级），并在对应条目下追加「处理（编排者）：转子任务 <序号>」——子任务的「完成」是终态，不回退。建议级条目由编排者裁决：处理→同样转修补子任务；不处理→条目下追加「处理（编排者）：<理由>」。修补子任务完成后做下一轮集成验收，循环至通过。
8. **完成**：通过的判定＝本轮无阻塞条目、此前「转子任务」条目均已复核认可、建议级条目均已裁决；通过后状态置「完成」。

### 变更与恢复

- 执行中调整拆解：取消的子任务在清单行尾追加「已取消：<理由>」（文件与清单行不删）；新增子任务追加新序号。历史不改写。
- 中断恢复：读 `_母任务.md` 状态行——「拆解」继续拆解；「进行」扫子任务状态行，对未完成者按依赖续派（拆解清单中尚未建档的行视为未开始）；「集成验收」继续验收循环。

## 全局规则

对所有角色生效；与角色文件冲突时以本节为准，与 AGENTS.md 冲突时以 AGENTS.md 为准：

1. 单任务与子任务的状态行只能取五个值之一，只能按「状态机」表流转；例外仅两处且均属编排者——阶段验收退回（步骤 4）与收尾裁决（步骤 6）。`_母任务.md` 的状态行按「母任务」节的四值流转。
2. 除开发角色外，禁止修改 `src/`、`src-tauri/`、`crates/` 及根目录配置文件。
3. 阶段交接内容只写任务文件，禁止写入 PRODUCT.md、DESIGN.md、TODO.md 等根目录文档。沉淀性变更是仅有的例外：开发按 AGENTS.md 同步 TODO.md 功能点状态；UI/UX 新增设计令牌经编排者确认后同步 DESIGN.md。
4. 「评审记录」只追加不覆盖：每轮新起「### 第 N 轮」小节，禁止删除或改写历史轮次；开发的处理结果以追加形式写在问题条目下。
5. 任何角色遇到无法自行决定的问题：把问题写进任务文件对应章节末尾，保持状态不变，停止并报告编排者；禁止擅自扩大或缩小范围。
6. 验证命令只用 AGENTS.md「应用命令」节列出的命令。

## 示例

以新功能「番茄专注计时」为例（全流程）：

1. 编排者建 `tasks/番茄专注计时.md`，级别=全流程，状态=需求。
2. 产品写「需求」节（目标与场景、范围、验收标准）→ 状态=设计。
3. UI/UX 查 DESIGN.md 与 uno.config.ts 后写「规格」节 → 状态=开发。
4. 开发实现，`pnpm run check` 通过并手动走查，填「实现记录」（改动文件、自验结论），更新 TODO.md → 状态=评审。
5. 评审第 1 轮：按「实现记录」的文件清单评审，1 条阻塞、1 条建议，运行验证命令 → 状态=开发。
6. 开发只处理阻塞条目，处理结果追加在条目下，更新「实现记录」→ 状态=评审。
7. 评审第 2 轮：复核有「处理（开发）」行而未复核的条目与新增改动，逐条追加「复核（评审）：认可」，通过 → 状态=完成。
8. 编排者收尾：裁决遗留建议条目，确认 TODO.md 已同步。

评审记录条目与处理结果的格式：

```markdown
### 第 1 轮

- 阻塞 · src/components/TodoItem.vue:42 · v-for 缺稳定 key · AGENTS.md Vue 规范
  - 处理（开发）：已修复，改用 todo.id 作为 key
  - 复核（评审）：认可
- 建议 · src/stores/todo.ts · 计时逻辑可下沉组合式函数 · 简约至上
  - 处理（编排者）：本次不处理，已知悉

验证：pnpm run check 通过
```

## 与 Claude Code 的关系

- 角色文件采用 subagent 兼容格式（frontmatter 含 name/description，tools 可选，省略即继承全部工具）。Claude Code 只自动发现 `.claude/agents/` 下的定义，本目录文件经「派发调用模板」由 subagent 自行阅读生效；如需自动发现可复制到 `.claude/agents/`。
- 通用缺陷深挖可由编排者另行运行内置 `/code-review`；本流程评审角色侧重项目私有标准（AGENTS.md 规范、DESIGN.md 还原、验收标准覆盖）。
