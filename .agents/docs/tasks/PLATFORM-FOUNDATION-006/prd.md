# PRD：同步传输与设备通信

## 目标

让桌面客户端通过 HTTP 与既有的 Axum 服务端同步待办变更，实现跨设备（以及同设备重启后）的状态一致。服务端是同步的权威来源；客户端在启动时从服务端拉取变更，在本地变更后把操作推送给服务端。

## 范围

### 包含

- 客户端同步传输层：通过 `fetch` 调用 `POST /v1/sync` 与 `GET /health`，复用既有 `todo-contracts` 契约（`SyncRequest` / `SyncResponse`）。
- 同步引擎：把本地待办变更记录为同步操作（upsert / delete），维护设备身份（`device_id`）与游标（`cursor`），在启动时与变更后自动同步。
- 远端变更合并：把服务端返回的 `TodoSyncChange` 按修订顺序合并到本地 store（服务端优先 / 字段级合并），不产生循环记录。
- 设备身份：首次启动生成并持久化 `device_id`，在设置页可见。
- 设置页：配置服务端地址、手动触发同步、显示同步状态与设备 ID。
- 浏览器 / 移动端降级：无服务端时安全跳过，不阻塞启动。

### 不包含

- 本地持久化（SQLite / 文件）：当前 todos store 为纯内存，服务端作为状态来源，启动时通过同步重建。
- 实时推送（WebSocket / SSE）：当前为拉取 + 变更后推送，实时通道留作后续。
- 账户与鉴权：同步暂不鉴权，设备仅凭 `device_id` 标识。
- 冲突 UI：字段级以服务端优先自动解决，不弹冲突选择。

## 用户故事

- 作为桌面用户，我希望在一台设备上的变更能在另一台设备同步后看到。
- 作为用户，我希望重启应用后待办能从服务端恢复。
- 作为用户，我想知道当前同步状态和服务端是否可达。

## 验收标准

1. 客户端启动后能从服务端拉取变更并重建本地待办。
2. 本地新增 / 完成 / 删除 / 编辑待办后，变更被记录并在自动同步时推送给服务端。
3. 服务端返回的远端变更正确合并到本地 store，不产生循环记录。
4. `device_id` 生成并持久化，设置页可见。
5. 浏览器 / 移动端不阻塞启动。
6. 设置页可配置服务端地址、手动同步、显示状态。
